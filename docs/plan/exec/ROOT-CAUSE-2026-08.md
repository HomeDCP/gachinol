### 1-1. 결정적 증거 — 정상적 개선이 잠복 결함을 깨웠다

`apps/reporter/app/(app)/contents/new/index.tsx`의 촬영 핸들러:

```ts
const video = await camera.recordAsync();
if (video) {                                    // 웹: {uri:''} 는 truthy
  setMedia({
    uri: video.uri,
    sizeBytes: 0,                               // ← 주석: "Mock 업로드라 무해"
  });
}
```

`expo-camera`의 웹 구현은 `record()`가 `console.warn` 후 **`{uri: ''}`를 반환**한다
(`ExpoCamera.web.js:71-74` 실측). 빈 객체가 truthy라 그대로 통과한다.

**이 주석이 결함의 전모다.** 이 코드가 쓰였을 때는 업로드가 목이라 정말 무해했다. 그런데
**T-W2-02(웹 업로더 실동작)가 그 전제를 깨뜨렸고 주석만 남았다.**

⇒ **검사 범위를 넓히지 않으면, 앞으로의 모든 정상적 개선이 같은 방식으로 잠복 결함을 깨울 수 있다.**
이것이 이 문서의 핵심 명제이며, 순서를 정하는 축이다.

## 3. MVP 정의에 구멍이 있다

CLAUDE.md와 ROADMAP이 정의한 MVP는 **"기자 업로드 → 카톡채널 송출 → 구독자 시청"** 한 바퀴다.
그런데 **가운데 토막이 실재하지 않는다.**

- 배포 기본값은 `KakaoMockAdapter`(항상 성공하는 가짜).
- 반자동 게시 모델이 요구하는 **게시자산 준비 경로가 0줄**. `go-link.module.ts:16` 주석이
  *"후속: 반자동 게시자산 준비가 `buildShareLinks`를 소비(조치 2)"*라고 **아직 없음을 자인**한다.
- 카카오 메시지에는 **15분 만료 presigned URL**이 실린다(`distribution-producer.service.ts:122,129`,
  `DOWNLOAD_URL_TTL_SEC` 기본 900). 담당자가 나중에 손으로 게시하면 **링크가 이미 죽어 있다**(#175).
- **YouTube 송출 어댑터는 아예 없다**(#176). youtube 채널로 distribute하면 워커가
  `지원하지 않는 플랫폼`으로 failed 처리한다.
- **계획에 태스크가 아예 없다**(#184). 피벗 계획이 *"바뀌지 않는 것: 백엔드 전체"*로 선언해
  송출 백엔드를 완성된 것으로 전제했다. E2 §0의 비범위 선언에도 없으므로 **배제가 아니라 누락**이다.

### 3-1. "env를 켜면 실 제공자가 켜진다"는 전제가 세 곳에서 거짓이다 (#174)

실 어댑터 3종이 전부 **무조건 예외를 던진다** — 카카오 `publish` throw, SNS 댓글 `poll` reject,
ai-worker `raise NotImplementedError`. 키를 설정하는 순간 동작이
**"항상 성공(목)"에서 "항상 실패"로 더 나빠진다.** env 스키마는 이 조합을 거부하지 않는다.

⇒ 이 리포의 *"게이트만 열면 된다"*류 서술 전반을 재검토해야 한다.
**코드 관점의 진술이 운영 관점에서 거짓인 유형**이다.

## 4. 정본을 끝까지 수행해도 제품이 완성되지 않는다

- `01-product-strategy.md`가 *"제품 최종 가치(AI가 편집해 방송국이 송출)는 **T-AI 완료 후에 성립**한다"*고
  규정한다.
- 그런데 `08-rollout-transition.md`는 **T-AI가 W0~W4 어느 DoD에도 포함되지 않는다**고 선언하고,
  E2는 *"본 문서에 태스크를 만들지 않는다"*로 확정한다.
- 그리고 그 T-AI의 실체인 **auto_edit Phase 2(글콘티 3지선다)·Phase 3(아카이브 매칭)의 범위 정의가
  리포 전체에 ROADMAP 1행뿐**이다(#183). 설계 원천이 **리포 밖**에 있다.

⇒ **정본을 완주해도 정본 자신이 정의한 종착점에 도달하지 않는다.** 그리고 사용자가
*"이 기능을 얼마나 잘 구현하는지가 서비스의 성패를 판가름한다"*고 규정한 바로 그 기능의
범위가 계획에 없다.

### 4-1. 완성 기준이 서로 다른 것을 가리킨다

| 출처 | 완성의 정의 |
|---|---|
| `08` W4 DoD | 문서·CI 반영 완료, 네이티브 트랙 잔재 0 |
| `01` §A-1 | 제품 최종 가치는 **T-AI 완료 후** 성립 |

**기술 런칭·대외 런칭·제품 완성이 세 개의 다른 종착점**이며, 어느 것도 다른 것을 함의하지 않는다.

| **1. 도달 경로 자동화** | api·워커 CD 편입 · 배포 후 스모크 · 파괴적 마이그레이션 게이트 · 모니터링 최소 구현 | 0단계를 사람이 매번 하면 또 stale이 된다. **오늘 하루에 "고쳤는데 도달하지 않았다"가 3건 실측**됐다 |
| **2. 검사 범위 확장** | 웹 경로 로드 · 계약-구동 게이트 확장 · e2e CI 편입 · 판정 도구 수리 | **미래 결함을 막는 유일한 층.** 3·4단계의 수리가 회귀 방어를 받으려면 선행돼야 한다 |
| **3. 정본 재정합** | Distribute 실 송출 태스크 신설 · auto_edit Phase 2·3 범위 · STT 로컬 전환 반영 · 인벤토리 복구 | 4단계에서 만들 것들이 정본에 **자리가 없다**. 규율 13과 사용자 원칙("정본 순서부터 확인") |
| **4. MVP 한 바퀴 실성립** | 기자 웹 촬영(#173) · #168 교착 · 카카오 게시자산(#175) · 주민 제보 수정 액터(#136) | 0~2단계 없이 만들면 도달하지 않거나 곧 깨진다 |
| **병렬(0단계부터 상시)** | 사업자등록 · 법률자문 계약 · 스토어 계정 · 도메인 | 코드가 못 열고 리드타임이 길다 |

**기능이 아니라 배포·검사가 먼저인 근거 3가지**
1. 오늘 **"고쳤는데 도달하지 않았다"가 세 건 실측**됐다. 그 위에 기능을 쌓으면 반복된다.
2. 카메라 결함은 **T-W2-02라는 정상적 개선이 활성화**시켰다(§1-1). 검사 범위를 넓히지 않으면
   앞으로의 모든 개선이 같은 방식으로 잠복 결함을 깨울 수 있다.
3. 사용자가 반복해 말한 **"기본틀을 잡아두고 고쳐나간다"**가 정확히 이 순서다.

**다만 하나는 미루지 않는다** — auto_edit Phase 2의 **범위 정의**(#183). 정본은 이것을
"W2 완료 후"로 두었지만 **W2는 지출·사람 트랙 때문에 종료가 불가능한 상태**이고, 사용자는 이
기능이 서비스의 성패를 가른다고 규정했다. 구현을 당기자는 것이 아니라 **3단계에서 범위 정의만이라도
정본에 넣자**는 것이다.
