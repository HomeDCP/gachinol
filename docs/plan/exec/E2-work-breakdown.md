## A. 태스크 크기 기준 (G2)

**정의**: 1태스크 = **서브에이전트 1회 기동으로 구현+테스트+자가 검증까지 완결되는 단위**(E5 §A 게이트① 1회 실행
범위와 1:1 대응). 크기 상한은 **수정 파일 ≤10개 대략** — 절대 규칙이 아니라 "이 이상이면 분할을 먼저 검토하라"는
신호다. 아래 3가지는 **분할 예외**(초과해도 분할하지 않는 근거를 명시하는 조건)로 인정한다:

1. **게이트 완결성**: 두 하위 작업을 분리하면 어느 쪽도 단독으로 상위 문서의 완료 조건(DoD)을 충족하지 못하는 경우
   (예: `packages/ui` 토큰 — "스키마 반영만으로는 게이트가 닫히지 않는다", 02 §E 1번). 이 경우도 **내부적으로는
   스키마 정의/소비 전환 두 단계로 순서를 분리**해 자가 검증을 단계별로 받되, 태스크 ID·완료 선언은 하나로 묶는다.
2. **기계적 반복 패턴**: 동일 패턴(예: import 경로 교체)이 여러 파일에 반복될 뿐 파일별 판단 분기가 없는 경우
   (예: 디자인 토큰 소비 전환 — 앱당 11~21개 파일이지만 전부 `theme.ts` → `packages/ui` 토큰 import로 교체하는
   동일 작업). 분할 비용(태스크 조정·컨텍스트 재구축)이 병렬화 이득보다 크다고 판단해 앱 단위 1태스크로 유지한다.
3. **원자적 DB 마이그레이션**: Prisma 스키마 변경 + 그 스키마를 사용하는 최소 엔드포인트 세트는 분리 배포 시
   깨진 중간 상태(마이그레이션만 있고 소비 코드가 없는 상태, 또는 반대)를 만들므로 분리하지 않는다.

**분할 기본값**: 위 3예외에 해당하지 않는 한, 서로 다른 워크스페이스(`apps/*` vs `services/api` vs `packages/*`)에
걸치는 작업은 **워크스페이스 경계에서 분할**한다(예: 02 §E 16번 계측 파이프라인 → 클라이언트 로깅 태스크 + 서버
집계 엔드포인트 태스크 2개). 이는 파일 소유권 배타 병렬(G3)과도 정합한다 — 워크스페이스 경계 분할은 곧 파일
소유권 경계 분할이다. **복수 앱 동시 편집 판정 의무(EVAL-ROUND-22 22B X2-6/D22-8 신설)**: 동일 그룹 내 복수
앱(`apps/reporter`/`apps/control-center`/`apps/subscriber`)의 화면·설정 파일을 동시 편집하는 태스크도 이 분할
기본값의 대상이다 — 미분할 시 위 3예외 중 어느 것을 원용하는지 **해당 행에 1구 명시**한다(DD1이 T-W1-07을 앱
경계로 분할한 판정과 T-W0-05·T-W3-02의 미분할이 모순이 아니려면 그 차이(파일별 판단 분기 유무)가 행에 기록돼야
한다 — 舊 두 행은 분할도 예외 인용도 없는 무기록 상태였다. 두 행에 예외② 인용 부기 완료, **재현**(리포 루트):
`grep -c "분할 예외[①②③]" docs/plan/exec/E2-work-breakdown.md` → **≥ 1**(그 시점 값은 같은 명령의 출력으로
읽고 본 절에 박제하지 않는다 — D7-1 박제 금지 · E4 §G #6 전환 선례 동형. 舊 표기 `5→7`은 이 절이 **자기 파일**의
문자열 수를 세는 자리라 앵커 ⑨ 검산 절 판정 기준의 정의역 밖이어서 어떤 앵커도 갱신을 강제하지 못했고, 라운드25에
예외 원용 부기가 순증하며 실측과 어긋났다[EXEC-EVAL-ROUND-26 J2-3/D26-3] — 값을 없애면 원리적으로 어긋날 수 없다.
舊 파일 인자도 bare 파일명이라 리포 루트에서 exit 2였다[D26-4 동형 처리]).

**파일 소유권 명시 원칙(EVAL-ROUND-3 영역3 감점1·Z-8 신설)**: **계획 시점에 비교 가능한 파일 집합이 존재해야
E3의 웨이브 배타 근거가 검증 가능하다** — 소속 앱조차 특정되지 않은 파일 소유권 서술("~화면(신규 1~2)")은
E3가 동일 웨이브 타 태스크와의 배타를 문서만으로 판정할 수 없게 만든다. 모든 태스크는 최소 1개의 **예상 경로**
(expo-router 규약·기존 모듈 구조에서 합리적으로 추론 가능한 구체 경로)를 파일 소유권 열에 기재한다 — §G 리스크
2행의 "착수 직전 조율자 실측 grep 재확인"은 이 예상 경로를 갱신하는 절차이지, 예상 경로 자체를 생략해도 되는
근거가 아니다. **대량 소비 전환 태스크 재실측 예고(EVAL-ROUND-21 Y2-9 신설)**: 대량 소비 전환 태스크(T-W1-02·
T-W2-05·T-W2-06)의 소비 파일 수는 계획 시점 실측치이며, 선행 웨이브가 신설하는 UI 파일(예: T-W2-18의
`SceneOrderChecklist.tsx`)이 그 소비 전환 태스크 착수 시점에는 새로운 소비자로 편입돼 있을 수 있다 — 착수
직전 실측 grep 결과를 앵커 ⑦ 대조 입력으로 쓰고, 버킷 이탈이 발생하면 §C 셀·E4 §A-6을 동반 갱신한다(완화책
자체는 §G 리스크 2행·E3 §B "재발 방지" 문단이 이미 절차적으로 흡수하므로 이 구는 그 절차가 이 3태스크에도
적용됨을 예고하는 것이지 신규 절차 신설이 아니다).

**공용 패키지 신설 태스크의 소비측 선언 동반 원칙(EVAL-ROUND-25 K2-1/D25-1 신설 — EXEC-DECISIONS #6이 동적 라우트
신설에 세운 "동반 산출물" 원칙의 동형 확장)**: `packages/*`를 **신설**하는 태스크가 있으면, 그 패키지의 소비를
성립시키는 **소비자 `package.json` 워크스페이스 의존성 선언**(`"<pkg>": "workspace:*"`)과 그에 따른 **루트
`pnpm-lock.yaml` 갱신**은 그 **신설 태스크의 동반 산출물**이다 — 소비 전환 태스크가 아니라 신설 태스크가 소유한다.

2. **소비 시점 원칙 충족**: 선언(Wave 3)이 소비(Wave 5·13a·14)보다 **앞선다** — 각 소비 전환 착수 시점에 import가
   이미 해결돼 있다. "선언이 없으면 import가 해결되지 않는다"는 요건은 ⓑ가 더 안전하게 만족한다(ⓐ는 동일 태스크
   안에서 선언과 소비가 같은 시점).
3. **리포 선례 동형**: T-W0-05(Wave 1 [SOLO])가 이미 3앱 `package.json`에 의존성 3종을 **한 태스크로** 추가하고
   분할 예외②를 원용한다 — 워크스페이스 링크 1건을 3앱에 동일 선언하는 본 건은 그와 같은 형태다.
4. **게이트③ 비용 무증가**: T-W1-01은 `packages/ui` 신설로 이미 루트 전체 회귀 대상이라 회귀 횟수가 늘지 않는다.
   ⓐ는 T-W1-02·T-W2-05·T-W2-06 **3건을 새로 루트 전체 회귀 대상으로 승격**시키는데, lockfile 델타는 논리적으로
   1회분(워크스페이스 링크 1건)이라 얻는 것이 없다.
5. **소비 전환 태스크의 성격 보존**: 세 태스크는 **분할 예외②(기계적 반복 패턴 = import 경로 교체)**로 미분할을
   정당화하는데, 의존성 선언·lockfile 갱신이 섞이면 "파일별 판단 분기 없음"이라는 그 근거가 흐려진다.

**ⓑ의 비용(정직 고지)**: T-W1-01 파일 수가 3 → **6**이 돼 버킷이 **S → M**으로 바뀐다 → **E4 §A-6 Wave 3 행 재계산
