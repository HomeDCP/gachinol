# EXEC-ROUND-3-DECISIONS — 라운드 3 횡단 결정 (조율자 선확정)

> [EXEC-EVAL-ROUND-3](EXEC-EVAL-ROUND-3.md)의 이슈 16건(Z-1~Z-16) 중 문서 간 공유 판단을 선확정한다.
> 수정 에이전트는 확정 문안을 **인용**하며 재해석하지 않는다. (2026-08-04)

## DDD1. 사이징 라벨 전건 재판정 — Z-10 (E3 → E4 순서 강제)

**확정.** E3 §C의 43개 코드 태스크 사이징 라벨을 **E2 파일 소유권 열의 파일 수 기준으로 전건 재판정**한다
(S=1~3·M=4~6·L=7~11·XL=12+, Wave 2에 적용했던 것과 동일 절차). 파일 수와 다른 라벨을 유지하는 태스크는
**T-W3-04와 같은 형식의 1줄 정당화**를 해당 셀에 부기한다(무설명 이탈 금지 — 예: T-W1-11b가 1파일이지만
CI 게이트 3종 신설로 L을 유지하려면 그 근거를 셀에 적는다. 정당화가 없으면 파일 수 기준으로 하향).
재판정으로 라벨이 바뀌면 **E4 §A-6 재계산 동반**(라운드 2와 동일하게 **E3 수정 완료 후 E4 착수** — 순서 강제).
방향이 전부 보수적(하향)이므로 상한 200만 판정이 뒤집힐 가능성은 낮으나 재계산으로 확정한다.

## DDD2. T-NC-14 증적 경로 = `reviews/dod-evidence/broadcast-url-procedure/` — Z-14

**확정: E5 §C 표기가 정본이다**(E2 §E 서두 스스로 "증적 경로는 E5 §C를 그대로 인용(재정의 금지)"라 선언).
근거: T-NC-14(방송별 HLS URL 게시 절차 문서 + 첫 방송 전 리허설 1회)는 **1회성 절차 증적**이라 전용 경로가
맞고, `ops-review.md`는 **상시 리뷰 누적 전용**(T-NC-11·12·15)이다. 적용: E2 §E T-NC-14 행·E3 §D 해당 행을
`broadcast-url-procedure/`로 정정, EXEC-PLAN §2 경로 목록에 조율자가 추가.

## DDD3. W1 종료 웨이브 = Wave 12 통일 — Z-9

**확정.** DD1(T-W1-07a → Wave 12)의 귀결로 **W1 종료 웨이브 = Wave 12**다. E3의 4개소(§A 앵커 2 매핑·
§C Wave 16 선행 열·§D T-NC-05·06 하류 영향)를 Wave 12로 정정하고, 정정 후 `grep -n "Wave 11"` 잔존 히트가
정당한 것(T-W1-11b SOLO 배치·§G 배정 기록)뿐임을 완료 보고에 동봉한다. W1 DoD 판정(T-NC-05·06 소비)은
Wave 12 종료 보고에 귀속된다.

## DDD4. W3 실행–승인 분리 — Z-13

**확정 문안**: E5 §C W3 행의 실행 담당 = "**사용자**(스토어 제출·심사 대응 — 본인 인증 행위) +
**법무/운영 지원**(절차 정리·상태 추적)", 판정 승인 = **조율자**. 구 표기 "PM(사용자 승인 동반)"은
E1 §A-1의 "기획(PM)=조율자" 매핑상 실행자=승인자 동일 주체가 되므로 폐기(D5 구현자≠승인자 원칙의 확장).
E2 §E T-NC-10 담당 열도 동일 문안으로 통일.

## DDD5. qa-verifier 단가 축의 근거 명시 — Z-11

**확정.** E4 §A-6의 qa-verifier 단가(XL·L=25만 / M·S=10만)는 **크기 버킷을 대리 지표(proxy)로 쓰는 계획
단계 편성값**이다 — 근거: 게이트②의 재현 범위(읽을 파일·재실행할 테스트 수)는 AC 복잡도와 상관하며 크기와
동행하는 경향. §A-2의 "AC 복잡도" 정의와 모순이 아니라 **실측 전 근사**임을 §A-2·§A-6 양쪽에 1줄 명시하고,
"W0 첫 웨이브 실측으로 교체" 대상에 포함한다. §B-4 "크기≠에포트"와의 관계도 1줄 부기(에포트는 추론 예산,
qa-verifier 단가는 검증 재현 비용 — 서로 다른 축이라 모순 아님).

## DDD6. 초기 opus 보정 범위 확장 — Z-12

**확정.** E4 §B-1 초기 보정 조항을 "W0 Wave 1~2의 '높음' 판정분"에서 "**§B-4 '높음' 4조건(a~d) 각각의
리포 최초 1건**(예: 최초 Prisma 변경=T-W2-08, 최초 api 신규 모듈=T-W1-05, 최초 신규 골격=T-W3-03/04,
최초 다중 워크스페이스 계약=해당 최초 태스크)은 opus 선배정 — 해당 유형 게이트② FAIL 0건이면 같은 유형의
후속 태스크부터 sonnet 하향"으로 확장한다(유형별 표본 1건 확보 — 인프라 성격 2건만으로 전 유형을 대변하던
표본 편향 해소).

## DDD7. 네이티브 동결의 승계 형태 — Z-3

**확정: 태스크가 아니라 상시 제약으로 승계한다**(1회 완결 단위가 아님). ① E2 §0(비범위·원칙)에
"**네이티브 트랙 즉시 동결**(08 §D — 피벗 승인 즉시 발효): 전환 기간 중 네이티브 앱 코드에 신규 기능 커밋
금지, 버그 수정은 웹 전환 완료 전 치명 결함에 한함" 선언 추가. ② E5 §E 진행 보고 5항(게이트 상태)에
