## 1. 총평

갖췄고, 대부분의 트리거가 수치화돼 있다.

무엇보다 **검증 가능한 수치 주장이 전부 재현됐다**. 평가자가 직접 실행한 명령으로 다음이 정확히 일치했다:

3. **stale 전파 누락 2건**: 라운드 8의 65→66 총계 갱신이 E3 §D 앵커4 행·§G 앵커4 문단에 전파되지
   않았고(P-2), 라운드 8의 T-W2-17 신설이 E2 §F-2 라벨 5 롤업 열거에 전파되지 않았다(P-3). 둘 다 같은
   문서의 다른 곳에서는 이미 정정된 항목이라 비대칭이 뚜렷하다.
4. **정본 문언 중 무주공산 1건**: 08 §A W4 산출물 "CLAUDE.md·**docs** 갱신"의 docs 몫이 어느 태스크의

5. **축은 세웠으나 실행 수단이 없는 것 1건**: 에포트 등급을 44+22건 전건 판정하고 위임 프롬프트 머리에
   표기까지 강제하지만, 그 라벨이 서브에이전트의 추론 예산을 **어떻게** 바꾸는지 규정한 문장이 전 문서에
   0건이다(P-8). 모델 축이 sonnet/opus라는 실행 가능한 식별자를 갖는 것과 대조된다.
6. **검출력 구멍 1건**: 게이트③의 "테스트 건수 before→after" 판정이 동일 워크스페이스 다중 태스크가
   같은 웨이브에 있을 때(Wave 9 = `apps/subscriber` 3건, Wave 10 = subscriber 2 + api 2) 델타 귀속
   규칙을 갖지 않는다(P-12).
7. **추적 장치의 사각지대 2건**: PIVOT §6-11 상태 칸의 grep 재현성을 검증하는 앵커가 없고(실제로 #12는

이 12건은 모두 **1~2줄 편집으로 닫히는 유형**이며 구조 변경을 요구하지 않는다. 웨이브 재편·태스크 재분해·
예산 재계산은 전혀 필요 없다(P-1도 셀 1개에 게이트 문구를 추가하는 일이다). 다음 라운드에서 전건이

### 영역 1. 마스터플랜 정합성 — 9.3

**강점(실행 확인)**: 02 §E 28라벨·08 §E 13라벨이 실측 grep과 정확히 일치하고(§5 A-6), §F-1·§F-2 대사표가
전건을 태스크 ID로 사상하며 요약 산식(1:1 13 + 분할 12 + 트리거 3 = 28 / 코드 3 + 비코드 5 + PoC 1 +
롤업 4 = 13)이 성립한다. §0 비범위 선언 5항목(T-AI·커머스 2단계·04 자체 소유·05 수치·08 §C 대시보드)이
전부 정본 문언 인용으로 근거를 남겼고, 특히 D8-3 (b) 택일은 08 §C 원문의 "미구축(수동 집계 — 자동화는
§E 8번 대시보드 구축 시 편입)" 셀을 정확히 읽은 판정이다(§5 A-8 원문 확인). 신규 범위 발명은
발견되지 않았다. 정본 이탈 4건(EXEC-DECISIONS #2·#4·#6·#7)이 모두 배경·원문 인용·채택안·영향 문서
4항목 형식으로 기록됐고, 특히 #7은 "정본 준수" 방향의 태스크 신설이라 이탈이 아니라 복구다.

**감점 사유**

1. **E2 §F-2 라벨 5 롤업 열거가 stale**(P-3). 해당 행은 `| 5 | W2 롤업 — **T-W2-01~16b** + T-NC-07(개별
   태스크 인용) | 롤업 |`인데, 라운드 8 D8-1이 T-W2-17을 신설하며 W2 코드 태스크를 17→18건으로 올렸다.
   같은 문서의 §C "W2 코드 태스크: **18건**" 선언, §F-1 라벨 9("T-W1-11a + T-W1-11b + T-W2-07 +
   **T-W2-17**"), §E T-NC-07 게이트 열("T-W2-01~**17**")은 전부 갱신됐으므로 §F-2만 남았다. 더구나
   T-NC-07 행의 각주는 "舊 `T-W2-01~16b`는 T-W2-17 신설 미반영 stale 표기였다"라고 자기 진단까지 해 둔
   상태다 — 같은 문서 안에서 동일 문자열이 한쪽은 정정되고 한쪽은 남았다.
2. **08 §A W4 산출물 "CLAUDE.md·docs 갱신"의 docs 몫이 무주공산**(P-9). E2 §C T-W4-01의 파일 소유권 열은
   `CLAUDE.md`(§9+§11)뿐이고, T-W4-02는 `ci.yml`, T-W4-03은 신규 실측 리포트 문서다. E2 전체에서 파일
   소유권 열에 `docs/` 경로를 가진 태스크는 **0건**(§5 A-11). 그런데 E5 §C W4 행의 판정 명령①은
   `grep -rn "expo-env\.d\.ts\|EAS Build" CLAUDE.md docs/ --exclude-dir=exec`로 `docs/`를 스캔 대상에
   포함한다 — 현재 `docs/` 히트가 0건이라 판정 자체는 통과하지만(§5 A-10), "docs 갱신"이라는 정본
   산출물의 소유자가 없는 상태다. 08 §E-7("W4: 문서·CI 정리, 네이티브 트랙 종료 선언")도 같은 공백을
   가리킨다.
3. **§F-3의 08 §A 시간축 매핑표 대사가 12행 중 9행만 명시 처리**(P-10). §F-3 3번째 행은 4활동(패널 R2·
   R3, 03 §B-4 1·2차)을 T-NC-16~19로 태스크화하고 "나머지 행(패널 R1=T-NC-04, 앵커 2/3/4, M1~M12=05
   소유)은 기존대로 각자의 매핑을 유지 — **이 4행만 누락돼 있었다**"라고 닫는다. 그러나 시간축 매핑표의
   실제 행은 12개이며(MVP 착수 / 패널 R1 / 패널 R2 / 런칭 / 대외 런칭 / 패널 R3 / 첫 촬영 재개(전) /
   03 §B-4 1차 / 03 §B-4 2차 / W2 가동 이후 / 첫 실 방송 / M1~M12, §5 A-9), **MVP 착수(앵커 1)·첫 촬영
   재개(전)·W2 가동 이후 3행이 어느 분류에도 열거되지 않았다**. 셋 다 태스크가 필요 없는 정의·앵커 행이라
   실질 누락은 아니지만, §F가 "전건 매핑 — 누락 0건"을 선언하는 근거 열거로서는 불완전하다.

### 영역 2. 에이전트 편성 적정성 — 9.4

**강점**: E1 §A가 8역할 전건에 (소유·금지·기동 방식·산출물 형식·완료 보고 고정 문구) 5열을 부여했고,
평가자 실행으로 8역할이 §A 표에 실재함을 확인했다(§5 A-12). "상근 = 상주 프로세스가 아니라 태스크 단위

수집 주체·시점까지 지정돼 있다는 점이다. SOLO 비용을 토큰 축(PMO 160만)·동시성 축(32 슬롯-웨이브)·
게이트② 큐 깊이 축(20 태스크-대기)으로 분리 정량화하고 "억지 단일화 금지"를 명시한 것도 정확하다.
재개 프로토콜은 5단계 + 실증 4건 + §C-4 검증 원칙(`ls`/`Read` 실측 없는 재작성 금지)까지 갖췄다.

**감점 사유**

1. **§F가 앵커 ⑨ 형식 규칙을 위반**(P-5의 E4 몫). §F "라운드4 착수 시점 재실행" 블록은
   `grep -c "| \*\*QA 리드\*\* |$" → 1`, `grep -c "| \*\*PMO\*\* |$" → 1`, `"카운트 대상은 서브에이전트
   전부" → 3건 히트`, `"파일이 일부/전부" → E1 1건·E4 1건`을 원시 수치로 담는다. 평가자 재실행 결과
   값은 전부 정확하지만(§5 A-14), E5 §D 앵커 ⑨(D9-1)가 E4 §F를 "인용 요약문 절"로 명시 열거하고 원시
   수치 주장을 값과 무관한 형식 위반으로 규정했으므로 위반 상태다. 더구나 §F 자신은 "이후 라운드는 본
   절의 출력 블록을 **수정하지 않는다**"는 자기 규칙(라운드 4)을 선언하고 있어, **E4 §F의 자기 규칙과
   E5 §D 앵커 ⑨의 형식 규칙이 정면으로 상충**한다 — 어느 쪽을 따를지가 문서에 없다. 이는 단순 표기가
   아니라 규칙 충돌이므로 첫 웨이브 PMO가 판단 불가 상태에 빠진다.

**9.5 도달 수정 지시**

- E4 §F의 grep 출력 블록을 E1 §E와 동일한 형식(기능 위치 열거 + 자기 매칭 제외 명시)으로 전환하고,
  §F 말미의 "본 절의 출력 블록을 수정하지 않는다" 자기 규칙을 **"본 절은 원시 수치를 담지 않으므로
  stale 대상이 아니며, 지속 정합은 E5 §D 앵커 ⑨가 담당한다"**로 교체하라 — 이로써 E4 §F 자기 규칙과
  앵커 ⑨의 충돌이 소멸한다. §F-1(표만 있고 수치 주장 없음)은 무변경으로 둔다.

### 영역 6. 모델·에포트 배분 — 9.3

**강점**: 배분의 근거가 두 축 모두에서 명시적이다. §B-1은 작업 성격 5행에 모델과 근거를 부여하고
"구현 코드에 대한 sonnet 적합성"을 **미검증 상태로 인정**한 뒤 검증 시점(Wave 2 종료 보고)·주체(조율자)·
기준(게이트② FAIL율 ≥25%, 분모 = 해당 웨이브의 sonnet 구현 태스크 수 = Wave 2 실제 3건)까지 확정했다 —
불확실성을 방치가 아니라 관리 대상으로 전환한 모범적 처리다. §B-4는 판정 규칙(기본 낮음 + 4조건 (a)~(d)
중 하나면 높음, 규칙 밖 상향은 근거 1줄 필수)을 세우고 **44건 전건**을 분류했으며, 평가자 대조 결과
분류표의 태스크 집합이 E2 코드 44건과 차집합 0, 높음 10·opus 5로 선언과 일치했다(§5 A-18). §B-4-1이
T-TRIG 3 · T-NC 19 · PMO/QA 리드/법무 역할까지 덮어 "모델 표(8역할 축)와 에포트 표(코드 44건 축)의
커버리지 비대칭"을 해소했다. DDD6 초기 opus 보정(4조건 각각의 리포 최초 1건 = 5건)은 사후 트리거만
있던 구간의 표본 편향을 정면으로 다뤘고, §B-3 과대 배분 표본 정의(웨이브당 무작위 1건, 직전 3건
중앙값의 2배 초과, 3건 미만이면 유보)와 D8-7의 "유보 구간 노출액 상한 175만"까지 계산돼 있다.
"크기≠에포트" 원칙이 4회 실증 사례로 검증된 것도 좋다.

**감점 사유**

1. **에포트 등급을 실행에 반영하는 수단이 전 문서에 없다**(P-8). E4 §B-4/§B-4-1이 66건 전건 등급을
   판정하고 E1 §B 6번 요소가 위임 프롬프트 머리에 `에포트: <낮음|높음|최고> (근거: …)` 1줄을 강제하지만,
   그 라벨이 실제로 서브에이전트의 추론 예산을 **어떻게** 바꾸는지 규정한 문장은 0건이다. 평가자 검색
   결과 "추론 예산/thinking budget"은 §B-4 배경 단락 1회뿐이고(§5 A-19), 도구 파라미터·프롬프트 지시문·
   대체 수단 어느 것도 지정되지 않았다. 모델 축은 `sonnet`/`opus`라는 **실행 가능한 식별자**를 갖는
   반면 에포트 축은 라벨만 있어, 위임자가 같은 sonnet 태스크의 "낮음"과 "높음"을 실제로 다르게 실행할
   방법을 알 수 없다. 그 결과 §B-2 상향/하향 트리거·§B-4-1 상향/하향 수치 트리거가 발동해도 **바꿀 수
   있는 대상이 없다** — 배분 체계 전체가 감사 추적용 라벨로만 기능하게 된다. 루브릭 영역 6이 이름에
   "에포트"를 명시하는 이상, 이 축의 실행 수단 부재는 "실행계획 문서로서 더 고칠 것이 없는 상태"의
   반례다.

**9.5 도달 수정 지시**

- E4 §B-4 서두(또는 §B-4-1 말미)에 **"에포트 등급의 실행 적용" 1소절**을 신설하고, 3등급 각각이 발주
  시 무엇으로 구현되는지를 1행씩 지정하라 — 예: 라벨 자체(감사 추적) + 위임 프롬프트의 사고 지시 강도
  (낮음 = 지시 없음 / 높음 = "설계 대안을 2개 이상 비교한 뒤 선택 근거를 완료 보고에 기재" / 최고 =
  독립 평가 전용, 코드 태스크 비부여) + 조율자가 쓰는 기동 수단(가용한 경우 도구 파라미터, 불가하면
  프롬프트 지시로 대체한다는 선언). 수단이 환경상 제한된다면 **그 제한을 명시**하는 것만으로도 충분하다
  (루브릭상 방치가 감점이고 명시된 제약은 아니다).
- E1 §B 6번 요소에 위 소절 참조 1구를 추가해, 위임자가 라벨을 적을 때 무엇을 함께 부착해야 하는지가
  프롬프트 표준에서 닫히게 하라.

### 영역 7. 품질 게이트 — 9.3

**강점**: §A 4단 게이트가 (주체·입력·실행 내용·산출물/증적·통과 기준·실패 시 조치) 6열로 정의되고
순서 강제·건너뛴 완료 무효가 명문화됐다. 글로벌 헌법 "Trust but Verify"의 핵심 요구인 "테스트 미실행
완료 선언 금지"가 **로그 동봉 의무 = 게이트① 통과 조건**이라는 검사 가능한 형태로 번역됐고, 위반 시
조치 4단계(원복 → EXEC-DECISIONS 기록 → 재위임 시 문구 굵게 재명시 → 웨이브 내 2회 반복 시 위임 표준
재점검)까지 있다. 게이트②의 "자가검증 로그 재신뢰 금지, AC 최소 1개 독자 재현"과 재시도 한도(재기동
1회 → 이월 → 2웨이브 연속 시 재설계)가 무한 재기동을 막는다. §B 회귀 명령표는 **리포 실체와 정확히
일치**했다 — `services/api`에 `lint` 스크립트 실재, 3앱에는 부재(루트 turbo가 커버), E2E 4스위트 실재,
`ci.yml`의 `pnpm lint→typecheck→test`·`ruff check .`·`pytest` 잡 구성 일치(§5 A-20). 게이트③ 통과
기준에 "산출물 자체가 파일·API 제거인 경우 그 대상에 종속된 테스트 감소는 회귀가 아니다(무설명 감소는
여전히 회귀)"라는 예외를 둔 것은 T-W1-02·T-W2-05·06의 `theme.ts` 제거를 실제로 통과 가능하게 만드는
정확한 처방이다. §C W단계 DoD 표가 실측 명령·증적 형식·저장 위치·실행 담당·판정 승인을 분리하고,
비-DoD 11건까지 별도 표로 덮는다. 게이트④의 조율자 자기 승인 금지(QA 리드 대행)도 G6의 재귀 적용이다.

**감점 사유**

1. **게이트③ before→after 델타의 귀속 규칙이 없다**(P-12). §A 게이트③ 통과 기준은 "테스트 건수
   **before→after** 비교 … 기존 테스트 건수 감소·레드 없이 신규 건수만 증가(또는 불변)"인데, **동일
   워크스페이스의 복수 태스크가 같은 웨이브에 병렬 배치되는 경우의 판정 규칙이 없다**. 실제로 E3 §C
   Wave 9는 T-W1-09·T-W1-10·T-W2-09가 **전부 `apps/subscriber`**이고, Wave 10은 T-W1-11a·T-W2-11이
   subscriber, T-W2-12·T-W2-15가 `services/api`다(§5 A-21). 파일 소유권은 배타적이라 편집 충돌은 없지만,
   세 태스크가 각자 `pnpm --filter @gachinol/subscriber test`를 실행하면 서로의 신규 테스트가 상대의
   before/after에 섞인다 — ① 어느 태스크가 회귀를 냈는지 귀속이 불가능하고, ② 한 태스크의 감소가 다른
   태스크의 증가에 가려져 **"감소 없음"으로 오판정될 수 있다**. 이는 게이트③의 검출력 자체에 관한
   구멍이며, 공용 자산 루트 회귀(SOLO라 안전)가 아니라 **개별 워크스페이스 회귀** 경로에서 발생한다.
2. **E1 §A QA 리드 행의 게이트③ 4종 표기**(P-4, 영역 2와 공동)는 게이트③ 주체·범위 정의의 단일 원천
   (E5 §A 게이트③)이 하류 문서에서 다르게 복제된 상태이므로, 품질 게이트의 실행 근거 문서 간 정합에도
   감점 사유다.
3. **W4 DoD의 docs 몫**(P-9, 영역 1·3과 공동)은 판정 명령이 스캔하는 범위와 태스크 소유 범위가 어긋난
   경우다 — 게이트가 판정하는 대상 중 일부에 책임자가 없다.

**9.5 도달 수정 지시**

- E5 §A 게이트③ 통과 기준(또는 §B "개별 워크스페이스" 행 비고)에 **동일 워크스페이스 다중 태스크
  웨이브의 델타 귀속 규칙** 1항을 신설하라 — 택일 후 근거를 명기한다: **(a)** 같은 웨이브의 동일
  워크스페이스 태스크는 게이트③을 **완료 순서대로 직렬 실행**하고 각자의 before를 "직전 태스크의 after"로
  잡는다(조율자가 순서를 지정), 또는 **(b)** 각 태스크가 **자기 소유 파일에 대응하는 테스트 ID 집합**만
  before→after 대조 대상으로 삼고 워크스페이스 전체 건수는 참고치로만 기록한다. 어느 쪽이든 "감소한
  테스트 ID를 열거하고 사유를 1건씩 명시"라는 기존 원칙과 접속되게 하라.
- 영역 2의 P-4 수정 지시와 영역 1의 P-9 수정 지시를 이행하라.

### 영역 8. 추적·정합 유지 — 9.1

**강점**: 대장을 **새로 만들지 않고** PIVOT-PLAN §6에 6-11 소절로 연장한 결정(단일 원천 유지)이
정확하고, 평가자 재현 결과 §6 본문 총계 **89 = 마스터플랜 67 + 6-11 22행**이 성립한다(앵커 ⑫, §5 A-22).
상태 SSOT 단일화(D7 — 문서 측은 `→ 6-11 #n 참조`만)가 E2·E3·E4·E5 전건에 적용됐고, 등재 책임 규칙이
"완료 보고 = 게이트①의 완료 선언에 신규 위임 목록 포함(없으면 '없음' 명시, 무언급은 절차 위반)"으로
실행 단계에 이식됐다. PMO가 웨이브마다 1회 기동해 **발굴이 아니라 검증**만 한다는 권한 분리와, PMO가
먼저 "E1~E5에 §신규 위임 목록 절이 존재하는지"부터 확인하는 분모 밖 재발 방지 절차가 좋다.
**앵커 ①~⑫**는 이 문서군의 백미다 — 수치 앵커 5 + 문자열 앵커 3 + 자체 점검 재현 앵커 4가 각각
재현 명령과 관계 불변식을 갖고, D7-1의 **박제 금지**(기댓값·실행 출력을 본문에 남기지 않고 관계식만
둔다)는 "stale이 stale을 낳는 순환"을 발생 지점에서 끊는 정확한 구조 처방이다. 평가자가 실행 가능한
앵커를 전종 재현한 결과 ①(66) ②(8=8=8) ③(22행·전건 ≤4·합 44) ④(19 4자) ⑤(상한 200만 3자·총예산
2,181~2,341만 2자) ⑥(W0 이원·W1=12·W2=15b·W3=17b·W4=19) ⑦(사이징 전건 일치) ⑧(경로 diff 빈 출력)
⑩(32−10=22) ⑪(4패턴 일치) ⑫(67+22=89)가 **전부 통과**했다.

**감점 사유**

1. **앵커 ⑨가 지정한 형식 규칙을 대상 절 4개 중 2개가 위반 중**(P-5). E1 §신규 위임 목록과 E4 §F가
   원시 `grep -c` 수치 주장을 담고 있다(값은 정확하나 규칙이 값과 무관한 형식 위반으로 규정). 추적
   장치의 관점에서 이것이 문제인 이유는, **첫 웨이브 PMO 기동이 곧바로 위반 2건을 보고하게 되고**
   그것이 진짜 정합성 문제가 아니라 규칙-문서 간 미전파이므로, 앵커 ⑨가 신호 대신 소음을 내는 상태로
   시작한다는 데 있다. D9-1이 정확히 이 형해화("상시 위반 5건 무력화")를 해소하려고 만든 규칙인데
   같은 유형이 다른 자리에 남았다.
2. **§6-11 상태 칸의 grep 재현성을 검증하는 앵커가 없고, 실제로 #12는 재현되지 않는다**(P-6). 앵커
