# 02. 웹 아키텍처 전환 설계 (네이티브 3앱 → 웹앱 3종 + 쉘 앱)

> 웹 피벗의 기술 핵심 문서. 평가 영역 1(실행 가능성)·2(서비스 성립성)의 주 근거.
> 원칙: **이미 검증된 로직(3앱 UI·도메인 로직·백엔드 전체)을 최대 재사용**하고, 웹이라는 배포 형태만 바꾼다.

**위임 상태 서술 갱신 규칙 (04 §0 규칙의 02 승계, EVAL-ROUND-11 영역1 감점1 수정지시·정합성 이슈 K-3 재발
방지)**: 02가 서술하는 타 문서 위임 상태("신설 완료"/"신설 예정"/"미수신" 등, 리포 실측치 인용을 포함한 문서
전 구간)는 **매 라운드 해당 문서 제목 grep(또는 리포 실측 재실행)으로 재확인한 뒤에만** 갱신한다 — 추측이나
이전 라운드 기억으로 상태를 반복 단정하지 않는다. D-T9의 "07 §3-15 라운드 2 신설 예정"이 실제로는 신설
완료 후에도 갱신되지 않은 채 여러 라운드 잔존했던 것, §B의 jest-expo 테스트 건수가 stale 원천(CLAUDE.md §11)을
grep 재확인 없이 인용해 어긋난 것이 모두 이 규칙 부재의 동일 유형 오류였다. 이후 **문서 전체**가 이 규칙을
따른다.

## A. 전환 전략 결정

**표 갱신 규칙(EVAL-ROUND-16 영역1 감점2·정합성 이슈 P-5 해소, 07 §6 "상시" 블록의 OSS 라이선스 PR 체크리스트와
동일 형식)**: 이 표의 분모는 3앱 `package.json` `dependencies` 전건이다. 신규 의존성 추가 시 이 표에 행을
추가하는 것을 PR 체크리스트 항목으로 둔다.

**분모 경계 각주(EVAL-ROUND-17 영역1 감점3·정합성 이슈 Q-6 해소. **T-W0-05에서 재현 명령 형식으로 전환 —
EXEC-DECISIONS #10**)**: 이 표의 분모는 **3앱 `dependencies` 실측 union**이며, **그 시점 값은 재현으로 읽는다**
— 값·열거를 본문에 박지 않는다(D7-1 박제 금지 · EXEC-DECISIONS #9).

```bash
# 분모(그 시점 union) — 리포 루트에서 실행
python3 -c "
import json
u=set()
for a in ('reporter','control-center','subscriber'):
    u|=set(json.load(open(f'apps/{a}/package.json'))['dependencies'])
print(len(u)); print(sorted(u))
"
```

**전환 근거**: 舊 각주는 union 수(**19개**)와 전체 모듈명 열거, 그리고 "위 표는 이 중 18건을 행으로 다룬다"는
계수를 본문에 고정하고 있었다. T-W0-05(Expo Web 활성화)가 3앱에 `react-native-web`·`react-dom`·
`@expo/metro-runtime`을 추가하는 순간 union이 19→22로 바뀌어 그 세 수치가 동시에 stale됐다 — **값을 다시 고쳐
적으면 다음 의존성 추가 태스크(E3 §B 준-공용 자산 2가 열거하는 lockfile 갱신 태스크군)에 또 깨지므로 형식을
바꿔 종결한다.** 이 각주가 실제로 보장해야 하는 것은 "몇 개냐"가 아니라 **"분모가 무엇이고 무엇이 그 밖인가"**라는
경계 규칙이다.

**경계 규칙(값이 아니라 규칙이므로 유지)**: **프레임워크 3종(`expo`·`react`·`react-native`)**과
**`@gachinol/shared`**는 이 표의 분모 밖으로 둔다 — 프레임워크 3종은 D-T1이 이미 "3앱 전체가 커스텀 네이티브
모듈 0으로 웹 타깃 동작"을 판정한 축(이 표가 재확인할 대상이 아니라 이 표의 전제)이고, `@gachinol/shared`는
§B `packages/shared` 행(재사용 100%, 무변경)이 소유하는 축이다 — 이 표는 "3앱이 웹에서 그대로 동작하는가"를
개별 모듈 단위로 판정하는 표이므로, 이미 다른 절이 판정을 끝낸 두 축을 중복 판정하지 않는다.
`expo-file-system`은 "presigned PUT 업로드" 행 본문에 모듈명이 명시돼 별도 행 없이 커버된다(행 1:1 대응이
아닌 유일 예외 — 표를 읽을 때 이 행을 누락으로 오판하지 않도록 남긴다).

### D-T3. 인증 — 웹 보안 모델로 교체 (api 소폭 수정, 기존 계약의 유일한 변경 — 신규 엔드포인트 추가는 §B 참조)

**§B가 열거한 신규 api 표면 8계열(주민 임시 업로드 링크 API·멀티파트 presign·공개 렌디션 복사·`go.` OG SSR 라우트·
콘텐츠 소비+업로드 퍼널 계측 집계·라이브커머스 클릭 계측·미성년자 승인 전이 가드·**웹푸시 구독/발송 + 쉘 푸시 토큰 수신**,
EVAL-ROUND-9 영역1 감점3·정합성 이슈 H-3 해소)은 이와 별도다** — 아래는 기존
refresh 토큰 전달 방식(바디 vs 쿠키)의 변경만 다룬다(EVAL-ROUND-5 영역1 감점1·정합성 이슈 C-9 해소).

현행(앱): access 15m 메모리 + refresh 14d secure-store, 바디로 refresh 전달. 웹에서는 XSS에 노출되므로:

- **웹**: access = 메모리(JS) / refresh = **HttpOnly + Secure + SameSite=Lax 쿠키**(JS 접근 불가).
  api에 쿠키 기반 refresh 경로 추가 — **기존 바디 방식과 병행**(하위호환, 회전·재사용 탐지 로직 재사용).
  **경로는 분리 3종 `POST /v1/auth/web/{login,refresh,logout}`이다**(T-W0-01 구현 확정, **EXEC-DECISIONS #14**로
  정정 — 舊 문안 "`POST /v1/auth/refresh` 쿠키 수용"은 기존 라우트 확장안이었으나, 그러면 바디 부재 시 동작이
  달라져 네이티브 계약 표면이 변하고 CSRF 가드를 라우트 단위로 좁게 부착할 수 없다. 분리안이 "기존 방식 병행"
  요건을 구조적으로 더 강하게 만족한다 — 게이트② 독립 검증 판정).
  재현: `grep -cE "@Post\('web/(login|refresh|logout)'\)" services/api/src/auth/auth.controller.ts` → **3**
  (`@Controller('auth')` 하위이므로 소스에 `auth/web/` 문자열은 등장하지 않는다 — 경로 문자열로 grep하면
  재현되지 않으니 데코레이터로 읽는다).
- **CSRF**: SameSite=Lax + 상태 변경 요청의 커스텀 헤더(`X-Requested-With`) 요구 + Origin 검증. refresh만 쿠키라 공격면 최소.
- **CORS**: api에 웹 오리진 화이트리스트(env `WEB_ORIGINS`) — credentials 허용은 화이트리스트 오리진 한정.
- WS(socket.io)는 현행 유지: 채팅=익명 핸드셰이크, 프롬프터·관제=JWT(메모리 access를 함수형 auth로 — 관제 앱에 이미 구현된 `getFreshAccessToken` 패턴 재사용).

### D-T4. 업로드 — presigned 유지 + 멀티파트 승격

- 원본 실측 ≈ 90MB/분(infrastructure.md §1) → 10분 촬영 ≈ 0.9GB. 모바일 웹 단일 PUT은 중단 시 전체 유실.
- **1단계(전환 직후)**: 현행 단일 presigned PUT 유지(MVP 촬영분 2~4건/일 수용) + 업로드 중 이탈 경고(`beforeunload`) + 실패 시 전체 재시도. 이 구간은 위 웹 호환성 실사표대로 **웹용 XHR 업로더 어댑터 신규 작성**이 선행돼야 성립한다(§B 수정 대상).
- **승격 조건(이 문장이 유일 원천 — 01은 인용만 한다, ROUND-1-DECISIONS X6)**: **"업로드 실패율 주간 5% 초과 또는 평균 원본 크기 300MB 초과 시 멀티파트로 승격"**. 충족 즉시 **S3 멀티파트 업로드**(R2 지원)로 전환 — part 단위 재시도·중단 재개. api에 `create/complete-multipart` presign 엔드포인트 추가. 다른 수치(15%/85% 등)는 이 문장 기준으로 통일하며, 타 문서에 남아 있으면 오기다.
- 웹 한계 고지: 백그라운드 업로드 불가(탭 유지 필요) → 기자 UX에 "화면 유지" 안내 + 진행률 상시 표시(03 문서 연계).

### D-T5. 웹 호스팅·도메인

- 산출물 = 정적 파일(HTML/JS/CSS) → **제온 서버 nginx 컨테이너**가 3앱 서빙 + **Cloudflare 프록시**(TLS·캐시·DDoS). `docker-compose.xeon.yml` 오버레이에 `web` 서비스 1개 추가.
- **사실 정정(ROUND-1-DECISIONS X1)**: 정적 페이지 셸(HTML/JS/CSS)은 Cloudflare 캐시에 얹혀 제온이 죽어도 생존하지만, **VOD 피드 목록과 재생 서명 URL은 api가 발급**한다(`GET /v1/feed`, `GET /v1/feed/:id/playback` → `s3.presignGet`). 따라서 **제온(api) 다운 시 신규 VOD 시청은 중단된다** — 생존하는 것은 캐시된 정적 웹 + 진행 중인 라이브 시청(CF Stream) + 이미 발급된 서명 URL의 잔여 유효시간뿐이다. "시청 경로 전부 생존"이라는 舊 주장은 철회한다. 보강안은 아래 D-T8(W2).
- 서브도메인: `watch.<도메인>`(구독자) · `go.<도메인>/c/<id>`(카톡용 단축 공유 링크) · `reporter.<도메인>` · `center.<도메인>` · `api.<도메인>`.
- 롤백: 정적 배포 = 이전 빌드 디렉토리 스왑, 1분 내 복원. **단, 이는 오리진 스왑일 뿐이다** — 이미 서비스워커가 자산을 캐시한 PWA·TWA·iOS 쉘 설치자에게는 아래 갱신 정책 없이는 도달하지 않는다.

**서비스워커 갱신·캐시 무효화 정책 (EVAL-ROUND-7 영역1 감점2·정합성 이슈 F-14, ROUND-7-DECISIONS S3)**

PIVOT-PLAN §1이 전환 이유로 드는 "웹 배포 즉시 반영(심사 없음)"이 PWA·TWA·iOS 쉘 설치자에게 실제로 성립하려면 오리진 정적 파일 교체(위 롤백)만으로는 부족하다 — 서비스워커가 이미 캐시한 구버전 자산을 계속 서빙하기 때문이다. 아래 5요소가 이 주장의 **기술적 성립 조건**이다:

1. **정적 자산 캐시 버스팅**: JS/CSS 등 빌드 산출물은 콘텐츠 해시를 파일명에 포함(`app.[hash].js`) — 파일 내용이 바뀌면 URL도 바뀌므로 캐시된 구 URL과 충돌하지 않는다.
2. **SW 활성화 — 사용자 확인 후**: 신규 서비스워커가 `waiting` 상태로 감지되면 이미 열려 있는 탭에 "새 버전이 있습니다 — 새로고침" 알림을 노출하고, **사용자가 누른 뒤에** `skipWaiting()`을 트리거해 활성화한다. 새 SW의 `activate`에서 `clients.claim()` + 구버전 캐시 청소를 수행하고, `controllerchange`를 받은 시점에 재로드한다. 작업 중 이탈을 유발하는 자동 강제 새로고침은 금지 — 재로드는 **사용자 트리거로만**.

   > **사실 정정 (T-W1-04 구현 중 반증됨, 2026-08-16 — 대장 #140)**: 이 항의 이전 버전은
   > *"신규 서비스워커 감지 시 `self.skipWaiting()` + `clients.claim()`으로 **대기 없이 즉시 활성화**하고 …
   > 자동 강제 새로고침은 금지"*라고 적어 **한 문장 안에서 모순**이었다. `install` 시점에 무조건
   > `skipWaiting()`을 부르면 새 SW가 즉시 활성화되고 `clients.claim()`이 **구 번들을 실행 중인 탭까지
   > 제어**한다 — 그 탭은 **구 번들 + 신 SW**라는 버전 스큐 상태가 되고, 신 SW의 `activate`가 구버전 캐시를
   > 지우면 그 탭이 참조하던 해시 자산이 캐시에서 사라진다(오프라인·롤백 상황에서 화면이 조용히 깨진다).
   > **"즉시 활성화"와 "사용자 트리거 재로드"는 함께 성립할 수 없다** — 재로드를 사용자에게 맡기는 이상
   > 활성화도 그 시점까지 미뤄야 한다. 이 앱은 **영상 시청 중 이탈이 치명적**이라 사용자 트리거 쪽이
   > 지켜야 할 제약이다. 구현(T-W1-04)은 `skipWaiting`을 사용자 확인 뒤로 옮겼고 `clients.claim()`은
   > 본 항대로 `activate`에 유지했다. `install` 시점 자동 적용을 되살리는 뮤테이션이 테스트에 잡히도록 고정돼 있다.
3. **HTML 엔트리 no-cache**: `index.html`(및 expo-router 정적 출력의 엔트리 문서)은 `Cache-Control: no-cache`로 서빙해 항상 서버에 재검증한다 — 해시 파일명을 참조하는 진입점 자체가 캐시되면 1·2가 무력화된다.
4. **배포 파이프라인 CF 캐시 퍼지**: CI 배포 잡의 마지막 단계로 Cloudflare 캐시 퍼지(**엔트리 HTML · 매니페스트 · `/sw.js`** 최소 대상)를 추가한다 — 엣지 캐시가 3의 no-cache 헤더보다 오래 남는 경우를 차단한다.

   > **대상 보강 (T-W1-04, 2026-08-16 — 대장 #140)**: 이전 버전은 "엔트리 HTML·매니페스트"만 적었으나
   > **`/sw.js`가 빠지면 4번이 서비스워커 자신을 갱신하지 못한다**. `/sw.js`는 SW가 자기 스코프 위쪽을
   > 제어할 수 없다는 제약 때문에 **루트에 고정 이름**으로 있어야 해서 1번(해시 캐시버스팅)의 보호를 받지
   > 못하는 유일한 자산이다 — 즉 4번이 유일한 방어선이다. 오리진 쪽 대응(`location = /sw.js`에 `no-cache`)은
   > T-W1-04가 `infra/docker/nginx.conf`의 구독자 vhost 2곳에 넣었고, **reporter·center vhost는
   > T-W3-02(Wave 17a)가 자기 SW와 함께 동반 소유**한다.
5. **"즉시 반영" 주장의 근거 = 이 정책**: PIVOT-PLAN §1·01 §A-2가 주장하는 "웹 배포 즉시 반영"은 위 1~4가 실제로 구현·검증된 상태에서만 성립한다. 미구현 상태에서는 이 주장을 근거 없는 낙관으로 취급한다.

**롤백 시 SW 캐시 무효화**: 위 D-T5 롤백은 오리진 자산만 되돌린다 — 이미 신버전 SW가 활성화된 클라이언트는 2의 즉시 활성화 메커니즘이 그대로 작동해 **롤백 빌드도 새 버전으로 인식하고 갱신**되므로(1~4가 롤백 방향에도 대칭 적용) 별도 절차가 추가로 필요하지는 않다. 단, 롤백 배포 시에도 4(CF 캐시 퍼지)는 반드시 실행해야 한다 — 생략하면 오리진은 되돌아갔는데 엣지 캐시는 구버전(=롤백 직전 버전)을 계속 서빙하는 불일치가 발생해 "1분 내 복원"이 성립하지 않는다.

PWA·TWA·iOS 쉘 웹뷰는 모두 동일한 브라우저 엔진 기반 서비스워커 API를 쓰므로 위 정책은 세 경로 모두에 동일 적용된다(쉘 고유의 별도 캐시 계층 없음 — D-T2 "비즈니스 로직 0" 원칙과 정합).

**담당**: FE 리드. **기한**: W1(구독자 웹 배포 시점부터 필요, §E 4-1번) — TWA 패키징(§E 10번) 착수 전 필수 완료.

사전 렌더링한다 — `[id]` 같은 파라미터화 경로는 실제 요청 URL(예: `/watch/abc123`)에 대응하는 정적 파일이 애초에
존재하지 않는다. nginx가 이 요청을 파일 경로로 그대로 해석하면 404를 반환하고, 카톡 링크 클릭이 그 자리에서
끝난다 — §C가 측정하려는 TTFF 경로 자체가 성립하지 않는다.

**규칙 확정**:

1. **rewrite/SPA 폴백**: nginx `web` 서비스에 `try_files $uri $uri.html /index.html;` 류의 SPA 폴백 규칙을
   적용한다 — 요청 URI가 실제 정적 자산(해시 파일명 JS/CSS·이미지 등)과 매칭되지 않으면 404 대신 엔트리 문서
   (`index.html`)를 반환하고, expo-router의 클라이언트 사이드 라우터가 브라우저 URL(`/watch/:id` 등)을 파싱해
   올바른 화면을 렌더링한다. 이 규칙은 위 실측 목록의 `/watch/:id`·`/live/:id`·`/contents/:id`·
   `/recommendations/:id` 4개 동적 라우트 패턴을 전부 포괄해야 하며, 앱별 서브도메인(`watch.`·`reporter.`·
   `center.`) 각각에 동일 규칙을 적용한다.
2. **캐시 헤더 정합(위 3항과 일치)**: 폴백으로 반환되는 `index.html`은 위 3항(HTML 엔트리 no-cache)과 동일하게
   `Cache-Control: no-cache`로 서빙한다 — 정적 자산(해시 파일명)은 기존 1항의 장기 캐시를 그대로 유지한다. 즉
   이 규칙은 새 캐시 정책이 아니라 SW 갱신 정책이 정한 캐시 경계(해시 자산=장기 캐시 / 엔트리 문서=no-cache)를
   nginx 레벨에도 동일 적용하는 것이다.
3. **Cloudflare 캐시 규칙과의 경계**: D-T6의 `go.` Cache Everything(**200 OG HTML + 즉시 클라이언트 리다이렉트** 응답 캐시 — **舊 표기 "302 리다이렉트 응답" 정정**, 2026-08-08 Wave 4 T-W1-05 게이트② 판정 수신·조율자 반영, 근거는 EXEC-DECISIONS #21 ②: **302에는 본문이 없어 OG를 실을 수 없어** 302를 고수하면 크롤러 UA에만 200을 주는 UA 분기 2변형이 강제되는데, CF Free/Pro는 `Vary: Accept-Encoding` 외 Vary를 캐시 키에 반영하지 않아 Cache Everything이 켜지는 순간 **한 변형이 모두에게 서빙**된다 — 302가 카카오 스크레이퍼에 서빙되면 D-T6의 목적인 미리보기 자체가 붕괴한다. 200 HTML은 사람에게 서빙돼도 `<script>location.replace` + `<meta refresh>`로 즉시 정상 도달하며, 캐시된 HTML이 본문에 `watch.` 직접 링크를 담아 **api 다운 중 stale 서빙만으로 미리보기와 이동이 동시에 생존**한다)·D-T8의 공개 렌디션
   캐시는 **오리진 앞단**(엣지)에서 리다이렉트·공개 자산을 캐싱하는 별도 계층이다. 이 nginx 폴백 규칙은 그
   **뒤**(리다이렉트가 최종 도달하는 오리진, 즉 `watch.<도메인>` 등 웹앱 서빙 오리진)에서 작동한다 — `go.`는
   "어디로 보낼지"만 담당하고, 이 규칙은 "도달한 URL을 실제로 렌더링"을 담당한다. 적용 순서: 카톡 링크 탭 →
   `go.` **200 OG HTML + 즉시 클라이언트 리다이렉트**(CF Cache Everything 대상 — 舊 "302", 위 정정과 동일 근거) → `watch.<도메인>/watch/:id` 요청 → 본 nginx 폴백(이 응답은 no-cache
   헤더를 CF가 존중해 캐시하지 않는다) → 엔트리 문서 반환 → 클라이언트 라우팅 → api가 서명 URL/공개 URL로 실제
   콘텐츠 로드. 즉 두 규칙은 같은 요청 흐름의 **서로 다른 구간**을 맡아 충돌하지 않는다.
4. **담당**: 인프라 담당. **기한**: W1 — §E 4번(구독자 웹 export)과 동일 시점, §E 5번(`go.` 라우트 구축)보다
   선행 또는 동시(리다이렉트 목적지가 이 폴백 없이는 404이므로, `go.` 라우트만 먼저 열면 도달 실패가 재현된다).

§E 6번(제온 nginx `web` 서비스 항목)에 "동적 라우트 rewrite 규칙 포함"을 명시해 위 규칙의 실행 슬롯으로 삼는다.

### D-T6. 공유·SEO (카톡 유입의 기술적 뒷받침)

- **사실 정정**: 콘텐츠는 **빌드 이후에 생성**되므로 expo-router의 정적 렌더링은 신규 콘텐츠 라우트의 OG 메타를 애초에 만들 수 없다 — 이는 "동적 콘텐츠 증가 시"라는 조건이 아니라 **상시 참**이다. 해당 조건문은 폐기한다.
- **기본안(승격)**: 콘텐츠 상세(`/c/<id>` 등 동적 라우트) 링크는 `go.<도메인>` 단축 링크 서버(api 경량 라우트)가 **OG 태그만 SSR** 후 웹앱으로 리다이렉트한다 — 카톡 채널에 붙는 모든 콘텐츠 링크는 처음부터 `go.` 링크로 발급한다. **Next.js 도입 없이 해결.**
- **정적 OG는 고정 페이지 한정으로 격하**: 홈·지사 목록 등 빌드 시점에 내용이 확정되는 페이지만 expo-router 정적 렌더링의 OG 메타를 사용한다.
- W1 DoD(08 §A)에 "카카오톡 대화방에 붙인 `go.` 링크가 썸네일+제목 미리보기로 렌더된다(실기기 캡처 첨부)"를 포함한다.

**`go.` 라우트 가용성 조치 (ROUND-9-DECISIONS P1, EVAL-ROUND-9 영역1 감점1·정합성 이슈 H-1 해소)**

`go.<도메인>/c/<id>`는 **api 라우트**다 — 위 기본안이 확정한 대로 카톡 채널에 붙는 **모든** 콘텐츠 링크가 이 라우트를
경유한다. 제온(api)이 죽으면 시청자는 이 문을 통과하지 못하고 리다이렉트 자체를 받지 못한다 — D-T8이 보강하는
공개 렌디션 캐시·피드도 이 앞단이 살아 있어야 도달한다. 두 조치로 이 구멍을 닫는다:

1. **엣지 캐시**: `go.` 라우트의 **200 OG HTML 응답**(舊 표기 "302 응답" 정정 — 2026-08-08 Wave 4, EXEC-DECISIONS #21 ②. 302에는 본문이 없어 OG를 실을 수 없고, UA 분기 2변형은 CF가 `Vary: User-Agent`를 캐시 키에 반영하지 않아 성립하지 않는다. 상세 근거는 §D-T5 3항 정정 주석)을 **Cloudflare Cache Everything(짧은 TTL) + api 다운 시 stale 서빙**으로
   캐시한다 — **한 번이라도 방문(캐시)된 링크는 api 다운 중에도 미리보기·리다이렉트가 생존**한다. 단, 최초 미방문
   링크는 캐시가 없어 여전히 api 의존이 남는다.
2. **직접 링크 병행**: 방송 편성표·고정 공지 등 **상시 노출되는 링크**는 `go.` 단축 링크와 함께
   `watch.<도메인>/watch/:id` **직접 링크를 병행 발급**해 `go.` 의존 자체를 줄인다(§E 21번 정적 편성표 페이지가 이미
   이 원칙을 따르고 있으며, 이번 결정으로 반자동 게시 담당자의 카카오 채널 게시 절차 전반에 확장 적용한다).

**담당**: BE 리드. **기한**: W1(`go.` 라우트 구축과 동시, §E 5번).

**따라서 D-T8 "효과 ①"과 08 §B "보강 후" 매트릭스의 "VOD 신규 진입 ✅ 생존"은 `go.` 경유 신규 진입에 한해
"캐시된 링크 한정"으로 읽는다** — 아래 D-T8·08 §B에 동일 단서를 부기한다.

### D-T8. 공개 렌디션 캐시 서빙 (VOD 생존 보강, W2 범위, ROUND-1-DECISIONS X1)

- **목적**: D-T5가 정정한 대로 현행 구조는 제온 다운 시 신규 VOD 시청이 불가하다. published 콘텐츠는 애초에 전체 공개이므로 서명 URL로 비공개를 가장할 이유가 없다 — **공개 렌디션 전용 버킷(또는 접두사) 분리 + Cloudflare 커스텀 도메인 캐시 서빙**으로 전환한다.
- **동작**: 콘텐츠가 송출(published)되는 시점에 720p 렌디션·썸네일을 공개 경로로 **복사(멱등)**하고, 이후 피드 API는 서명 URL 대신 공개 URL을 내려준다. 원본·프리뷰(`awaiting_reporter_review` 이전의 비공개 단계)는 현행 서명 URL 방식을 그대로 유지한다 — 비공개가 필요한 구간까지 공개하지 않는다.
- **필수 대칭 설계 — 삭제·비공개 전환(ROUND-4-DECISIONS V7, EVAL-ROUND-4 영역 10 감점 1·D-7)**: 공개 복사가 있으면 **삭제·비공개 전환도 대칭으로 존재해야 성립하는 설계**다. 콘텐츠가 삭제되거나 published→비공개로 전이될 때 ① 공개 렌디션 버킷의 복사 객체(720p 렌디션·썸네일)를 **제거**하고 ② Cloudflare 커스텀 도메인의 **캐시 퍼지 API를 호출**하는 것은 이 설계의 **필수 단계**다(선택적 정리 작업이 아니라 위 "동작"과 짝을 이루는 반쪽) — 이 단계 없이는 "만료 없는 공개 URL"이 06 삭제 절차의 24시간 SLA를 구조적으로 무력화한다(임시 비공개를 실행해도 공개 URL과 엣지 캐시가 살아 있으면 조치가 실효하지 않는다). 삭제/비공개 전이 훅에 이 두 동작을 **반드시 포함**시키며, §E 14번이 이 구성 요소를 명시한다.
- **효과**: ① 제온 다운 시에도 **직전에 Cloudflare가 캐시한 피드 + 공개 URL 재생이 생존**(완전 실시간 최신화는 아니고 "직전 캐시" 수준) ② api의 서명 발급 부하 제거. **단서(ROUND-9-DECISIONS P1, EVAL-ROUND-9 영역1 감점1·정합성 이슈 H-1 해소)**: 카톡 유입은 반드시 `go.<도메인>` 리다이렉트(api 라우트, D-T6)를 경유하므로, 위 ①의 "생존"이 카톡 유입 경로에서 실제로 성립하려면 D-T6 신설 소절의 `go.` 가용성 조치가 함께 구현돼 있어야 하고, 그 경우에도 **캐시된 링크에 한정**된다(최초 방문 링크는 여전히 api 의존).
- **범위**: W2(§E 체크리스트에 항목 등재). 08 §B 생존 매트릭스는 이 시점을 기준으로 "보강 전/보강 후" 2단으로 구분한다.
- **담당**: BE 리드. **트리거**: 조건부가 아니라 W2 착수 시 무조건 착수(가용성 개선이므로). 삭제·비공개 경로도 동일 시점(W2)에 함께 구현한다 — 공개 복사만 먼저 배포하고 삭제 경로를 뒤로 미루는 순서는 금지(그 구간은 "삭제해도 안 지워지는" 창을 만든다).

> **차단선(HARD, 회귀 방어)과 목표치(SOFT, 정본 목표)를 분리**한다(사용자 결정 2026-08-16):
> 차단선 540,000 B는 실측 512,706 B 대비 +5.3% 여유로, **"지금보다 나빠지는 것"만** 막는다.
> 목표치 358,400 B는 정본 §C가 정한 350 KiB 그대로이며 **철회되지 않았다** — 라우트 분할이 실제로
> 도입되면 그때 차단선을 목표치 쪽으로 끌어내린다(그 조정은 `BUDGETS` 상수 + 이 표 동반 갱신).
>
> **측정 방식을 고정하는 이유**(재현 불가한 게이트는 게이트가 아니다): 압축 레벨을 적지 않으면 값이
> 환경마다 달라진다 — 같은 파일에 `gzip -9`=512,706 / `gzip -6`=514,729 / Node `zlib.gzipSync(level:9)`
> =513,887이다(세 번째는 deflate 구현 자체가 달라 1,181 B 차이). 그래서 게이트는 **`gzip -9` 바이너리**로
> 고정하고, 분자는 **엔트리 문서가 참조하는 초기 JS 청크만**(지연 청크·CSS·이미지·폰트 제외)으로 정의한다.
>
> **게이트 대상 = 구독자 앱 1종**(기자·관제는 측정만 하고 실패시키지 않는다). 근거는 위 Lighthouse CI 게이트
> 각주와 동일하다 — 이 표가 예산을 명시한 것은 구독자 앱뿐이고(카톡 유입 1순위·고령층 회선), 3앱 중
