## ① 총평

이 계획서는 "무엇을 왜 하는가"를 넘어 **"틀렸을 때 무엇으로 아는가"**를 대부분의 항목에 붙여 놓은,
계획 문서로서 상당히 높은 완성도에 도달해 있다. 심사역 관점에서 특히 높게 평가한 지점은 다음 넷이다.

1. **주장 대 리포 실체의 일치.** 표본 검증한 12개 정량 주장이 전부 리포와 일치했다 — 3앱 non-test 소스
   145개(reporter 54·control-center 58·subscriber 33), `services/api` 125 + `media-worker` 12 = 137,
   `packages/ui`에 `README.md` 1건뿐, 3앱 `package.json`에 `react-dom`/`react-native-web`/`@expo/metro-runtime`
   부재, `app.config.ts`에 `web` 블록 부재, `metro.config.js`는 3앱 모두 존재, `ai_provider="stub"`(config.py:14),
   `OpenAiAnalyzer`의 `NotImplementedError`, RTZR 연동 코드 0건, `auto_edit`는 `shared/src/job/job.ts` 상수와
   `transcode.ts` 주석뿐, `HttpUploadService`의 `expo-file-system/legacy` `createUploadTask`, feed의
   `@Get(':id/playback')`+`presignGet`, live env 기본값(poll 3000ms·capacity 5·refill 2000ms),
   `ArbiterModule`이 `QueueModule`만 import. **control-center 테스트는 직접 실행해 153건/15스위트를 확인했다**
   (02 §B의 275건 근거가 실제로 성립). 계획서가 자기 리포를 정확히 읽고 있다.
2. **불리한 재계산을 감추지 않는다.** 재사용률 93%→83.3%(3앱)/86.0%(전체) 하향, 광고 CPM 89,000원→595,000원으로
   6.7배 악화 후 "CPM 우위 논거 포기" 선언, 완전손익분기 "낙관 시나리오조차 12개월 내 미도달", 지사 담당자 총부하
   "M6부터 당번 주마다 구조적 초과 상시화", 제온 다운 시 "VOD 신규 시청도 중단" 정정. 낙관 편향을 스스로 잡아낸
   흔적이 문서마다 남아 있다.
3. **단일 원천(SSOT) 규율.** 방송시간·빈도=01 §C-5, 동시시청 환산 계수=01 §C-6, 예산·인건비=05 §B-3,
   전환 트리거=05 §C, TTFF=02 §C, 라이브 지연 지표=04 §A. 수치가 두 곳에 살아 있어 어느 쪽이 유효한지 알 수
   없는 상태가 거의 제거됐다.
4. **발주–수신 대장의 grep 재현성.** PIVOT-PLAN §6의 40행 상태 주장을 전건 grep으로 재현 검증한 결과
   **40건 모두 실제로 수신돼 있었다**(D-1~D-18, 6-2 17행, 6-3 4행, 6-4 3행). 상호 참조 절 번호도 전수 확인한
   범위에서 모두 실존한다. "수신 완료"라고 써 놓고 실제로는 없는 항목은 발견되지 않았다.

그럼에도 **전 영역 9.5 통과에는 이르지 못했다.** 남은 결함은 대부분 "새로 만든 통제가 자기 문서 안에서
반쪽만 배선된" 유형이고, 그중 하나(05 §B-3③)는 심사역 관점에서 무시할 수 없는 크기다.

- **치명적(영역 3)**: 이번에 신설된 **누적 현금 소요 상한 8,000만원**은 계획 전체의 유일한 재무 정지선인데,
  그 산정이 **M6·M12 종점 격차를 "월평균"으로 오인해 6을 곱하는 방식**이다(05 §B-3③). 매출이 램프업하는
  구간에서 종점 격차는 구간 최소값이므로 필요 운전자금이 체계적으로 과소 산정된다 — 05 자신의 B-2 궤적으로
  재계산하면 기본 시나리오 실제 누적 소요는 **약 7,100만원 이상**(하한 인건비 기준)으로, 상한 8,000만원과
  거의 붙는다. 즉 "M12까지 버틴다"는 전제가 계획서 자기 수치로 이미 위태롭다. 게다가 그 상한의 유일한 탈출구인
  **조달원 확정 액션은 "§G 체크리스트에 등재한다"고 선언만 하고 §G에 실제 항목이 없다**(grep 0건, 오너·기한 부재).
- **재발한 유형(영역 7)**: 04 §H-1 서두가 "Meta App Review·Business Verification의 08 §E 등재는 **여전히
  미수신**(08에 grep 0건)"이라고 단정하는데, **08 §E 10번에 담당·기한과 함께 등재돼 있다**. 07이 세우고 04가
  인용한 "제목으로 grep해 재확인" 원칙을 04가 이번 라운드에 이행하지 않았고, PIVOT-PLAN 대장(D-12 "수신 완료")과
  04 본문이 정면으로 어긋난다.
- **구판 인용(영역 8)**: 06 §A가 01 §C-7을 "당번 주 합계 약 28~36시간/주, 여유가 크지 않음"으로 인용하는데,
  01 §C-7 현재값에서 그 숫자는 **M3~M5의 "커머스 없는 당번 주"** 값이고 M6 이후 그 조합은 소멸한다(31~41시간
  상시). 06의 CS 1선 인력 성립 논증이 소멸한 전제 위에 서 있다.
- **측정 원천 공백(영역 6)**: 03 KPI 요약표의 "기자 업로드 위저드 완주율 ≥95%", "업로드 중단 후 재개 성공률
  ≥95%", "큰 자막 모드 활성 비율"은 계측 발주처가 어디에도 없다 — 02 §E 16번은 **콘텐츠 소비(재생) 계측만**
  커버한다. 01 §C-6이 측정 원천 열 + 미구축 시 대체 원천 + 종료 시점까지 명시한 수준에 03이 못 미친다.

종합하면 **11개 영역 중 1개(영역 10)만 통과선**이며, 나머지 10개는 9.2~9.4다. 다만 미달 폭이 모두 0.1~0.3에
그치고 결함 성격이 "새 범위 발명"이 아니라 **배선 마감·산식 정정·구판 인용 갱신**이라, 한 라운드의 좁은 수정으로
전 영역 통과가 가능한 상태로 판단한다.

### 영역 1. 실행 가능성 — **9.3**

**근거 문서**: 02-web-architecture.md, 08-rollout-transition.md

**인정 사항 (감점하지 않은 것)**
- 02 §A "Expo Web 활성화 선행조건" 3건이 **리포 실측과 정확히 일치**한다(의존성 3종 부재·`web` 블록 부재·
  `metro.config.js`는 이미 존재하며 pnpm resolver 커스터마이즈 보존 필요). 전환의 출발점을 사실대로 그렸다.
- 재사용률 산정표의 분모(3앱 145 / api+media-worker 137)를 **직접 세어 일치를 확인**했고, 산식
  (145−10)÷(145+17)=83.3%, (137−2)÷(137+15)=88.8%, (282−12)÷(282+32)=86.0%도 산술적으로 정확하다.
  신규 파일 열거 항목의 합(17·15)도 실제 합계와 맞는다.
- 02 §E 22개 항목 전부에 담당·기한(W단계)이 부여돼 있고, **차단형 게이트가 2개**(1번 디자인 토큰 승격 미완료 시
  W1 차단, 0-1번 `<input capture>` PoC 미통과 시 §E 7번 착수 불가) 실재한다. 08 §A W1 선행조건·§E 3-1번이
  같은 게이트를 반대편에서도 잠근다.
- 08 §A W1 DoD가 "지정 실기기 3종 × 카카오 인앱 × LTE × 각 20회, 합산 p75 ≤4초"로 **측정 프로토콜을 고정**했다.
  사용자 모집단 없는 런칭 전 단계에서 p75를 판정 가능하게 만든 설계로, 통상적인 "p75 4초 목표"보다 한 단계 낫다.
- 기간(주차) 미확정은 08이 "이월 대상은 기간이지 순서가 아니다"라고 명시하고 시간축 매핑표(3개 앵커 + 8행)로
  선후 관계를 확정했으므로 **감점하지 않는다**(RUBRIC: 실행 단계에서만 알 수 있는 것).

**감점 사유**
1. **02 §D-T3 제목의 과소 표현이 §B와 충돌한다.** 제목이 "인증 — 웹 보안 모델로 교체 (api 소폭 수정,
   **유일한 백엔드 계약 변화**)"인데, 같은 문서 §B `services/api` 행은 신규 표면을 **6계열**(주민 링크 API 4종 +
   `ContentOrigin` 마이그레이션, 공개 렌디션 복사, `go.` OG SSR 라우트, 콘텐츠 소비 계측 집계, 커머스 클릭 계측,
   멀티파트 presign) 열거하고, §B 하단 표가 이를 "신규 파일 15개"로 계상한다. "유일한 계약 변화"는 성립하지
   않는다 — 백엔드 작업량을 읽는 독자가 제목만 보면 규모를 3~4배 과소 평가한다.
2. **§E 20번(미성년자 플래그 + 승인 차단 전이 가드)이 §B 재사용률 산정표에 반영되지 않았다.** 같은 라운드에
   신설된 §E 21번(정적 편성표 페이지)은 산정표 신규 파일 목록에 "웹앱 정적 방송 편성표 페이지 1"로 반영되고
   항목 본문에도 "§B 신규 파일 목록 반영, 재사용률 산정표 갱신"이라고 적혀 있는데, 20번에는 그 문구가 없고
   실제로도 목록(17개)에 BE 전이 가드·데이터 모델·FE 입력 UI가 없다. 산정표가 "설계 단계 근사치"라는 단서를
   달았더라도, **같은 라운드에 추가된 항목 2개를 서로 다르게 처리한 것은 근사가 아니라 누락**이다.
3. **08 §B "보강 후(W2+)" 생존 매트릭스가 라이브 신규 진입 중단을 감춘다.** "보강 전" 표는 라이브 시청 칸에
   "✅ 생존(CF Stream 직결) — **신규 진입자의 세션 메타 조회는 04 문서 참조**"라는 단서를 달았는데, "보강 후"
   표는 "✅ 생존(CF Stream)"만 남기고 단서를 지웠다. 04 §B④ 표는 보강 후에도 "라이브 신규 진입 = ❌ 중단
   (X1 보강 범위 밖)"으로 명시한다 — 두 문서의 같은 사실이 08에서만 낙관적으로 보인다.
4. **W축 지연 시의 에스컬레이션에 오너가 없다.** 08 §A 시간축 매핑표 M1~M12 행은 "W축이 지연돼 W2~W4가 끝나지
   않으면 그 KPI는 '판정 불가'로 처리하고 **지연 자체를 리스크로 격상한다**"고 규정하는데, 격상의 담당·판정
   주기·격상 후 조치가 없다. 계획 전체가 M축(05 Kill Criteria·01 KPI)과 W축의 정합에 의존하는데, 그 정합이
   깨졌을 때 누가 무엇을 하는지가 비어 있다.

**9.5 도달 수정 지시**
- (a) 02 §D-T3 제목의 "유일한 백엔드 계약 변화"를 **"기존 계약의 유일한 변경(신규 엔드포인트 추가는 §B 참조)"**
  으로 고치고, D-T3 본문 첫 줄에 "§B가 열거한 신규 api 표면 6계열은 별도"라는 1줄을 넣어라.
- (b) 02 §B 재사용률 산정표의 신규 파일 목록에 **§E 20번 산출물(미성년자 플래그 데이터 모델·전이 가드 1,
  기자 앱 플래그/동의서 첨부 UI 1)을 추가**하고 합계(17→19), 3앱 재계산((145−10)÷(145+19)), api 재계산,
  전체 재계산 수치를 함께 갱신하라. §E 20번 본문에도 21번과 동일하게 "§B 신규 파일 목록 반영" 문구를 붙여라.
- (c) 08 §B "보강 후" 표의 라이브 시청 칸을 **"라이브 진행 중 시청 ✅ / 라이브 신규 진입 ❌(04 §B④ — X1 보강
  범위 밖, 카톡 공지·정적 편성표 HLS URL 직접 게시로 완화)"**로 2행 분해하거나 동일 취지의 단서를 되살려라.
- (d) 08 §A 시간축 매핑표 M1~M12 행에 **"판정 불가 발생 시 담당: 기획(PM), 월 1회 W축 진척 점검에서 판정,
  2개월 연속 판정 불가 시 05 §C 트리거 점검 회의 안건으로 자동 상정"**을 명시하라(담당·주기·조치 3요소).

### 영역 2. 서비스 성립성 — **9.4**

**근거 문서**: 01-product-strategy.md §A, 02-web-architecture.md

**인정 사항**
- 01 §A-1의 9행 논증이 각 단계를 **현재 구현과 1:1 대조**하고, 웹 고유 제약이 실제로 존재하는 3개 단계
  (1 촬영·3 업로드·8 재생/채팅)로 문제를 좁힌 뒤 §A-3에서 개별 관리방안을 준다. "루프가 끊기는 지점은 없다,
  1·3의 매끄러움 정도 문제로 좁혀진다"는 결론이 논증과 정합한다.
- **T-AI 분리의 정직성.** ai-worker가 결정적 스텁이고 `auto_edit`가 미구현이라는 사실을 리포 경로까지 적시하며
  (실측 결과 전부 사실), "AI가 편집해 방송국이 송출"이라는 제품 최종 가치가 아직 없음을 §A-5 리스크 1행으로
  올려 담당·트리거를 붙였다. 대외 표현 절제 원칙까지 명문화했다. 심사역이 가장 자주 속는 지점을 스스로 열었다.
- 잃는 것 4종(백그라운드 업로드·카메라 제어·오프라인·푸시)에 각각 손실 정의 → 관리방안 → **잔여 리스크**가

  배포 전이라 사전 실측이 구조적으로 불가능하므로 **이 항목 자체는 감점하지 않는다**.

**감점 사유**
1. **§A-4 KPI 4행 중 2행이 측정 불가하거나 산출 근거가 닫히지 않는다.**
   - "업로드 평균 완료 시간 = **네이티브 대비 +20% 이내**" — 같은 표가 다른 행에서 "**현 네이티브 운영 관측치
     부재**"를 인정한다. 비교 기준선이 존재하지 않으므로 이 KPI는 원리적으로 판정 불가인데, 기준선 확보
     계획(예: 전환 전 Expo Go 실기 업로드 N회 측정)이 어디에도 없다.
   - "iOS A2HS 전환율 3개월 15%, 6개월 30%"의 산출 근거가 "3개월 25%·6개월 40% 수락률을 노출 모수에 곱한 값"
     인데, 역산하면 노출 모수가 3개월 60%·6개월 75%로 **시점마다 다르다**. 그 모수(1회 시청 완료율)가 어디서
     왔는지, 왜 시점에 따라 변하는지가 없다. 이 KPI는 "6개월 20% 미만 = 웹푸시 축 폐기"라는 실제 의사결정
     트리거를 물고 있어 근거 공백의 무게가 가볍지 않다.
2. **"업로드 성공률(멀티파트 승격 이후) ≥95%"의 근거가 "업계 대용량 업로드 성공률 참고치 차용"인데 출처가
   없다.** 같은 문서가 인구·이용률 통계에는 각주 5종을 붙였으므로, 출처 표기 기준이 문서 내부에서 일관되지 않다.

**9.5 도달 수정 지시**
- (a) 01 §A-4 "업로드 평균 완료 시간" 행을 **"W0~W1 병행 PoC(02 §E 0-1번)에서 Expo Go 네이티브 경로 업로드
  기준선을 동일 파일·동일 회선으로 각 3회 측정해 확보한 뒤, 그 실측치 대비 +20% 이내"**로 고치고, 기준선 확보를
  0-1번 PoC 산출물 목록에 1줄 추가하라(담당: FE 리드). 기준선 확보가 불가하면 이 KPI를 **절대값 목표**
  (예: 300MB 원본 LTE 업로드 p75 ≤ N분)로 교체하라.
- (b) 01 §A-4 A2HS 행에 **노출 모수의 정의와 값**("배너 노출 대상 = 1회 시청 완료 방문자, 가정 3개월 60%·
  6개월 75% — 근거: …")을 명시하거나, 모수를 단일값으로 고정해 산출식이 재현되게 하라.
- (c) "업계 대용량 업로드 성공률 참고치"에 각주 출처를 달거나, 출처를 못 찾으면 **"출처 미확보 — 첫 3개월 실측
  후 목표 재설정"**으로 표기를 바꿔라(무출처 수치를 목표로 남기지 말 것).

**감점 사유**
1. **B-4(객원 인력 영입) 자체가 실패할 경우의 트리거·대체 경로가 리스크 테이블에 없다.** §B-6은 "영입 후보자의

   문제는 B-3이 "컨택 경로: B-4에서 영입한 인력의 **개인 네트워크를 통한 소개 경로를 1순위**로 삼는다"며
   B-4에 의존하고, §B-4 "시너지" 문단도 B-2 시딩 효과를 B-4에 기대게 해 놓은 것이다. **B-4가 0명이면 B-2·B-3이
   동시에 약화**되는데 그 연쇄에 대한 판정 시점·대체 경로(예: 지역 대학 미디어학과·지자체 마을미디어 활동가
   풀 등)가 없다.
2. **B-5 "레거시 시청자 유래 비중 ≥30%"의 응답 편향 통제가 없다.** 측정 방법이 "QR 부스·온라인 등록 시 1문항
   수집"인데, QR 부스는 지사 담당자·부녀회가 대면으로 등록을 대행하는 채널이므로(§B-2 "대신 등록해준다") 응답이
   대행자에게 노출된다. 이 지표는 흡수 성과의 **직접 지표로 신설된 유일한 정량 근거**인데, 대면 수집 편향에
   대한 언급이 없다.

**9.5 도달 수정 지시**
- (a) §B-6 리스크 테이블에 **"객원 인력 영입 자체 미성사"** 행을 신설하라 — 완화책: 컨택 채널 2순위·3순위
  사전 확보(제주 지역 대학 미디어 관련 학과·지자체 마을미디어 활동가 풀·지역 영상 프리랜서 커뮤니티),
  담당: 기획(PM), **발동 트리거: MVP 착수 +8주 시점 위촉 계약 체결 0건**. 동시에 §B-3 "컨택 경로" 문단에
  **B-4 미성사 시의 B2B 대체 컨택 경로**(지자체 미디어 담당 부서 경유·지역언론 공모 등)를 1줄 명시해
  B-3이 B-4 단일 의존이 되지 않게 하라.
- (b) §B-5 "레거시 시청자 유래 비중" 행의 가정/근거 칸에 **응답 편향 통제 방법**을 1줄 추가하라(예: "대면
  대행 등록 시에는 대행자가 응답을 대신 기재하지 않고 응답지를 봉투 수거하거나, 온라인 등록분만 별도 집계해
  대면분과 비교 — 격차 20%p 이상이면 대면분 수치를 참고치로 강등").

### 영역 5. 콘텐츠 확보 용이성 — **9.4**

**근거 문서**: 01-product-strategy.md §C, 03-accessibility-ux.md §C

**인정 사항**
- **"포맷 준수가 권장이 아니라 업로드 완료 조건"이라는 논증이 코드로 뒷받침된다.** `packages/shared/src/content/content.ts`의
  `Scene.caption` 필수 제약을 확인했다 — 클라이언트 기술과 무관한 서버 계약이므로 웹 전환 후에도 품질 하한이
  유지된다는 주장이 실제로 성립한다.
- **총부하표가 이 계획서에서 가장 잘 쓰인 표다.** 7개 업무를 주당 시간으로 합산해 M3~M5 4조합 / M6 이후
  2조합을 제시하고, "M6부터는 **커머스 없음 조합 자체가 소멸**해 당번 주마다 31~41시간이 **상시** 발생한다 —
  가끔 초과가 아니라 **구조적 상시화**"라고 판정을 스스로 강화했다. 그 위에 **M5 말 판정 시점 + 센터장 택일
  ((a) 증원 / (b) 빈도 하향) + 택일 전 임시 원칙(촬영 건수 하향)**을 걸었다. 노동 부하를 이 정도로 계량해
  게이트까지 만든 계획서는 드물다.
- C-5-1 "주 3건 → 주 5건 전환표"가 요일·소재 카테고리·확보 경로·담당까지 지사별로 명시돼 있고,
  "이 전제의 실현 가능성은 C-7 총부하가 상한"이라고 스스로 한계를 지시한다.
- C-6 수요 측 KPI에 **측정 원천 열 + 계측 미구축 시 대체 원천 4종 + 대체 사용 종료 시점(02 §E 16번 완료)**까지
  붙였고, "완시청률은 서버 로그로 근사 불가 → **측정 불가 상태를 그대로 인정**하고 포맷 교체 트리거에서 제외"라고
  적었다. 측정 불가를 인정하는 KPI 설계는 이 문서 전체의 모범 사례다.
- 03 §C-4 간단 모드가 **STT 비의존으로 재설계**되고(사람이 검수 단계에서 자막 입력), 03 §C-5 주민 링크의
  제약치 5종(72h·5건·500MB·IP 10회/h·검수 게이트 필수)이 수치로 확정돼 02 §D-T9 API 표면과 1:1 대응한다.

**감점 사유**
1. **C-5-1 전환표의 흡수 경로 3개 중 2개가 미확보/미구현인데, 둘 다 실패했을 때의 KPI 하향 규칙이 없다.**
   원문 가정: "① 기존 담당자의 촬영 밀도 증가, ② **B-4 객원 인력(파일럿 3개월 2명)의 촬영 지원**,
   ③ **W2 가동 이후 주민 제보(X5) 편입**으로 흡수한다". ②는 영역 4에서 지적한 대로 성사 보장이 없고,
   ③은 W2 산출물이라 3개월 시점에 존재할지 08 시간축상 확정되지 않는다(W축은 기간 미확정). 결국 **①만 남으면
   담당자 1인의 촬영 시간이 12→20시간으로 늘어 C-7 상한을 더 밀어 올린다.** C-7 리스크는 M6 커머스 상시화만
   다루고 이 +2건 시나리오의 판정 트리거는 없다("얹히면 초과 폭이 더 커진다"는 서술만 있음).
2. **C-7 M6 택일 (b)를 선택했을 때의 연쇄 재계산 대상이 01 안에서만 지시된다.** 원문은 "(b) 라이브커머스 방송
   빈도를 월 4회에서 하향(예: 격주 유지, **05 §A-1과 함께 재조정**)"이라 하는데, 실제 연쇄 대상은 05 §A-1(GMV)
   외에도 **05 §B-1(라이브 비용)·05 §E(KPI)·04 §A SLO#1 모수·04 §E 용량표**까지다. 01 §C-5가 방송시간·빈도의
   단일 원천임을 선언한 만큼, 원천 변경 시 갱신해야 할 하류 문서 목록이 완전해야 한다.
3. **"카테고리 6종 커버리지 100%"가 MVP 캘린더로 구조적으로 보장되지 않는다.** C-6은 이를 "캘린더 설계상
   구조적 보장 목표"라 하는데, MVP 격일 로테이션 표(애월 월·수·금 / 제주시 화·목)에 `politics_talk`가 지사
   편성으로 없고 센터 일요일 "교양/정치인 대담 라이브 **또는** 녹화방송"에만 선택적으로 등장한다. "또는"이므로
   특정 월에 정치인 대담 0건이 가능하다 — 구조적 보장이 아니라 편성 재량이다.

**9.5 도달 수정 지시**
- (a) §C-5-1 표 아래에 **"흡수 경로 실패 시 KPI 하향 규칙"** 문단을 신설하라 — "M3 시점에 ②(객원 위촉 0명)
  또는 ③(W2 미완료)이면 주 5건 목표를 **주 4건으로 자동 하향**하고, 둘 다 미충족이면 주 3건 유지.
  판정: 담당 지사 담당자 + 기획(PM), 시점: MVP 착수 +10주(3개월 실측 회의와 동시)". 존재하지 않는 자원에
  건 목표를 자동으로 걷어내는 규칙이 있어야 C-7 총부하가 추가로 밀리지 않는다.
- (b) §C-7 M6 택일 (b) 문구를 **"(b) 라이브커머스 방송 빈도 하향 — 선택 시 갱신 대상: 01 §C-5 램프표(원천) →
  04 §A SLO#1 모수·04 §E 월간 총 방송시간표 → 05 §A-1 GMV 표·§B-1 라이브 비용표·§E KPI. 갱신 책임: 기획(PM),
  기한: 택일 확정 +2주"**로 확장하라.
- (c) §C-6 "카테고리 6종 커버리지" 행의 근거 칸을 **"월 1회 이상 `politics_talk` 편성을 센터 편성 담당이
  월간 편성표 확정 시 필수 확인(미편성 시 그달 예비 소재일에 배정) — 담당: 센터 편성 담당"**으로 고쳐
  "구조적 보장"이 실제 절차로 뒷받침되게 하라.

### 영역 6. 고령층 사용성 — **9.3**

**근거 문서**: 03-accessibility-ux.md

**인정 사항**
- **현재 코드 기준선을 실측으로 제시하고 갭을 수치로 못박았다** — `apps/subscriber/src/ui/theme.ts`의
  `typo = { title: 20, body: 16, caption: 13 }`을 직접 확인했고, 03의 "13px 캡션·8px 여백 칩은 60~80대에게
  사실상 읽을 수 없거나 누르기 어려운 수준"이라는 진단이 실제 값 위에 서 있다.
- WCAG 2.2 AA 8개 SC × 목표치 × 적용범위 × **KWCAG 2.2 잠정 매핑**을 표로 제시하고, 법정 강제 여부의 판정은
  07 §3으로 위임하되 "판정과 무관하게 AA 상회를 자체 채택"으로 게이트를 스스로 잠갔다.
- `rem` 전환이 react-native-web에서 표준 API가 아니라는 **기술적 제약을 인정하고 실현 경로**(CSS 커스텀 프로퍼티
  + `Platform.select('web')` 분기)와 일정(W1 착수 전 토큰 승격 완료, W2까지 3앱 적용)·수신처(02 §B/§E·08 W1)를
  붙였다. 02 §E 1번·08 §A W1 선행조건에 실제로 수신돼 있음을 확인했다.
- **패널 설계가 연구 수준이다** — 3회차 배치, 과업 4종, 성공 기준 6개, **표본 크기별 실패 허용치 판정식
  ⌊N×0.1⌋ + 경계값 처리(표본 24명 확대 후 재판정)**, SUS 10문항 국문 고정(회차 간 비교 가능성), 치명적 접근성
  결함의 **정의(ⓐ/ⓑ)·판정 주체(모더레이터+FE 리드 합의)·시한(24시간)·기록 양식**, 회차별 예산(≈162~246만원,
  05로 편입 위임). "≥90%"를 표본 수로 판정 가능하게 만든 것이 특히 좋다.
- A-6 재생 실패 폴백 화면이 **라이브(YouTube 전환 + 전화) / VOD(다시 시도 + 전화)로 분기**하고 "VOD는 YouTube
  상시 대체 채널이 없으므로 **없는 대체 경로를 있는 것처럼 안내하지 않는다**"고 명시한 것은 정직한 UX 설계다.
- 리스크 10건·실행 체크리스트 22건 전부에 담당·기한이 있다.

**감점 사유**
1. **KPI 요약표 10행 중 3행의 측정 원천이 발주되지 않았다.**
   - "기자 업로드 위저드 완주율 ≥95%" — 측정 시점만 "런칭 후 상시"로 적혀 있고 계측 구현이 어디에도 없다.
     02 §E 16번(콘텐츠 소비 계측)은 **재생 시작·진행률 25/50/75/100%·조회 집계**만 다루므로 업로드 퍼널을
     커버하지 않는다(02 §B 신규 파일 목록·api 행 모두 확인).
   - "업로드 중단 후 재개 성공률 ≥95%" — "QA + 런칭 후 상시"인데 런칭 후 상시 측정의 원천이 없다.
   - "큰 자막 모드 활성 비율(관찰 지표)" — `localStorage` 로컬 상태이므로 서버 집계 경로 없이는 관찰 불가.
   같은 계획서의 01 §C-6이 **측정 원천 열 + 미구축 시 대체 원천 + 대체 종료 시점**까지 갖춘 것과 대비되어,
   03의 KPI는 판정 근거가 비어 있는 채로 "≥95%" 목표만 남아 있다.
2. **패널 R1과 디자인 토큰 게이트의 순서가 서로를 무력화한다.** 리스크 8은 토큰 승격을 "**W1 착수 전** 완료
   (미완료 시 W1 진행 차단)"로, 리스크 1은 "**패널 R1 과업1 완료율 <90% 관측 시 즉시 토큰 재조정**"으로 건다.
   그런데 08 §A 시간축 매핑표는 R1을 "**W1 진행 중**(§E 1번 토큰 완료 직후 ~ 4번 웹 export 스모크 사이)"에
   배치한다 — 즉 토큰은 R1보다 **먼저 확정·차단 해제**되고, R1은 이미 확정된 토큰을 사후 재조정하는 구조다.
   "저해상도 프로토타입(클릭목업)"으로 토큰 수치를 **사전 검증**한다는 R1의 목적이 게이트 순서와 어긋난다.
3. **03 §C-2 "가상 키보드 회피" 등 공급자 UX 요구가 QA 게이트로 연결되지 않았다.** 실행 체크리스트에 구현
   항목(W2)은 있으나, 이 항목의 검증 방법(어떤 기기·어떤 조건에서 통과로 판정하는지)이 없다 — 같은 문서가
   카톡 인앱 웹뷰 QA에는 "배포 게이트 편입"을 명시한 것과 대비된다.

**9.5 도달 수정 지시**
- (a) 03 §B-2에 **"공급자 측 계측(신설)"** 항목을 추가하고, 02 §E 16번의 범위를 **"콘텐츠 소비 + 업로드 퍼널
  이벤트(위저드 단계 진입·이탈·업로드 시작/재개/완료·큰 자막 모드 토글)"**로 확장 발주하라(02 §E 16번 제목·
  본문 갱신 + §B `services/api` 행에 집계 엔드포인트 범위 추가, 담당: FE 리드 + BE 리드, 기한: W2).
  즉시 발주가 불가하면 01 §C-6과 동일하게 **KPI 표에 "측정 원천" 열을 신설**하고 3개 행에 대체 원천
  (예: 위저드 완주율 = `POST /contents` 생성 건수 대비 `upload-complete` 호출 건수 서버 로그 비율)과
  대체 사용 종료 시점을 기재하라.
- (b) 리스크 1의 트리거를 **"패널 R1 결과로 토큰을 재조정할 수 있도록, R1은 §E 1번 토큰 승격 **PR 머지 전**
  클릭목업(피그마 등 코드 외 산출물)으로 수행한다"**로 고쳐 사전 검증 성격을 회복시키거나, 반대로 리스크 1의

### 영역 8. CS 구축 — **9.3**

**근거 문서**: 06-cs-voc.md §A

**인정 사항**
- **"가용성과 처리시간을 혼동하면 안 된다"는 진단이 정확하고, 그 진단으로 舊 설계를 폐기했다.** 평일 09~18시
  즉시 응대 = 주 45시간 대기 요구 → 센터 운영 0.5인(주 20시간) 예산의 2배 초과 → "문의가 0건이어도 구조적으로
  성립 불가"를 인정하고 코어타임 주 25시간 + 그 외 콜백으로 택일했다. 나아가 **코어타임 창(25h) > 근무 예산(20h)의
  잔여 간극까지 "근무시간 배치 + 당번 착신전환"으로 흡수 설계**했다.
- 문의량 가정이 **01 §C-6 WAU 궤적 인용**으로 통일됐고(독자 모집단 제거), 여유율(6~150배)이 과도해 월 300건
  트리거가 유명무실해지는 문제를 **조기 경보 트리거(실측 월 문의량이 WAU의 10%를 2개월 연속 초과)**로 보완했다.
  트리거가 발동하지 않는 트리거를 스스로 찾아내 보조 트리거를 단 사례다.
- CS 인건비를 처리시간으로 환산해(월 300건 × 15분 = 75시간 ≈ 0.5인 예산의 86%) **"전담 CS 채용 트리거 도달 =
  겸임 불가 확정 신호"**로 재해석하고, 채용 검토를 유예 없이 개시하도록 규정했다. 05 §B-3에 "트리거 발동 시
  증분 150~200만원" 행으로 실제 편입된 것을 확인했다.
- 주말·방송 시간대 운영표가 **시간대 × 4역할 × CS 1선 상태**로 그려져 "토·일 방송 중 전화 CS 완전 공백"을
  숨기지 않고 대체 경로(카톡 당번·아나운서 인지)를 지정한다. 담당자 부재(휴가·이직) 백업 1인 사전 지정,
  인수인계 체크리스트, 헬프데스크 이관 계획(필드 매핑·2주 이중 운영·3개월 CSV)까지 있다.

**감점 사유**
1. **[구판 인용] §A "지사 담당자 겸임 총부하" 문단이 01 §C-7의 소멸한 조합을 인용한다.** 원문: "(당번 주 합계
   **약 28~36시간/주**, 40시간 근무 상한 대비 **여유가 크지 않음** — 01 §C-7 근거)". 01 §C-7 현재 표에서
   28~36시간은 **"M3~M5 · 당번 · 커머스 없음" 주**의 값이고, 01 §C-7은 "**M6부터는 커머스 없음 조합 자체가
   소멸**해 당번 주가 매번 31~41시간(상한 초과 구간)에 들어간다"고 판정했다. 06은 스스로 "01 §C-7이 단일
   원천이며 06은 인용만 한다"고 선언했으므로 **인용을 최신 값으로 갱신할 책임이 06에 있다.** 결과적으로
   06의 CS 1선(카톡 4시간 SLA·주말 당번) 인력 성립 논증이 **M6 이후에는 근거가 사라진 상태**다.
2. **헬프데스크 도구비가 예산 단일 원천(05)에 없다.** §A "헬프데스크 도구 도입 시 월 ~$50(트리거 충족 시에만)",
   §B "대체안 ③ 조기 도입 — 비용 = §A와 동일한 월 ~$50"인데 05에 "헬프데스크" 문자열이 0건이다.
   06은 전담 CS 인건비는 05로 편입 요청해 반영시켰으므로(§B-3 증분 행) **같은 처리를 도구비에는 하지 않은
   비일관**이다. 금액은 작지만 "05가 예산의 단일 원천"이라는 규율의 구멍이다.
3. **§A 채널 표의 "전화(지사 담당자 직통)" SLA가 다른 채널과 다른 근거로 완화돼 있다.** "업무시간 내 즉시 응대
   원칙(**개인 회선이라 코어타임 창 제약이 없음**)"이라 적었는데, 코어타임 제약은 회선 종류가 아니라 **담당자의
   근무 예산**에서 나온 제약이다. 지사 담당자는 01 §C-7 기준 이미 주 24~41시간을 다른 업무로 채우고 있으므로,
   "개인 회선이니 상시 즉시 응대"는 §A가 센터 운영자에 대해 세운 논리(가용성 ≠ 처리시간)를 지사 담당자에게는
   적용하지 않은 것이다.

**9.5 도달 수정 지시**
- (a) §A "지사 담당자 겸임 총부하" 문단의 인용을 **"01 §C-7 기준 M3~M5 당번 주 약 28~36시간, **M6 이후 당번
  주 약 31~41시간으로 40시간 상한을 구조적으로 상시 초과**"**로 갱신하고, 이어서 **"따라서 M6 이후 카톡 4시간
  SLA·주말 당번의 성립은 01 §C-7 M5 말 택일((a) 증원 / (b) 커머스 빈도 하향) 결과에 종속된다 — 택일 결과를
  받은 뒤 본 절의 인력 계획을 재확인한다(담당: 센터 운영자, 기한: M6 진입 직후)"**를 추가하라.
- (b) 06 §A·§B의 헬프데스크 도구비를 **05 §B-1에 "트리거 발동 시 증분: 헬프데스크 도구 월 ~$50(트리거: 월
  300건 초과 또는 다채널 감시 미지원 판정)" 행으로 편입 요청**하고, PIVOT-PLAN §6 대장에 발주–수신 행을
  추가하라(전담 CS 인건비 D-18과 동일 처리).
- (c) §A 채널 표 "전화(지사 담당자 직통)" 행의 SLA 근거를 **"업무시간 내 즉시 응대 원칙 — 단 지사 담당자
  총부하(01 §C-7)가 상한이므로, 촬영·주말 당번 등 다른 업무 수행 중에는 부재중 처리 후 당일 콜백을 정상
  처리로 간주한다"**로 고쳐 가용성/처리시간 구분을 지사 담당자에게도 동일하게 적용하라.

### 영역 9. 소통창구 관리 — **9.4**

**근거 문서**: 06-cs-voc.md §B

**인정 사항**
- **"시청자가 라우팅을 고민하게 하지 않는다"는 대원칙이 실제 규칙으로 구현돼 있다** — 접수자가 대장 기록 후
  **2시간 내 이관**, **SLA 시계는 접수 시각 기준으로 유지되며 이관으로 리셋되지 않는다**, **접수 채널로 회신하는
  책임은 접수자에게 남는다("시청자가 두 번 설명하지 않게")**. 이 3개 규칙이 라우팅 설계의 실효를 만든다.
- 라우팅 다이어그램이 시청자·출연자/판매자·내부 3계층으로 분리되고, 라이브 채팅 문의의 **기록 책임(방송 종료
  후 30분 내 프롬프터 수집분 일괄 등재, 즉답 종결분도 예외 없음)**과 **폭주 예외(50건 초과 시 기한을 익영업일로
  연장하되 미등재 0 유지, 모더레이션은 아나운서·센터장 분담)**까지 규정한다.

**감점 사유**
1. **지사 5개 초과 시 신설하는 "지역 매니저 계층"이 05 인건비 계획에 없다.** §B "지사 확장 시 창구 스케일 규칙 —
   운영 지사 **5개 초과 시 지역 매니저 계층을 신설**하고 … 결정권자: 센터장". 05 §B-3 확장기(4~6지사) 인력 표는
   기자 4~6인·센터 운영 1인·객원 4인·사업개발 0.5인으로 **지역 매니저가 없다**. 05 §C 트리거 ③이 "운영 지사
   6개 초과"를 클라우드 전환 신호로 쓰는 것과 비교하면, 06의 5개 초과 트리거가 재무 계획과 연결되지 않은
   상태로 떠 있다.
2. **폭주 시 모더레이션 분담이 04와 정합하지 않는다.** §B 폭주 예외는 "모더레이션은 **아나운서**·센터장이 분담해
   센터 운영자가 상태 전이 API 호출에 전념하게 한다"고 규정하는데, 04 §C·§D에서 아나운서는 방송 진행 + 프롬프터
   댓글 인지 + (06 §C⑦) 실시간 오보 정정 스크립트 낭독을 이미 맡고 있다. 방송 중 채팅 폭주 시 아나운서에게
   모더레이션을 얹는 것은 04의 역할 배치와 충돌하며, 05 §B-3 "정합성 한계" 문단이 지적한 겸임 물리 한계와도
   같은 종류의 문제다. 대체자(예: 당번 지사 담당자) 지정이 없다.

  행으로 편입 요청한다(트리거: 운영 지사 5개 초과, 단가: 센터 운영 200만원/인 준용)"**를 1줄 추가하고,
  05 §B-3에 해당 증분 행을 신설하도록 PIVOT-PLAN §6 대장에 발주–수신 행을 등재하라.
- (b) §B 폭주 예외 문구의 분담을 **"모더레이션은 센터장 + **당번 지사 담당자**가 분담한다(아나운서는 방송
  진행·프롬프터·오보 정정을 이미 맡고 있어 04 §C 역할 배치상 추가 부담 불가) — 아나운서는 프롬프터로 폭주
  사실을 인지해 센터장에게 알리는 역할까지"**로 고쳐 04와 정합시켜라.
