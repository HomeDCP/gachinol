## ① 총평

문서 8종은 분량·구조 면에서 이례적으로 성실하다 — 전 문서가 리스크 테이블(완화책·담당·발동 트리거 3요소)과 실행 체크리스트를 갖췄고, 04(라이브)·07(법률)은 코드 상수·법령 조문·외부 URL까지 대조해 "근거 없는 낙관"이라는 흔한 실패를 대부분 피했다. **그러나 이 계획의 통과를 막는 것은 개별 문서의 얕음이 아니라 문서 사이의 불일치다** — 같은 지표에 문서마다 다른 수치가 붙어 있고(업로드 트리거 3종, TTFF 3종, 클라우드 전환 트리거 2종), 한 문서가 이미 닫은 결정을 다른 문서가 여전히 열린 옵션으로 계산에 넣고 있으며(쉘 앱 네이티브 브릿지), 01이 다른 문서로 위임한 요구사항 5건은 수신 문서 어디에도 존재하지 않는다. 더 심각한 것은 **리포지토리 실측과 어긋나는 사실 주장 3건**이다: 재사용 논거의 핵심 수치인 "jest-expo 348건"은 실측 303건이고(15% 과장), 업로드 전송 계층은 웹 미지원 API(`expo-file-system`)로 구현돼 있는데 02는 "✅ fetch/XHR"로 표기했으며, 무엇보다 **"제온이 죽어도 VOD 시청은 생존한다"는 세 문서 공통 전제가 코드상 거짓이다**(피드 목록과 재생 서명 URL 모두 api가 발급). 이 세 번째 항목은 02·04·08의 가용성 설계와 05의 클라우드 전환 트리거 계산이 모두 그 위에 서 있으므로 단일 수정으로 끝나지 않는다. 규제 면에서도 07은 강하지만 개인정보 국외이전·청약철회·표시광고·웹 접근성 법정 의무라는 네 축이 통째로 비어 있어, "검토·반영됐는가"라는 영역 11의 질문에 아직 완결로 답하지 못한다. **전 영역이 8.0~9.0 구간에 있어 "실행 가능하지만 고칠 것이 남은 상태"이며, 통과선 9.5에 도달한 영역은 없다.**

## ③ 영역별 상세

### 영역 1. 실행 가능성 — **8.6**

**인정하는 강점**: 02 §B가 전 자산(shared·api·워커 2종·3앱·테스트·CI·compose)에 재사용/수정/폐기 판정을 붙였고 폐기 비용이 0인 이유(스토어 배포 전 단계)까지 논증했다. 08 §A의 W0~W4는 단계별 DoD·선행조건·병렬성을 명시했고, 롤백(정적 디렉토리 스왑, 1분)·클라우드 전환의 컴포넌트별 탈출 설계까지 있다. 02 §A의 웹 호환성 실사표는 실제 앱이 쓰는 모듈 단위로 작성돼 추상적이지 않다.

**감점 사유**

1. **핵심 수치 오류 (02 §A D-T1)** — "기존 화면·훅·스토어·테스트(jest-expo 단위 348건) 그대로 재사용"이라고 재사용 논거의 정량 근거를 제시했으나, 실측은 **303건**이다(`pnpm --filter @gachinol/{reporter,control-center,subscriber} test` 실행 결과: reporter 102 / control-center 153 / subscriber 48). 02 §B도 "3앱 348건"을 반복한다. 재사용률을 정당화하는 유일한 숫자가 15% 과장돼 있다.
2. **웹 미지원 모듈 1건 누락 (02 §A 실사표, §B 판정표)** — 실사표는 `presigned PUT 업로드 (HttpUploadService)`를 "웹 동작 ✅ fetch/XHR, 필요 조치: CORS 설정"으로 적었으나, 실제 구현은 `import * as FileSystem from 'expo-file-system/legacy'` + `FileSystem.createUploadTask`(`apps/reporter/src/upload/http-upload-service.ts:1,50)`로 **웹에서 동작하지 않는다**. 01 §A-1 3행은 "XHR `progress`/`abort`로 대체"라며 재작성을 인정하는데, 02 §B "수정 대상"에는 token-store·촬영·HLS·metro만 있고 업로드 전송 계층이 빠져 있다. 재사용 ~90% 산정의 분모가 검증되지 않았다.
3. **Expo Web 활성화의 최소 선행조건 부재 (02 §E, 08 §A W1)** — 3앱 `package.json`에 `react-dom`·`react-native-web`·`@expo/metro-runtime`이 **없고**, `apps/*/app.config.ts`에 `web` 블록(`bundler`·`output`)이 **없다**(실측). 02 §E 체크리스트 3번은 `expo export --platform web` 스모크부터 시작하는데, 그 명령이 성립하기 위한 의존성 추가·설정이 어느 체크리스트에도 없다.
4. **OG 정적 주입이 구조적으로 불가능한데 조건부로 서술 (02 §D-T6)** — "정적 출력으로 OG가 불충분하면(동적 콘텐츠 증가 시) `go.` SSR"이라 썼으나, 콘텐츠는 **빌드 이후에 생성**되므로 expo-router 정적 렌더링이 신규 콘텐츠 라우트의 OG를 만들 수 없는 것은 조건이 아니라 상시 참이다. 카톡 링크 미리보기는 03 §A-2가 유입의 사실상 전부라고 규정한 경로인데, 기본안이 작동하지 않는 상태로 W1 DoD(08 §A)에 "링크 미리보기 노출 확인"이 없다.
5. **가용성 설계의 사실 오류 (08 §B 생존 매트릭스, 02 §D-T5)** — "제온 다운 → 시청(VOD) ✅ 생존(CF 캐시+R2)", "제온이 죽어도 시청 경로는 생존 — 죽는 것은 API 의존 기능만"이라 단정했으나, VOD 재생 URL은 api가 `s3.presignGet`으로 서명 발급하고(`services/api/src/feed/feed.service.ts`, `GET /v1/feed/:id/playback`) 피드 목록도 api다. **api가 죽으면 신규 시청은 0이다.** 생존하는 것은 이미 로드된 서명 URL(만료 전까지)뿐이다. 이 오류 위에 08 §C 가용성 트리거와 05 §C 리스크비용 계산이 서 있다.
6. **문서 간 트리거 충돌 (08 §C ↔ 05 §C)** — 08은 "재무: 월 순수익이 클라우드 예상비($50~80/월)의 3배(≈월 22~35만원)를 3개월 연속" + "**하나라도** 충족 시 해당 컴포넌트 이관", 05는 "① 월 총매출 ≥ **800만원** 3개월 연속" + "**2개 이상** 동시 충족 시 착수". 임계값이 20~30배 다르고 발동 규칙이 상반된다. 어느 문서가 원천인지 선언돼 있지 않다.
7. **크리티컬 패스의 데드라인 부재 (08 §A W0, §D)** — 방화벽 개방/Tunnel 승인이 "사용자 승인 필요, 크리티컬 패스"로 식별됐고 트리거는 "W0 착수 시"뿐이다. **언제까지 승인이 나지 않으면 무엇을 포기·대체하는가**가 없다. 도메인 미결정 리스크는 "W3 전까지"라는 기한이 있어 대조적이다.

**9.5 도달을 위한 수정 지시**

- 02 §A·§B의 "348건"을 실측치 303건(reporter 102·control-center 153·subscriber 48)으로 교체하고, 수치 옆에 측정 명령과 측정일을 병기하라.
- 02 §A 실사표의 업로드 행을 "❌ `expo-file-system` 웹 미지원 → XHR(`upload.onprogress`/`abort`) 재작성 필요"로 정정하고, §B "수정 대상" 목록에 **업로드 전송 계층**을 추가한 뒤 재사용률(~90%)을 재산정해 산정식(수정 파일 수 ÷ 전체 파일 수 등)을 명시하라.
- 02 §E 체크리스트 3번 앞에 "0. 3앱에 `react-dom`·`react-native-web`·`@expo/metro-runtime` 추가 + `app.config.ts`에 `web: { bundler: 'metro', output: 'static' }` 설정"을 신설하라.
- 02 §D-T6에서 `go.` OG SSR을 **기본안으로 승격**하고 정적 OG는 고정 페이지 한정으로 격하하라. 08 §A W1 DoD에 "카카오톡 대화방에 붙인 `go.` 링크가 썸네일+제목 미리보기로 렌더된다(실기기 캡처 첨부)"를 추가하라.
- 08 §B 매트릭스의 "제온 다운" 행을 `시청(VOD) ❌ 신규 진입 불가(피드·재생 서명 URL 모두 api 발급) / 진행 중 재생만 서명 만료까지 생존`으로 정정하고, 02 §D-T5의 동일 문장을 수정하라. 그 위에서 "신규 VOD 시청 생존"이 필요하다면 완화책(예: 공개 읽기 전용 R2 버킷 + 사전 생성 매니페스트, 또는 Cloudflare Worker에서 서명 발급)을 담당·트리거와 함께 신설하라.
- 클라우드 전환 트리거의 **단일 원천 문서를 선언**하라(권장: 05 §C가 재무, 08 §C가 운영 트리거를 갖되 서로를 인용). 임계값과 "하나라도/2개 이상" 규칙을 한쪽으로 통일하고, 다른 문서는 링크만 남겨라.
- 08 §D에 "방화벽/Tunnel 승인 미도래 데드라인 = W0 착수 + 4주. 초과 시 Cloudflare Tunnel 단독안으로 확정하고 포트 개방 옵션을 폐기한다" 같은 **기한과 자동 결정 규칙**을 넣어라.

### 영역 2. 서비스 성립성 — **8.7**

**인정하는 강점**: 01 §A-1이 파이프라인 8단계를 현재 구현 파일 경로와 함께 대조하고 "루프가 끊기는 지점은 없다, 문제는 1·3·8의 매끄러움"으로 쟁점을 정확히 좁혔다. §A-2의 얻는 것/잃는 것 표는 손실 4종에 영향 범위·손실 정도·관리방안을 붙였고, §A-3은 각 손실에 **잔여 리스크**까지 남겨 과잉 낙관을 피했다. 통계 각주 6건에 출처 URL이 있다.

**감점 사유**

1. **이미 닫힌 옵션을 완화책으로 계상 (01 §A-3-①-4, §A-5 3행)** — "쉘 앱이 네이티브 브릿지(Capacitor)로 확정되면 백그라운드 업로드 손실을 사실상 제거", "doc 02 확정 대기 항목"이라 썼으나 **02 §D-T2는 이미 확정했다**: iOS는 WKWebView 래퍼, 쉘의 책임은 "① 웹앱 로드 ② 푸시 토큰 등록 ③ 딥링크 뿐, **비즈니스 로직 0**". 03 §D는 한 발 더 나아가 "쉘 앱 전용 기능이 생기면 원칙이 깨진다"를 배포 승인 기준으로 못박았다. 01의 조건부 해결책은 사망했는데 리스크 테이블에 살아 있다.
2. **업로드 트리거 3중 불일치** — 02 §D-T4는 "2단계(W2 내 **필수**)"라고 무조건 승격이라 쓴 동시에 같은 문단에서 "**발동 트리거**: 업로드 실패율 >5% 또는 평균 원본 >300MB"라는 조건부 트리거를 붙여 자기모순이고, 01 §A-5는 "첫 1개월 실패율 > 15%"를 트리거로, 01 §A-4 KPI는 "첫 1개월 성공률 ≥ 85%"(=실패율 15% 허용)를 목표로 잡는다. **02 기준으로 즉시 발동인 값이 01 기준으로는 목표 달성이다.**
3. **동일 지표의 목표 충돌 (01 §A-4 ↔ 03 §B-2)** — "구독자 URL→재생 성공률 ≥98%"(01) vs "재생 도달률(카톡 클릭→첫 프레임) ≥95%"(03). 정의가 사실상 같은데 목표가 다르고, 어느 쪽이 배포 게이트인지 없다.
4. **가용성 리스크 미등재** — 영역 1-5의 사실 오류(api 다운 = 신규 VOD 시청 0)가 01·02의 어느 리스크 테이블에도 없다. "서비스가 성립하는가"의 답에는 "제온이 살아 있을 때만"이라는 조건이 붙는데 그 조건이 명시되지 않았다.
5. **주민 제보 경로의 이중 설계 + 위임 실패 (01 §C-2 ↔ 03 §C-5 ↔ 02/08)** — 01은 `ContentOrigin`에 `resident_tip` 추가 + 기자가 Scene 대행하는 **스키마 변경형**을, 03은 만료·건수 제한이 붙은 **무인증 임시 업로드 링크형**을 제시한다. 두 설계는 인증 모델·데이터 모델·남용 방지가 전혀 다른데 조율되지 않았고, 01 부록이 이 항목을 위임한 **02·08 어디에도 존재하지 않는다**(02 §B는 api 추가분을 "CORS·쿠키 refresh·멀티파트 presign·`go.` OG 라우트"로 한정, 08 W0~W4에 항목 없음). 무인증 업로드의 용량·빈도·악용 통제 설계도 없다.
6. **오프라인 관리방안의 실현 근거 약함 (01 §A-3-③)** — "Service Worker + IndexedDB/OPFS로 촬영본 임시 보관"이라 했으나 `<input capture>`로 얻은 0.9GB급 File 객체를 IndexedDB에 보존하는 것은 iOS Safari 저장 쿼터·삭제 정책상 보장되지 않는다. PoC 항목(§A-6)은 있으나 **PoC 실패 시의 대체안**이 없다(현재는 "사무실 복귀 후 업로드" 운영 가이드가 유일한 백업인데, 이는 손실 자체를 수용하는 것이지 완화가 아니다).

**9.5 도달을 위한 수정 지시**

- 01 §A-3-①-4와 §A-5의 "조건부 완전 해결(Capacitor)" 항목을 삭제하고, "02 §D-T2로 쉘 = 순수 래퍼 확정 → ①·③의 웹 전용 완화책(청크 재개·로컬 보존)이 **유일 경로로 확정됨**"으로 문장을 교체하라. 리스크 테이블의 해당 행도 "결정 완료, 웹 완화책 필수"로 상태를 바꿔라.
- 멀티파트 승격의 조건을 **한 문장으로 통일**하라(권장: "W2 내 무조건 승격. 그 전 구간에서 실패율 >5%가 관측되면 W1 중 즉시 착수"). 02 §D-T4의 자기모순 문구를 정리하고, 01 §A-5 트리거(15%)와 §A-4 KPI(85%)를 이 기준에 맞춰 재작성하라.
- 재생 성공률 지표를 하나로 통합하라: 정의(카톡 클릭 → 첫 프레임), 목표치, 측정 도구, 게이트 여부를 03 §B-2에 단일 정의하고 01 §A-4는 인용만 하도록 고쳐라.
- 01 §A-5에 "api(제온) 다운 시 신규 VOD 시청 불가" 리스크를 신설하고 완화책·담당·트리거를 붙여라.
- 주민 제보 경로를 **한 설계로 확정**하라(01 §C-2 또는 03 §C-5). 확정안을 02에 "api 변경분"으로, 08에 "W2 내 서브 항목"으로 편입하고, 무인증 링크를 채택한다면 만료·건수·파일 크기·IP 레이트리밋·검수 게이트를 수치로 명시하라.
- 01 §A-6의 IndexedDB PoC 항목에 "실패 시 대체안: 촬영 직후 즉시 업로드 강제(임시 보관 없음) + 실패 시 재촬영 안내"를 미리 적고, PoC 완료 기한(예: W2 착수 전)과 담당을 넣어라.

### 영역 3. 수익화 가능성 — **8.3**

**인정하는 강점**: 05는 이번 계획에서 가장 정직한 문서 중 하나다 — §0에서 모든 수치가 가정임을 선언하고, 보수/기본/낙관 3케이스를 일관되게 유지하며, **인프라 OPEX 손익분기와 완전손익분기를 분리**해 "인건비를 숨긴 흑자"라는 흔한 기만을 스스로 차단했다. D절 가격 정책은 그립·네이버·카카오 실효 수수료를 출처와 함께 비교했고, 남도장터·여수 찰옥수수 사례로 GMV 가정의 상단을 보수적으로 잡았다. F절 리스크 9건 전부에 담당·트리거가 있다.

**감점 사유**

1. **트리거 공식이 계산 불가 (05 §C ④)** — 공식은 `월매출 × (연간 예상 다운타임시간 ÷ 8,760) > 연간 증분비용`인데, 바로 아래 판단근거 메모는 `500만원 ÷ 720시간 × 24시간 ≈ 16.7만원`이라는 **다른 식**을 쓴다. 공식 그대로 계산하면 500만 × (24/8760) ≈ 1.37만원으로 **12배 차이**다. 차원(월/연)이 섞여 트리거가 발동 여부를 판정할 수 없다.
2. **클라우드 트리거의 이중 정의** — 영역 1-6과 동일. 05는 "2개 이상 동시 충족 시 착수", 08 §C는 "하나라도 충족 시 이관". 같은 의사결정에 두 규칙이 병존한다.
3. **후원·멤버십 축이 스토어 정책과 충돌하는데 미해결 (05 §A-4 ↔ 07 §1-4 ↔ 02 §D-T2/03 §D)** — 05는 "웹 결제로 유도하면 수수료 없음 … **웹 전환 자체가 이 리스크를 원천적으로 제거**"라고 단정한다. 그러나 07 §1-4는 "디지털 전용 혜택(유료 구독·후원 결제·프리미엄 다시보기)으로 확장되면 그 즉시 IAP 의무 대상 … 실물과 디지털을 같은 결제 플로우에 섞으면 **앱 전체가 IAP 미준수로 리젝**"이라 경고하고, 02 §D-T2·03 §D는 쉘 앱이 **기능 분기 없이 동일 웹앱을 감싼다**고 못박았다. 결론: 쉘 앱 안에서 후원·멤버십 UI가 그대로 노출된다. M12 기본 60만원/월의 매출원이 스토어 리젝 리스크와 직결되는데 완화책·담당·트리거가 어느 문서에도 없다.
4. **광고 축의 규제 미검토 (05 §A-3·§D-3)** — 협찬·상품소개 슬롯·프리롤은 「표시·광고의 공정화에 관한 법률」과 「추천·보증 등에 관한 표시·광고 심사지침」상 **경제적 이해관계 표시 의무** 대상이고, 라이브커머스 중 판매자 발언은 부당표시 리스크가 있다. 05에도 07에도 이 축의 규제 항목이 없다. 광고 매출이 M12 기본 375만원(4축 중 최대 비중)인데 실행 조건 3개는 전부 영업 조건뿐이다.
5. **인건비 가정이 다른 문서의 인력 요구와 불정합 (05 §B-3)** — MVP 가정은 "기자 2인 + 센터 운영 0.5인 = 2.5인"이다. 그러나 04 §C 리허설은 T-60~T-0에 현장 PD·인프라 담당·아나운서·센터 운영 **4개 역할의 동시 투입**을 요구하고, 06 §A는 센터 운영자 1명 + 지사 담당자 2명의 CS 상시 대기를 전제한다. 05 §F-9가 "조직 계획 확정 시 재계산"이라는 트리거를 둔 것은 방치가 아니지만, **2.5인으로는 계획된 편성(토·일 라이브)이 물리적으로 불가능하다**는 정합성 문제 자체가 지적되지 않았다.
6. **중단 기준(kill criteria) 부재** — G절에 "파일럿 1회 → 실측 보정"은 있으나, 실측이 보수 시나리오(회당 GMV 30만원)에도 못 미칠 때 **어느 축을 언제 접는가**가 없다. F-4·F-5는 프로모션 전환·예산 신청 전환만 제시해 모든 경로가 "계속한다"로 수렴한다. 05 §B-3 결론도 "보수 시나리오는 … 사업모델 자체의 재검토 트리거로 삼는다"에서 멈춘다(재검토의 판정 기준·시점·결정권자 없음).

**9.5 도달을 위한 수정 지시**

- 05 §C ④의 공식을 `연매출 ÷ 8,760 × 연간 예상 다운타임시간 > 클라우드 이관 연간 증분비용(91~211만원)`으로 고치고, 메모의 예시 계산을 같은 식으로 다시 쓰라(월매출 500만원 = 연 6,000만원 → 6,000만 ÷ 8,760 × 24 ≈ 16.4만원 < 91만원 → 미발동).
- 05 §C와 08 §C의 트리거를 통합하라(영역 1과 동일 지시).
- 05 §A-4에 "쉘 앱(스토어 배포본)에서는 후원·멤버십 진입점을 **숨긴다**"는 설계 결정을 추가하거나, 반대로 "후원·멤버십은 스토어 쉘 출시 이후 도입 보류"로 로드맵을 조정하라. 어느 쪽이든 03 §D의 "기능 분기 없음" 원칙과의 충돌을 명시적으로 해소하고(예: "결제 진입점만 예외로 허용, 그 외 기능 분기 금지"), 담당(PO+테크리드)·트리거(쉘 앱 심사 제출 전)를 붙여라. 07 §1-4의 가드레일 항목에도 상호 링크를 걸어라.
- 05 §A-3 실행 조건에 "④ 유료광고 표시 문구·표기 위치 확정(「추천·보증 심사지침」) — 담당: 외부 법률자문+센터 운영팀, 트리거: 첫 협찬 계약 체결 전"을 추가하고, 07 §3에 대응 절(예: §3-10 표시·광고 규제)을 신설하라.
- 05 §B-3에 "이 인건비 가정으로는 04 §C 리허설의 4역할·06 §A의 CS 상시 대기를 충족할 수 없다 — 겸임 매핑표(누가 어느 시간대에 어떤 역할을 겸하는가)를 조직 계획 확정 시 함께 산출한다"는 한계 문장을 넣고, 겸임 매핑표를 G절 체크리스트 항목으로 올려라.
- 05 §F에 "축별 중단 기준"을 신설하라(예: "커머스: 파일럿 3회 누적 GMV < 90만원이면 M7 이후 방송 빈도 축소 및 광고 축으로 자원 재배분 — 결정권자 사업총괄, 판정 시점 M6 말").

### 영역 4. 레거시 미디어 흡수 — **8.4**

**인정하는 강점**: "기관 대 기관으로 경쟁하지 않고 시청자·콘텐츠·인력을 개인 단위로 흡수한다"는 프레임(01 §B-1)은 자원 비대칭을 정면으로 인정한 현실적 전략이다. 세 축이 서로를 지탱하는 구조(B-4 영입 인력의 개인 네트워크가 B-2 시딩과 B-3 컨택 경로를 동시에 연다)를 명시한 점이 특히 좋다. 각 축에 단계·기간·목표·경로 표가 있고, KPI 6종·리스크 5건(담당·트리거)·체크리스트 7항목이 붙어 있다.

**감점 사유**

1. **근거 통계의 노후 (01 각주 5·6)** — 애월읍 인구 36,233명은 **2019-12-31 기준 위키백과**, 70대 이상 스마트폰 보유율 36.3%는 **2019년** 조사다. 2026년 계획의 목표 인원 산정(지사당 3,000명 = 고령인구의 44%)과 리스크 판단(스마트폰 미보유 인구)의 근거가 7년 전 값이다. 문서가 "갱신 통계는 실사 필요"라고 스스로 적었으나, **실사의 담당·기한이 §B-7 체크리스트에 없다**(있는 것은 "3개월 시점 친구수 실측 후 목표 재조정 회의"뿐 — 인구 실사와 다른 항목이다).
2. **목표 산식의 논리 결함 (01 §B-2)** — "Phase 2 목표 지사당 3,000명은 애월 추정 고령인구(~6,900명)의 약 44%"라고 검산했으나, ⓐ 3,000명은 애월·제주시 **각 지사**의 목표인데 제주시(인구 규모가 애월과 자릿수가 다름)에 같은 절대 수치를 적용한 근거가 없고, ⓑ 카톡 채널 친구는 고령층 전용이 아닌데 분모를 고령인구로 잡아 44%라는 수치가 낙관인지 보수인지 판정 불가다.
3. **위임 항목이 수신 문서에서 미처리 (01 §B-4 → 05)** — 객원 인력 처우를 "활동비 + B2B 수익쉐어"로 제안하고 "doc 05 손익 검증 대기"라 명시했으나, **05 §B-3 인건비 가정에 객원 인력 항목이 없다**(기자 2인·센터 0.5인만). 01 부록 의존성 표의 "B-4, B-7 → 05" 항목이 수신되지 않았다.
4. **오너 공백 2건 (01 §B-6)** — "센터 콘텐츠전략 담당(신설, 담당자 미정 — 오픈 이슈)", "인사 담당(신설, 오픈 이슈)". 오픈 이슈로 표시한 정직함은 인정하나, 루브릭이 요구하는 것은 담당의 존재다. **누가 언제까지 이 담당을 지정하는가**(결정 담당·기한)가 없어 두 리스크의 완화책이 실행 주체 없이 떠 있다.
5. **경쟁 반응 시나리오 부재 (01 §B 전체)** — 리스크 테이블은 "레거시 방송사가 협업 요청을 경쟁자로 오인해 거부"만 다룬다. 그러나 이 전략의 실질 위협은 거부가 아니라 **모방**이다 — 지역 방송사·지역신문이 동일 포맷(마을 카톡 채널 + 짧은 로컬 클립)을 자체 브랜드로 복제하면 B-2·B-3이 동시에 무력화된다. 진입장벽(왜 우리만 할 수 있는가)이 C-3(날씨예보 비경쟁 포지셔닝)에만 있고 B절에는 없다.
6. **B2B 축의 선행조건이 두 문서에서 다름** — 01 §B-3은 "샘플 릴 3편 → 시연 → 6개월 유상 계약 1건"을 경로로 삼는데, 05 §A-2는 "콘텐츠 라이브러리 50건 이상 축적"을 실행 조건 1번으로 둔다. 01은 이 선행조건을 인지하지 않고 있어 두 문서의 B2B 타임라인이 우연히 맞은 것에 가깝다.

**9.5 도달을 위한 수정 지시**

- 01 §B-7 체크리스트에 "애월읍·제주시 최신 주민등록 인구·연령 구조 실사(출처: 제주특별자치도 인구통계 또는 KOSIS) — 담당: 기획(PM), 기한: MVP 착수 전"을 신설하고, §B-2 본문과 각주 5·6을 실사 결과로 갱신할 것을 문서에 명시하라.
- §B-2의 목표를 **지사별로 분리**하라(애월 3,000명 / 제주시는 별도 산정). 분모를 "지사 관할 전체 성인 인구"로 바꾸고 고령층 비중은 별도 KPI(≥40%)로만 남겨라.
- 05 §B-3 인건비 표에 "객원 인력 활동비(2명×월 X만원) + B2B 수익쉐어(매출의 Y%)"를 별도 행으로 추가하고, 01 §B-4의 "doc 05 손익 검증 대기" 문구를 05 해당 절 링크로 교체하라.
- 01 §B-6의 "담당자 미정" 2건을 "**지정 책임자: 기획(PM), 지정 기한: MVP 착수 + 4주. 미지정 시 센터장이 겸임한다**" 형태로 바꿔 오너 공백을 없애라.
- §B-6에 "레거시 미디어의 포맷 모방" 리스크를 신설하고 완화책(고정 출연진 개인 브랜드·지사 물리 거점·이미 확보한 카톡 친구 기반 등 복제 난이도가 높은 자산 중심의 해자 논리), 담당, 트리거(경쟁 채널 개설 인지 시)를 붙여라.
- 01 §B-3에 05 §A-2의 선행조건("라이브러리 50건 축적")을 인용하고, 01 §C-6 업로드 KPI로 그 시점이 언제인지 역산해 명시하라.

### 영역 5. 콘텐츠 확보 용이성 — **8.5**

**인정하는 강점**: 01 §C-1의 "데이터 구조가 품질 하한을 강제한다"는 논증은 코드로 검증된다 — `packages/shared/src/content/content.ts`의 `Scene.caption` 필수, `ProgramCategory` 6종이 실제로 타입 계약이며 클라이언트가 우회할 수 없다(실측 확인). 03 §C-4의 "간단 모드"(자막 생략 + AI 자동 생성)와 §C-5 주민 공급 경로는 공급자 진입장벽을 정면으로 겨냥한 좋은 설계다. C-3의 날씨예보 비경쟁 포지셔닝(제도권 기관이 구조적으로 "감"을 표방할 수 없다)은 복제 난이도 논리로서 설득력이 있다.

**감점 사유**

1. **주민 참여 경로의 이중 설계 + 구현 트랙 부재** — 영역 2-5와 동일. 01 §C-6은 "주민 제보 비중 6개월 10%"를 KPI로 잡았는데, 그 경로의 설계가 두 개(01 §C-2 / 03 §C-5)이고 02·08 어디에도 구현 항목이 없다. **KPI가 존재하지 않는 기능에 걸려 있다.**
2. **캘린더와 인력·KPI의 불정합 (01 §C-5 ↔ §C-6)** — §C-5는 월~금 5요일 × 2지사 = 주 10건을 요구하는 표를 제시하는데, §C-6 KPI는 "지사당 주 3건 → 3개월 후 주 5건"(주 6~10건)이다. 본문이 "격일 로테이션으로 시작"이라 완충하지만 **표 자체는 수정되지 않은 채 남아** 무엇이 계획인지 모호하다. `docs/infrastructure.md` §1의 실측 전제("하루 2~4건")와의 정합은 §C-6이 주장하지만, 주 5요일 편성은 그 상한(주 14~28건)이 아니라 인력 상한에 걸린다.
3. **"간단 모드"의 전제 기능이 미구현인데 의존이 추적되지 않음 (03 §C-4)** — 간단 모드는 "업로드 시 AI가 STT/장면분석으로 자동 자막 생성"을 전제한다. 그러나 `services/ai-worker`는 결정적 스텁이고 실 STT(RTZR) 연동은 미착수다(`docs/infrastructure.md` §7, 07 §4가 "RTZR 약관 확인"을 STT 실연동 착수 전 액션으로 둠). **03 실행 체크리스트에도 08 W0~W4에도 "ai-worker 실 STT 연동"이 없다** — 콘텐츠 확보 전략의 핵심 완화책이 미착수 선행 의존 위에 서 있다.
4. **재미의 측정 부재 (01 §C-4·§C-6)** — 루브릭 질문은 "재미있는 콘텐츠로 채우기 쉬운 구조인가"다. §C-4는 캐릭터화·사투리 자막·게임화를 나열하지만 §C-6 KPI는 **전부 공급량 지표**(업로드 건수·제보 비중·갱신 빈도·카테고리 커버리지)다. 시청 지속시간·완시청률·재방문 같은 수요 측 지표가 없어, 포맷이 실패했을 때(올리지만 아무도 안 봄) 이를 감지·교체할 기준이 없다.
5. **제작 공수 증가분이 손익에 반영되지 않음** — 사투리-표준어 병기 자막(§C-4)·고정 출연진 브랜딩·카테고리별 Scene 템플릿 준수는 모두 편당 제작 시간을 늘린다. 01 부록이 "C-5 날씨예보 갱신 빈도 확대의 인력 손익 정합 → 05"를 위임했으나 05에 해당 분석이 없다(위임 블랙홀).
6. **품질 하한의 이면 미검토** — §C-1은 Scene 구조 강제를 품질 보증으로 제시하지만, 같은 강제가 공급 위축 요인이라는 점은 03 리스크 9번에서만 다뤄지고 01 §C-7 리스크 테이블의 트리거("제보 시도 대비 완료율 < 50%")는 아직 존재하지 않는 제보 경로에 걸려 있다. **기존 기자 경로의 이탈률 트리거가 없다**(03 리스크 9번의 트리거도 "눈에 띄게 높게 관측 시"로 정성적).

**9.5 도달을 위한 수정 지시**

- 주민 제보 경로를 단일 설계로 확정하고 02·08에 구현 항목으로 편입하라(영역 2 지시와 동일). 확정 전까지 01 §C-6의 "주민 제보 비중 10%" KPI에는 "기능 개통 후 6개월 기준"이라는 기준 시점을 명시하라.
- 01 §C-5 캘린더 표를 MVP 실제 편성(2지사·격일 로테이션)으로 다시 그리고, 12지사 완성형 캘린더는 별도 "목표 상태" 표로 분리하라. §C-6 KPI와 표의 주간 건수를 일치시켜라.
- 03 §C-4에 "선행 의존: `services/ai-worker` 실 STT(RTZR) 연동 — 미완료 시 간단 모드는 '자막 없이 업로드 후 기자 사후 입력'으로 축약 동작한다"를 명시하고, 08 W2 체크리스트에 "ai-worker 실 STT 연동(간단 모드 전제)"을 추가하라.
- 01 §C-6에 수요 측 KPI를 추가하라: 콘텐츠당 평균 시청 완료율(≥X%), 업로드 후 7일 조회수 중앙값, 카테고리별 조회 편차. 그리고 "3개월 연속 하위 카테고리 = 포맷 교체 검토(결정권자: 센터 편성 담당)"라는 교체 규칙을 §C-7에 리스크 항목으로 넣어라.
- 05에 "콘텐츠 제작 공수 가정"(편당 촬영+자막+검수 시간)을 신설하고, 사투리 병기·템플릿 준수·날씨예보 빈도 확대의 증분 공수를 인건비 가정에 반영하라. 01 부록의 해당 위임 행에 05 절 링크를 걸어 위임 완료를 표시하라.
- 03 리스크 9번의 트리거를 정량화하라(예: "기자 위저드 자막 단계 이탈률 > 20% 또는 촬영 단계 대비 +15%p").

### 영역 6. 고령층 사용성 — **9.0**

**인정하는 강점**: 이 문서가 계획 전체에서 가장 완성도가 높다. ⓐ 현재 코드 실측 기준선 표(본문 16px·캡션 13px·제목 20px·터치 타깃 미정의)가 `apps/subscriber/src/ui/theme.ts`와 **정확히 일치**한다(실측 확인: `typo = { title: 20, body: 16, caption: 13 }`). ⓑ WCAG 2.2 AA 9개 SC마다 요구치와 자체 목표치를 수치로 대비했고 본문 대비 7:1처럼 AA를 상회하는 지점을 근거와 함께 특정했다. ⓒ "카톡 인입 → 원탭 재생, 중간 화면 0개"를 KPI(인터스티셜 0개, 매 배포 전 QA 게이트)로 못박았다. ⓓ 어르신 패널이 회차(R1~R3)·인원·모집 경로·과업 4종·성공 기준 6종(SUS 80 포함)·게이트(치명 결함 1건이면 다음 회차 전 필수 수정)까지 설계됐다. ⓔ 카카오 인앱 웹뷰에서 PWA 설치 API가 동작하지 않는다는 함정을 잡아내 "다른 브라우저로 열기 선행" 분기를 리스크·체크리스트 양쪽에 반영했다. ⓕ 리스크 9건 전부 담당·정량 트리거, 체크리스트 18항목.

**감점 사유**

1. **TTFF 목표 3중 불일치** — 03 §B-2 "4G ≤ 3초", 03 §B-1 성공 기준 "탭→첫 프레임 ≤ **15초**(4G)", 02 §C "카톡 링크 탭 → 재생 시작 ≤ 4초(LTE)". 같은 사용자 여정에 세 수치가 있고 **03 문서 내부에서도 3초와 15초가 충돌**한다(측정 조건 차이가 설명돼 있지 않다). KPI 요약 표는 3초를 채택해 §B-1과 어긋난다.
2. **재생 도달률 목표 충돌** — 03 §B-2 ≥95% vs 01 §A-4 ≥98%(영역 2-3과 동일 항목).
3. **국내 법정 접근성 기준 미참조** — 「장애인차별금지 및 권리구제 등에 관한 법률」과 국가표준 KWCAG 2.2(한국형 웹 콘텐츠 접근성 지침)가 03에도 07에도 없다. WCAG 2.2 AA를 바닥선으로 삼은 것은 실무적으로 타당하지만, 국내 의무 기준과의 매핑이 없으면 **컴플라이언스 근거로 쓸 수 없다**(예: 국내 지침의 자막·수어·색각 관련 항목은 WCAG와 요구 형태가 다르다).
4. **`rem` 전환의 기술적 실현 경로 부재 (03 §A-1)** — "`px` 고정이 아니라 `rem` 기반으로 전환"을 선결 조건으로 걸었으나, react-native-web은 RN 스타일의 숫자를 px로 변환하므로 `rem` 사용은 웹 전용 스타일 레이어나 `PixelRatio`/CSS 변수 우회를 요구한다. 03 리스크 8번이 "디자인 토큰 승격을 선행 작업으로 배치"라 했지만 **02 §B의 수정 대상 목록에도 08 W0~W4 일정에도 디자인 토큰/스타일 레이어 작업이 없다** — 담당(웹 프론트엔드 리드)은 있으나 일정이 없는 액션이다.
5. **패널 테스트의 예산·사례비 부재** — 16~24명 × 3회차 = 최대 72세션의 모더레이터 인시·참가 사례비·교통비가 어느 문서에도 없다(05 G절 체크리스트에도 없음). 06은 CS 도구 비용을 $50 단위까지 산정했는데 대조적이다.
6. **"치명적 접근성 결함 0건" 게이트의 판정 기준 부재** — 예시("글자 안 보임, 버튼 못 누름")만 있고 무엇이 치명인지의 정의·판정 주체가 없다. 게이트는 판정 규칙이 있어야 게이트다.

**9.5 도달을 위한 수정 지시**

- TTFF를 단일 정의로 확정하라: "정의 = 카톡 인앱 웹뷰에서 링크 탭 → 영상 첫 프레임 렌더. 목표 = 4G p75 ≤ 3초 / 상한(패널 과업 성공 판정) ≤ 8초". 03 §B-1·§B-2·KPI 표와 02 §C를 이 값으로 통일하고, 02는 03을 인용만 하도록 바꿔라.
- 재생 도달률 목표를 01과 통일하라(영역 2 지시와 동일).
- 03 §A-1 표에 "국내 기준" 열을 추가해 KWCAG 2.2 대응 항목을 매핑하고, 07 §3에 "웹 접근성 법정 의무(장애인차별금지법·KWCAG)" 절을 신설해 적용 대상 여부·담당·트리거를 판정하라.
- 03 §A-1의 `rem` 항목에 실현 경로를 명시하라(예: "웹 빌드에 한해 `packages/ui`가 CSS 변수 기반 타이포 스케일을 노출하고 RN 측은 `Platform.select`로 분기"). 그리고 02 §B 수정 대상에 "디자인 토큰 레이어(`packages/ui` 승격)"를, 08 W1 선행 작업에 같은 항목을 추가해 일정에 실체를 부여하라.
- 03에 패널 운영 예산 표(회차당 인원×사례비×회차 + 모더레이터 인시)를 넣고 05 G절 체크리스트에 비용 항목으로 반영하라.
- 03 §B-1에 "치명적 접근성 결함"의 정의를 넣어라(예: "모더레이터 개입 없이는 과업을 완료할 수 없게 만드는 결함, 또는 A-1 수치 기준을 위반하는 컴포넌트"). 판정 주체(모더레이터+웹 프론트엔드 리드 합의)와 기록 양식도 지정하라.

### 영역 7. 라이브 안정성 — **9.0**

**인정하는 강점**: 04는 이 계획의 기술 문서 중 가장 냉정하다. ⓐ §0에서 구현 완료/미구현을 ✅❌로 갈라 **CF Stream 실연동이 미구현**이라는 최대 공백을 첫 화면에 노출했다. ⓑ §B 서두 콜아웃 — "CF Stream simulcast는 단일 소스 파생이므로 CF가 죽으면 YouTube·Facebook도 함께 죽는다. 'YouTube 링크로 유도' 폴백은 시나리오 ②에 **원리적으로 무효**" — 는 근거 없는 낙관을 스스로 차단한 모범 사례다. ⓒ SLO 7종에 측정식과 근거가 있고, 인용한 코드 상수가 실측과 **전부 일치**한다(`LIVE_CHAT_RATE_CAPACITY=5`, `LIVE_CHAT_RATE_REFILL_MS=2000`, `LIVE_COMMENT_POLL_INTERVAL_MS=3000`, `LIVE_COMMENT_BATCH_MAX=50` — `services/api/src/config/env.schema.ts:80-85`). ⓓ 시나리오 7종 각각에 감지 방법·정량 임계치·폴백·복구 절차·담당이 있고, ⑥(DCP 공존)은 모듈 의존 관계로 "구조적으로 무관"을 논증했다. ⓔ 리허설 T-60~T-0, 스트림 키 1세션1키 정책, 백업 회선 2종 구분, 용량 계획의 병목 분석("시청 규모가 아니라 채팅 참여율이 제온 부하의 실질 변수")이 모두 근거 기반이다. ⓕ §G가 계측 미구축을 정직하게 인정했다.

**감점 사유**

1. **생존 범위의 사실 오류 (04 §B④)** — "죽는 것은 **api 의존 기능뿐**: 신규 세션 조회·로그인·채팅·프롬프터·업로드/처리"라고 열거하면서 **VOD 피드와 재생 서명 URL 발급을 빠뜨렸다**(`GET /v1/feed`·`GET /v1/feed/:id/playback` 모두 api). 또 라이브 신규 진입자도 `GET /live/sessions/:id`로 `hlsPlaybackUrl`을 받아야 하므로 "사전 공지된 카톡 링크/직접 URL로 유도"만으로는 재생이 시작되지 않는다(웹앱이 api를 호출한다). 08 §B 매트릭스를 승계한 결과 오류도 함께 승계됐다.
2. **SLO와 트리거 사이의 계측 단절 (§G ↔ §A ↔ 08 §C)** — SLO 6개 중 5개가 "미구축"이고 계측 구축 시점은 "첫 3회 실 방송 이후 우선순위 재평가"라는 정성적 문구다. 그런데 08 §C 클라우드 전환 트리거("라이브 방송 중 장애 2회", "다운타임 월 4시간 초과")와 05 §C ②(정지시간 월 10시간)가 모두 측정치를 전제한다. **측정 수단이 없으면 트리거는 발동하지 않는다.** "수기 기록으로 대체"는 가용성(SLO#1)·시작 성공률(#2)까지는 가능해도 지연 SLO(#4~#7)에는 불가능하다.
3. **첫 방송 게이트에 조달 항목이 빠짐** — R10(CF Stream 미연동)만 "완료 전 첫 실 방송 개시 금지"라는 게이트를 가진다. R1(현장 백업 회선)·R12(제온 LTE 백업 라우터)·R2(Tier-1 이중 인코더)는 모두 **미조달/미결정**인데 트리거가 "장애 발생 시"·"의사결정 대기"여서 사전 조달을 강제하지 않는다. §C 리허설 T-50은 백업 회선 점검을 요구하는데, 조달되지 않은 장비를 점검하라는 절차가 된다.
4. **부하테스트 트리거가 예측 불가 조건에 걸림 (R11)** — 트리거는 "2,000명 이상 방송 확정 시"인데, **동시접속을 사전 예측하는 수단이 문서 어디에도 없다**(카톡 친구 수 → 동시 시청 전환율 가정도 없음). 예측이 불가능하면 이 트리거는 사후에만 발동한다.
5. **위임 수신 실패 — 라이브커머스 인프라 (01 부록 → 04)** — 01 부록 의존성 표는 "C-4 라이브커머스 이벤트(경매·특가) 인프라 → 04"를 위임했으나 **04에 라이브커머스 관련 서술이 한 줄도 없다**. 라이브 중 결제 폭주·재고 동시성·구매 링크 장애는 라이브 안정성의 일부이며 05 §A-1의 매출 1축이 여기 걸려 있다.
6. **웹 피벗 고유 리스크의 얇음** — 이 문서는 웹 피벗 계획의 일부인데, 웹 전환이 라이브에 만드는 고유 리스크가 R13(hls.js 재생 실패) 하나뿐이다. 누락: ⓐ 모바일 브라우저 백그라운드 전환·화면 잠금 시 socket.io 연결 종료 → 방송 종료 직후 대량 재연결(thundering herd), ⓑ 카카오 인앱 웹뷰에서의 WS 연결·HLS 재생 동작(02 §C는 인앱 브라우저를 "1순위 실사용 환경"으로 규정했는데 04의 리허설·시나리오에는 없다), ⓒ 탭 다중 개방 시 중복 소켓.

**9.5 도달을 위한 수정 지시**

- 04 §B④의 "죽는 것" 목록에 **VOD 피드·재생 서명 URL 발급**과 **라이브 세션 메타 조회(신규 진입자의 hlsUrl 획득)**를 추가하고, "제온 다운 시 신규 시청자는 라이브도 VOD도 시작할 수 없다"를 명시하라. 그 위에서 완화책을 하나 이상 정의하라(예: 방송 시작 시 CF HLS URL을 카톡 공지에 직접 포함해 api 없이 재생 가능한 우회 경로 확보 — 담당: 센터 운영, 트리거: 헬스체크 3회 연속 실패).
- §G에 계측 구축의 **최소 세트와 기한**을 못박아라(예: "첫 실 방송 전까지 SLO#1·#2 수기 대장 양식 확정 + `status_transition_logs` 주간 집계 스크립트. 3회 방송 후 4주 내 SLO#4·#5 서버 타임스탬프 로깅"). 08 §C·05 §C ②의 트리거 옆에 "측정 원천"열을 추가해 계측 미구축인 트리거를 표시하라.
- §H에 "첫 실 방송 개시 게이트" 절을 신설해 R10 외에 **R1(현장 백업 회선 1세트 조달 완료)·R12(제온 LTE 백업 라우터 도입 또는 미도입 리스크 수용 서명)·R2(Tier-1 이중 인코더 도입 여부 결정 완료)** 를 게이트 항목으로 올려라. 미충족 시 무엇을 축소하는지(예: 첫 방송은 Tier-1 지정 없이 진행)도 함께 적어라.
- R11의 트리거를 예측 가능한 선행 지표로 바꿔라(예: "지사 합산 카톡 채널 친구 수 × 과거 최고 동시접속 전환율 ≥ 2,000명이 예측되는 시점" 또는 "직전 3회 방송의 최고 동시접속이 500명 초과"). 전환율 추정 방법을 §E에 한 문단으로 정의하라.
- 04에 "§B-⑧ 라이브커머스 이벤트 부하(경매·선착순 특가)" 시나리오를 신설하거나, 01 부록의 위임 대상을 05로 변경하고 05에 결제·재고 동시성 리스크를 추가하라. 어느 쪽이든 **위임이 수신됐음이 문서에서 확인 가능해야 한다.**
- §B에 웹 고유 시나리오를 추가하라: "⑧ 클라이언트 대량 재연결(백그라운드 전환·탭 종료 후 복귀)" — 감지(동시 `live.join` 급증), 완화(재연결 지수 백오프·`REDIS_URL` 사전 설정), 담당, 트리거. §C 리허설 T-30에 "카카오 인앱 웹뷰 실기기에서 HLS 재생 + 채팅 송수신 확인"을 필수 항목으로 추가하라.

### 영역 8. CS 구축 — **8.2**

**인정하는 강점**: "고령층은 전화, 그 외는 카카오톡"이라는 설계 원칙(06 서문)이 신규 도구 도입을 최소화하면서 실제 사용자 행태와 맞물린다. 채널 4종에 대상·운영 주체·응답 SLA가 모두 붙어 있고, 전담 CS 채용 트리거(월 300건 또는 SLA 위반율 20%가 2개월 연속)·헬프데스크 승격 트리거(월 300건)·회선 증설 트리거(월 200통)가 전부 수치다. "대장 없는 CS 금지"를 원칙으로 세우고 월간 리포트가 대장 기반이라 미기록이 드러나는 **구조적 강제**를 설계한 점이 좋다. 비용도 ≈0 / 월 $50로 산정돼 있다.

**감점 사유**

1. **운영시간이 편성과 충돌 (06 §A ↔ CLAUDE.md §2 ↔ 01 §C-5)** — 전화는 "평일 09~18시"인데 라이브는 **토·일**이고, 06 §C⑤는 "방송 중 즉시" 대응을, §E는 "라이브 중 클레임 폭주"를 리스크로 든다. **주말 CS 당직 체계가 없다.** "방송 중 라이브 핫라인 겸용"이라는 단서가 있으나 누가 주말에 그 회선을 받는지, 그 시간의 근무·수당이 어떻게 되는지 없다.
2. **1인 겸임의 물리적 가능성 미검증** — 채용 트리거는 월 300건(영업일당 약 14건)인데, 그 부하를 지는 센터 운영자 1명은 동시에 04 §C 리허설 T-60~T-0의 절차 담당, §D Runbook의 상태 전이 API 호출자, 채팅 모더레이터, 05 §F-3의 라이브커머스 진행 보조까지 겸한다. **방송 중에는 CS 1선을 수행할 수 없는 시간대가 구조적으로 존재**하는데 그 공백의 대체자가 지정되지 않았다.
3. **4시간 SLA의 실현 근거 없음 (06 §A ↔ §E 1행)** — 지사 카톡 채널 1선의 첫 응답 SLA는 영업일 4시간인데, 같은 문서 §E가 "지사 담당자의 CS 방치(**휴무 이력 있는 조직**)"를 리스크로 인정한다. 완화책은 "주 1회 전수 점검, 48h 무응답 시 센터 대행"이라 **48시간을 허용하는 사후 장치**여서 4시간 SLA를 지키는 수단이 아니다. SLA 준수율 KPI ≥90%의 달성 경로가 비어 있다.
4. **비용 산정에서 인건비 제외 (06 §A "비용")** — "추가 비용 ≈ 0"은 도구 비용만이다. CS가 요구하는 인시(월 300건 × 처리 시간 + 주말 당직)가 05 §B-3 인건비 가정(센터 운영 0.5인)과 연결되지 않았다. CS를 0.5인의 잔여 시간으로 감당한다는 주장이 검증되지 않았다.
5. **도구 마이그레이션 계획 부재** — "월 300건 초과 시 헬프데스크 도구 도입 검토"라고만 되어 있고, 스프레드시트 대장 → 헬프데스크 전환 시의 **이력 이관·컬럼 매핑·이중 운영 기간**이 없다. 대장이 VOC 루프(§D)의 유일 원천이므로 이관 실패는 지표 단절로 직결된다.
6. **체크리스트에 기한 부재 (06 §F)** — 7개 항목 중 담당·기한이 붙은 것이 없다(FAQ 20문항 작성은 §A 표에서 "기획(PM), 분기 갱신"으로만 확인 가능). 다른 문서들이 트리거·기한을 붙인 것과 대비된다.
7. **문서 밀도** — 06은 7.8KB로 8개 문서 중 최소인데 루브릭 영역 3개(8·9·10)를 담당한다. 특히 CS 인력의 교육·이직·백업(단일 담당자 부재 시)이 전혀 다뤄지지 않는다.

**9.5 도달을 위한 수정 지시**

- 06 §A에 **주말·방송 시간대 CS 운영표**를 신설하라: 토·일 방송 시간 ±1시간의 1선 담당(예: 지사 담당자 로테이션), 전화 착신 전환 규칙, 방송 중 센터 운영자가 CS를 받을 수 없는 구간의 대체자, 수당·보상 방식.
- 06 §A 인력 계획에 **역할 겸임 매핑표**를 추가하라(시간대 × 역할 × 담당자). 04 §C 리허설 시간대에 CS 1선이 비는 것을 표에서 드러내고 대체자를 지정하라. 05 §B-3 인건비 가정과 이 표가 서로를 인용하게 하라.
- 지사 4시간 SLA를 실현 수단과 함께 재작성하라: 예) "지사 담당자는 카톡 채널 알림을 상시 수신(스마트폰 푸시 필수 설정), 미응답 2시간 시점에 센터 대장이 자동 리마인드(수동 점검이면 하루 2회 정시 점검), 4시간 초과 시 센터가 즉시 대행". 또는 SLA를 지사 실행 가능 수준(영업일 1일)으로 낮추고 긴급 유형만 4시간으로 분리하라.
- 06 §A "비용"에 인건비 환산 행을 추가하라(월 300건 × 평균 처리 15분 = 75시간/월 등). 05 §B-3에 이 값을 반영하라.
- 06 §A 티켓 대장 항목에 "헬프데스크 이관 계획: 컬럼 매핑표 사전 작성, 2주 이중 운영, 과거 3개월 이력 이관"을 추가하라.
- 06 §F 체크리스트 7항목 전부에 담당과 기한(또는 트리거)을 붙여라.
- 06에 "CS 담당자 부재(휴가·이직) 시 백업 지정 및 인수인계 절차" 한 항목을 추가하라.

### 영역 9. 소통창구 관리 — **8.6**

**인정하는 강점**: 06 §B의 대원칙("시청자가 라우팅을 고민하게 하지 않는다 — 어느 창구로 들어와도 접수한 쪽이 기록하고 내부에서 이관한다")은 소규모 조직에서 실제로 작동하는 설계다. 라우팅 다이어그램이 외부 3경로·내부 2경로를 모두 그렸고, **이관해도 접수 채널로 회신할 책임은 접수자에게 남는다**는 규칙은 "시청자가 두 번 설명하는" 전형적 실패를 정면으로 막는다. 역할이 1선(지사/센터)–2선(센터장)–3선(법무)으로 계층화됐고, 내부 창구를 관제 앱 수정요청·반려로 고정하며 **"카톡 개인 지시 금지"**를 명문화한 점, 주간 편성회의에 VOC를 고정 안건으로 넣은 점이 좋다. B2B 문의를 센터장 단일 창구로 못박아 01·05와 연결한 것도 정합적이다.

**감점 사유**

1. **이관의 시간 규율 부재** — 접수자 회신 책임은 지정됐으나 **이관 소요 시간 목표가 없다**. §A의 4시간 첫 응답 SLA가 이관 케이스(지사 접수 → 센터 처리)에도 적용되는지, 아니면 이관 후 시계가 리셋되는지 규정되지 않았다. 이관은 SLA가 새는 대표적 지점이다.
2. **라이브 채팅 유입 경로의 접수 책임 미지정** — "라이브 채팅 중 문의 → 프롬프터로 아나운서 인지 → 방송 중 답변 또는 종료 후 센터 접수"에서, 다른 경로가 모두 "접수자가 대장에 기록"으로 책임자가 있는 것과 달리 **이 경로만 기록 주체가 없다**. 방송 중 답변으로 종결된 건이 대장에 남지 않으면 VOC 루프(§D)에서 통째로 누락된다.
3. **출연자·판매자 창구 부재** — 소통창구를 "고객↔방송국"으로 정의했으나, 실제 분쟁 당사자는 **출연자(초상권 삭제 요청 — §C①)와 판매자(커머스 분쟁 — §C③)**다. 출연자·판매자 전용 창구·담당·SLA가 없다. 05 §F-3은 "센터 스탭이 PD 역할 보조"만 언급한다.
4. **12지사 확장 시 스케일 모델 없음** — "지사 채널 문의를 센터 대장에서 **주 1회 전수 점검**"(§E)은 2지사 전제다. 12지사에서 전수 점검이 성립하는지, 지사 수 증가에 따른 창구 구조 변화(지역 매니저 계층 추가 등)가 없다. 01 §B-2 4단계가 12개월 내 신규 지사 확장을 계획하므로 이 공백은 예정된 문제다.
5. **채널 간 유입의 수집 자동화 부재** — 카톡 12채널 + 센터 채널 + 전화 + 웹 문의가 전부 **사람이 스프레드시트에 옮겨 적는** 구조인데, 누락 검출 수단이 월간 리포트뿐이다(§E가 인정). 접수 누락은 SLA 위반으로 계측되지도 않는다(대장에 없으니 위반 자체가 보이지 않는다).
6. **깨진 상호참조** — §C가 07의 절차를 인용하며 "07 §6"을 두 번 참조하나, 07 §6은 "종합 액션 체크리스트"이고 실제 근거는 §5-1(정보통신망법 임시조치)·§3-8(불법촬영물)이다. 창구 운영자가 문서를 따라가면 절차에 도달하지 못한다.

**9.5 도달을 위한 수정 지시**

- 06 §B 이관 규칙에 시간 규율을 추가하라: "이관은 접수 후 **2시간 이내**, 첫 응답 SLA 시계는 **접수 시각 기준으로 유지**(이관으로 리셋되지 않음)". §A SLA 표에 "이관 케이스 포함"을 명시하라.
- 라이브 채팅 유입 경로에 기록 책임자를 지정하라(예: "센터 운영자가 방송 종료 후 30분 내 프롬프터 수집분 중 문의성 항목을 대장에 일괄 등재"). §D VOC 리포트의 입력 원천에 이 항목을 포함하라.
- §B에 "출연자·판매자 창구" 행을 신설하라: 대상(인터뷰이·라이브커머스 판매자·배경 인물), 창구(지사 담당자 직통 + 센터 대표번호), SLA(초상권 삭제 요청은 §C① 24h 게이트 준용), 담당.
- §B 말미에 "지사 확장 시 창구 스케일 규칙"을 넣어라(예: "운영 지사 5개 초과 시 지역 매니저 계층 신설, 센터 전수 점검을 샘플링 점검 + 자동 미응답 알림으로 전환 — 결정권자 센터장, 트리거 지사 5개 초과").
- 대장 입력 누락을 계측 가능하게 하라: 카톡 채널별 월간 수신 건수(채널 관리자 통계)와 대장 등재 건수의 **대사(reconciliation)**를 월간 VOC 리포트 고정 항목으로 추가하고, 괴리율 임계치(예: >10%)를 트리거로 걸어라.
- §C의 "07 §6" 두 곳을 각각 "07 §5-1", "07 §3-8"로 정정하라.

### 영역 10. 클레임 해결 — **8.0**

**인정하는 강점**: 06 §C가 클레임을 5유형으로 나누고 각 유형에 1차 조치 SLA·처리 절차·에스컬레이션을 붙였다. ①(초상권·개인정보 삭제)의 "24시간 내 임시 비공개 → 외부 채널 전파 → 사실 확인 후 영구 삭제 또는 복원"은 순서가 정확하고, **카톡은 반자동 게시라 삭제도 수동**이라는 구조적 사실을 잡아 §E에 "삭제 체크리스트(자체·YouTube·카톡 12채널)를 대장 필수 컬럼으로 — 전 채널 확인 전 종결 불가"라는 하드 게이트를 만든 것은 이 계획에서 손꼽히는 설계다. "처리 완료의 정의 = 대장 기록 + 접수 채널 회신, 회신 없는 종결 금지"도 좋다. 07 §5-1(정보통신망법 제44조의2)·§5-2(초상권 비법정 절차)·§5-3(정산 미개입)이 법적 근거를 제공한다.

**감점 사유**

1. **깨진 상호참조 2건 (06 §C①·§C⑤)** — "정보통신망법 임시조치 절차는 **07 §6**", "불법촬영물·명예훼손 = **07 §6** 절차"라 하나 07 §6은 종합 액션 체크리스트다(실제: §5-1·§3-8). 클레임 처리는 절차 문서를 따라가는 업무인데 **참조가 목적지에 도달하지 않는다.**
2. **SLA 수치가 두 문서에서 다름 (06 §C ↔ 07 §5-1·§5-2)** — 07은 "신고 접수 → **3영업일** 내 검토", "본인 확인 후 **3영업일** 내 1차 응답"을 명세로 06에 전달한다고 썼는데, 06 §C①은 "**24시간** 내 임시 비공개"다. 더 엄격한 쪽을 택한 것이므로 모순은 아니지만, **07이 발주한 명세와 06이 채택한 값이 달라 어느 것이 운영 기준인지 문서상 판정 불가**하다.
3. **법정 절차 요소가 06에 미반영** — 07 §5-1은 정보통신망법상 ⓐ 신청인·게시자 **양쪽 통지**, ⓑ 판단 곤란 시 **30일 임시조치**, ⓒ 조치 사실 **공시**, ⓓ **약관에 절차를 미리 구체적으로 명시할 의무**를 적시했다. 06 §C에는 이 넷 중 어느 것도 절차로 들어와 있지 않다(게시자 통지·30일 임시조치·공시 모두 없음). 법정 의무가 실행 절차에서 누락된 상태다.
4. **커머스 클레임에 청약철회가 없다 (06 §C③, 07 §3-4)** — 전자상거래법 제17조의 **청약철회(단순 변심 7일)**와 소비자분쟁해결기준이 두 문서 어디에도 없다. 06 §C③은 "판매자 연결 + 무응답 3영업일 시 중재"만이고, 07 §3-4는 신고·중개자 고지·연대책임·개인판매자 신원정보만 다룬다. 환불 클레임의 **법정 기한이 계획에 존재하지 않는다.**
5. **3선(법무)의 실체 부재** — 에스컬레이션 최종단이 "법무 자문"(06)/"외부 법률자문"(07 §0)인데, **계약된 자문사·비용·회신 SLA가 어디에도 없다**. 24h 삭제 게이트와 30일 임시조치 판단이 외부 자문에 의존하는데 그 자문이 24시간 내 응답한다는 근거가 없다. 05 G절·07 §6 체크리스트에도 "법률자문 계약"이라는 항목 자체가 없다.
6. **모더레이션 정책 부재 (06 §C⑤)** — 채팅·댓글 신고의 조치는 "관제의 hide → 반복 시 레이트리밋 차단"인데, **무엇을 숨기는가의 기준(금지 표현 목록·판정 원칙)과 이용자 이의제기 절차가 없다**. 익명 채팅에서 자의적 삭제는 그 자체로 분쟁 원인이 된다.
7. **KPI 검증 수단의 약함** — "삭제 요청 24h 준수율 **100%**"(법적 리스크 직결)를 내걸었는데 측정 원천은 수기 대장이고, 같은 문서 §E가 "티켓 대장 미기록(구두 처리 관행)"을 리스크로 인정한다. 100% 주장을 뒷받침할 독립 검증(예: 콘텐츠 비공개 전환 로그와 대장 대사)이 없다.

**9.5 도달을 위한 수정 지시**

- 06 §C①·§C⑤의 "07 §6" 참조를 각각 "07 §5-1", "07 §3-8"로 정정하고, 07 §5-1·§5-2 말미에 "운영 절차는 06 §C가 원천"이라는 역방향 링크를 걸어 왕복 참조를 완성하라.
- 삭제요청 SLA를 단일화하라: 06을 원천으로 삼되 "접수 → **24시간 내 임시 비공개** → **3영업일 내** 사실 확인 및 신청인·게시자 양측 통지 → 판단 곤란 시 **30일 임시조치** 전환 및 조치 사실 공시"로 한 흐름에 통합하고, 07 §5-1·§5-2의 수치를 이 흐름으로 교체하라.
- 06 §C①에 게시자 통지·30일 임시조치·공시 3개 단계를 절차 칸에 명시적으로 추가하고, 07 §6 "첫 촬영 재개 전" 체크리스트의 이용약관 항목에 "삭제요청 처리 절차 조항(법정 의무)"이 포함됨을 상호 표시하라.
- 06 §C③에 "청약철회(수령 후 7일, 전자상거래법 제17조)" 안내·처리 절차를 신설하고, 중개자로서의 안내 의무 범위·판매자 이행 확인 방법·미이행 시 조치를 적어라. 07 §3-4에 대응 근거 절을 추가하라.
- 06 §C·07 §0에 "외부 법률자문"의 실체를 부여하라: 05 G절과 07 §6 "즉시" 목록에 "법률자문 계약(자문 범위·긴급 회신 SLA 24시간·월 비용) 체결 — 담당 PO, 트리거: 첫 촬영 재개 전"을 항목으로 추가하라.
- 06 §C⑤에 **모더레이션 정책**을 신설하라: 숨김 사유 유형(욕설·개인정보 노출·광고·명예훼손 등), 판정 주체, 숨김 사실의 발화자 고지 여부, 이의제기 경로. 07 §5-1의 "이용자가 알 수 있게" 요건과 연결하라.
- 06 KPI에 "삭제 요청 24h 준수율" 측정 방법을 명시하라(예: "`status_transition_logs`의 비공개 전환 타임스탬프 ↔ 대장 접수 시각 월간 대사, 대장 미기록 건은 위반으로 계상").

### 영역 11. 법률·라이선스 — **8.6**

**인정하는 강점**: 07은 조사 밀도와 실행 가능성 모두에서 우수하다. ⓐ §0에서 사업자등록을 전 항목의 게이팅 전제로 세우고 §6 체크리스트를 트리거별(즉시 / 사업자등록 이후 / 첫 촬영 전 / 스토어 제출 전 / 커머스 개시 전 / B2B 착수 전 / 성장 마일스톤 / 상시)로 정렬해 **바로 실행 가능한 형태**로 만들었다. ⓑ OSS 인벤토리가 리포 실측과 일치한다(`ffmpeg-static`·`ffprobe-static`·`fluent-ffmpeg` — `services/media-worker/package.json:21-23`; MinIO는 `infra/docker/docker-compose.xeon.yml:69-70`에 실제 존재; Redis는 `redis:7-alpine`으로 compose에 존재). ⓒ FFmpeg GPL 판단이 conveying/exec 분리/FSF FAQ를 근거로 정교하고, **GHCR 이미지 public 전환과 백엔드 재판매**라는 두 실제 노출 지점을 특정한 뒤 각각에 액션·담당·트리거를 붙였다. ⓓ MinIO AGPL을 R2 전환의 **우선순위 상향 근거**로 재해석하고 Redis→Valkey를 저비용 액션으로 제시한 것은 실무적으로 정확하다. ⓔ 언론중재법상 "언론" 지위 미보유가 초상권 면책 법리 원용 불가로 이어진다는 §3-5의 구조적 논증은 이번 조사의 진짜 발견이다. ⓕ 국내 규제 9종 전부에 "요구사항 / 현재 계획 반영 여부 / 액션 / 담당 / 기한·트리거 / 근거 URL" 6요소가 있다.

**감점 사유**

1. **개인정보 국외이전 미검토 (개인정보보호법 제28조의8)** — 영상은 초상·음성을 담은 개인정보이고, 이 계획은 그것을 **Cloudflare R2·Cloudflare Stream(해외)**에 저장·전송하며 STT는 **RTZR**, 옵션으로 **OpenAI**에 보낸다. 국외이전의 고지·동의(또는 계약 근거) 요건과 개인정보처리방침 기재 의무가 07 어디에도 없다. §4의 외부 서비스 표는 "상업적 이용·재판매 제약"만 보고 **개인정보 관점은 한 줄도 없다.** 이 계획의 인프라 결정(R2·CF Stream)이 전부 국외 사업자이므로 이는 부수적 누락이 아니다.
2. **웹 접근성 법정 의무 미검토** — 「장애인차별금지법」과 국가표준 KWCAG 2.2가 없다. 03이 고령층 접근성을 제품의 핵심 가치로 세웠고 WCAG 2.2 AA를 목표로 잡았으나, **국내 법정 기준과의 매핑을 판단할 문서가 07인데 다루지 않았다**(적용 대상이 아니라는 판정조차 없다).
3. **표시·광고 규제 미검토** — 05 §A-3(라이브 배너·상품소개 슬롯·정기 협찬)과 §A-1(라이브커머스 판매자 발언)은 「표시·광고의 공정화에 관한 법률」과 「추천·보증 등에 관한 표시·광고 심사지침」의 **경제적 이해관계 표시 의무** 대상이다. 07 §3은 원산지·식품 표시(§3-7)만 다룬다.
4. **청약철회·소비자분쟁해결기준 미검토 (§3-4)** — 통신판매업 신고·중개자 연대책임·개인판매자 신원정보 축소까지는 조사했으나, **전자상거래법 제17조 청약철회**와 소비자분쟁해결기준(농수산물 반품 등)이 없다. 커머스가 수익 1축인데 반품·환불의 법정 요건이 계획에 없다(영역 10-4와 동일 결함의 법률 측면).
5. **§1-3의 전제가 다른 문서에서 이미 폐기됨** — 07 §1-3은 "네이티브 `expo-camera` → 웹 `getUserMedia`(MediaRecorder) 전환"을 전제로 "10분 이상 연속 녹화 실기기 검증"을 **즉시 액션**에 올렸다. 그러나 01 §A-3-②·02 §A 실사표·03 §C-1은 모두 `<input type="file" capture>`(OS 카메라 위임)를 **기본 경로로 확정**하고 MediaRecorder를 보조로 강등했다. 07의 "최상위 기술 리스크"가 채택되지 않은 설계를 겨냥한다. 나아가 실패 시 대안으로 제시한 "기자 앱만 Capacitor 하이브리드화"는 02 §D-T2(쉘은 비즈니스 로직 0)·03 §D(쉘 전용 기능 금지)와 **정면 충돌**한다.
6. **선거 관련 규제 미검토** — CLAUDE.md §3-2와 01이 "정치인 게스트 대담"을 6종 콘텐츠의 하나로 명시한다. 선거기간 중 정치인 출연 방송은 공직선거법·인터넷선거보도심의 관련 검토가 필요한데(특히 §3-5 결론대로 "언론" 지위가 없다면 적용 관계가 더 복잡해진다) 07에 없다.
7. **스토어 리젝의 최종 포기 기준이 문서 간 비동기** — 02 §D 리스크 테이블은 "1차 리젝 → 플랜 B, 2차 리젝 → PWA 단독"이라는 종료 규칙을 갖는데, 07 §1-1은 "재제출까지 통상 1~2주 소요되므로 리드타임을 로드맵에 반영"에서 멈춘다. 스토어 정책 리스크의 **오너 문서인 07에 종료 조건이 없다.**

**9.5 도달을 위한 수정 지시**

- 07 §3에 "**개인정보 국외이전**(개인정보보호법 제28조의8)" 절을 신설하라: 이전 대상(영상·음성·썸네일), 수령자(Cloudflare·RTZR·OpenAI), 국가, 이전 목적·항목·보유기간, 요건 충족 경로(동의 / 계약 이행에 필요한 처리 등), 처리방침 기재 문안, 담당(PO+외부 법률자문), 트리거(개인정보처리방침 최초 공개 전). §4 표에 "개인정보 국외이전 해당 여부" 열을 추가하라.
- 07 §3에 "**웹 접근성**(장애인차별금지법·KWCAG 2.2)" 절을 신설하고 적용 대상 여부를 판정하라. 적용 시 03 §A-1 목표치와의 매핑표, 미적용 시 그 근거를 명시하라.
- 07 §3에 "**표시·광고 규제**(표시광고법·추천보증 심사지침)" 절을 신설하고, 협찬·슬롯·프리롤의 유료광고 표시 문안·표기 위치와 라이브 중 구두 고지 스크립트를 액션으로 발주하라(수신 문서: 05·06).
- 07 §3-4에 "**청약철회**(제17조, 7일)·소비자분쟁해결기준" 항목을 추가하고, 06 §C③의 절차와 상호 링크하라.
- 07 §1-3을 다시 쓰라: 제목·전제를 "`<input capture>` OS 카메라 위임(확정 기본 경로)의 실기기 검증"으로 바꾸고, 검증 항목을 실제 리스크(대용량 파일 선택 후 메모리·업로드 안정성, iOS Safari 백그라운드 중단, 카카오 인앱 웹뷰에서 `capture` 동작 여부)로 교체하라. 대안으로 남긴 "Capacitor 하이브리드화"는 02 §D-T2·03 §D와의 충돌을 명시하고, 채택하려면 **세 문서를 함께 개정해야 함**을 조건으로 달아라.
- 07 §3에 "선거 관련 규제(공직선거법·인터넷선거보도심의)" 절을 신설해 정치인 대담 콘텐츠의 선거기간 중 취급 기준·담당·트리거(선거일 D-120 등)를 정하라.
- 07 §1-1·§1-2에 "리젝 대응 종료 규칙"을 추가하라: "1차 리젝 → 플랜 B(구독자 전용 쉘), 2차 리젝 → iOS는 PWA 단독으로 확정하고 App Store 트랙 종료"(02 §D와 동일 문장). §6 "스토어 제출 전" 체크리스트에도 이 규칙을 넣어라.
