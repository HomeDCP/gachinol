# 03. 접근성·UX — 고령층 시청자 중심 설계

> 웹 피벗 마스터플랜의 접근성·UX 트랙. RUBRIC.md 영역 6(고령층 사용성)의 1차 근거 문서이며, 영역 5(콘텐츠 확보 용이성)의
> 공급자(기자·주민) 진입장벽 부분도 함께 다룬다. 전제·용어는 `CLAUDE.md` §2~§4(조직도·앱 3종·편성 원칙)를 따른다.
>
> 작성 기준일 2026-08-03. 코드 근거는 `apps/subscriber`, `apps/reporter` 현재 구현(Expo/React Native, 웹 전환 전)을 실측해
> 갭을 짚는다.

## 0. 왜 이 문서가 존재하는가

Gachinol의 주 시청층은 "이장·촌장·어촌계장·삼춘 세대"다(CLAUDE.md §2·§3-4). 이들은 **출연자이자 시청자**이며,
유입 경로의 사실상 전부가 **카카오톡 채널 알림 → 링크 클릭**이다(카카오는 발행 API가 없어 반자동 게시로 유입 채널
역할만 함, CLAUDE.md §2·§8). 즉 이 서비스의 성패는 "앱스토어 UX"가 아니라 **"카톡 링크를 누른 70대가 4초 안에
무엇을 보는가"**(TTFF 정의·목표치의 정본은 [02 §C 성능 예산](02-web-architecture.md#c-성능-예산-고령층-회선기기-배려) —
"카톡 링크 탭 → VOD 첫 프레임, p75 ≤ 4초(LTE·카카오 인앱 브라우저 기준)", ROUND-1-DECISIONS X4. 03은 이 정의를
인용만 하며 별도 수치를 두지 않는다)에 달려 있다. 네이티브 3앱을 웹앱으로 피벗하는 지금이, 이 기준을 코드가
아니라 계약(디자인 토큰·게이트웨이 원칙)으로 못박을 유일한 시점이다.

현재 코드 실측 기준선(갭 식별용):

| 항목 | 현재 값 | 근거 |
|---|---|---|
| 본문 글자 크기 | 16px (`typo.body`) | `apps/subscriber/src/ui/theme.ts` |
| 자막/보조 텍스트 | 13px (`typo.caption`) | 동일 |
| 제목 | 20px (`typo.title`) | 동일 |
| 디자인 토큰 성숙도 | "최소 스타일 상수 … 다음 단계에서 packages/ui 디자인시스템으로 승격 예정" (파일 상단 주석). **실측 보강(라운드 17 — EVAL-ROUND-17 수정지시 4)**: 이 `theme.ts`는 3앱에 각각 로컬 복제돼 있고(subscriber·reporter·control-center), subscriber는 값까지 분기돼 있다 — 승격 시 3파일 통합·값 정합이 필요하며, 소비측 파일 계상·2단 게이트(W1=구독자 소비 전환/W2=3앱 전면)는 02 §B·§E 1번이 정본 | `apps/*/src/ui/theme.ts` 3파일 실측(02 §B 계상과 동일 근거) |
| 터치 타깃 | 명시적 최소 크기 정의 없음(칩·버튼이 `spacing.sm`(8) 패딩 기준으로 가변) | `apps/subscriber/app/(tabs)/index.tsx` 칩 스타일 |
| 카톡 인입 후 재생까지 | 피드 목록 → 카드 탭 → `/watch/[id]` 재생 (2탭, 인터스티셜 없음) | `apps/subscriber/app/(tabs)/index.tsx`, `app/watch/[id].tsx` |
| 로그인 요구 | 없음(구독자 앱은 익명 전용, 토큰 저장소·refresh 로직 자체가 없음) | CLAUDE.md §11 "구독자 앱 Expo 스캐폴딩" 항목 |

13px 캡션·8px 여백 기준 칩은 60~80대 사용자에게는 사실상 "읽을 수 없거나 누르기 어려운" 수준이다. 아래 A~D는
이 갭을 웹 전환 시점에 어떻게 메울지를 규정한다.

## A. 고령층 시청 UX 원칙

### A-1. WCAG 2.2 AA 적용 항목 (수치 확정) + 국내 법정 기준 대응

이 프로젝트는 WCAG 2.2 AA를 **바닥선**으로 하고, 고령층 특화 항목은 AA 수치를 상회하는 자체 목표를 둔다.
아래 "국내 기준" 열은 「장애인차별금지 및 권리구제 등에 관한 법률」(장차법) 제20조(정보접근에서의 차별금지)·
제21조(정보통신·의사소통에서의 정당한 편의제공 의무)가 요구하는 접근성의 실무 척도인 **국가표준 KWCAG 2.2**
(한국형 웹 콘텐츠 접근성 지침) 검사항목에 대한 잠정 매핑이다. **이 프로젝트에 장차법·KWCAG 준수가 법적으로
강제되는지(사업 규모·업종 기준 적용 대상 여부)의 최종 판정은 07(법률·라이선스) §3의 소관**이며, 03은 그 판정과
무관하게 UX 설계상 WCAG AA를 상회하는 목표를 자체 채택한다 — 아래 표는 07의 판정 작업이 곧바로 참조할 수
있도록 WCAG↔KWCAG 대응관계를 먼저 정리한 것이다.

| 기준(SC) | WCAG AA 요구치 | Gachinol 목표치 | 적용 범위 | 국내 기준(KWCAG 2.2, 잠정 매핑) |
|---|---|---|---|---|
| 1.4.3 대비(최소) | 일반 텍스트 4.5:1, 큰 텍스트(24px 이상 또는 굵게 19px 이상) 3:1 | 본문 텍스트 **7:1**(AAA 강화 대비) 우선 적용, 최소 4.5:1 하회 금지 | 전 화면 텍스트 | 5.4 텍스트 콘텐츠의 명도 대비(4.5:1 이상 — WCAG와 수치 동일) |
| 1.4.11 비텍스트 대비 | UI 컴포넌트·아이콘 경계 3:1 | 3:1 이상, 재생 버튼·CTA는 4.5:1 | 버튼·칩·아이콘 | 국내 지침 명시 조항 없음(2.2 개정 반영 여부는 07 §3 확인) — 자체 상회 기준 유지 |
| 1.4.4 텍스트 크기조절 | 200% 확대까지 콘텐츠·기능 손실 없음 | 준수(전 텍스트 `px` 고정 금지, `rem` 기반 — 실현 경로·일정은 본 절 하단) | 전 화면 | 7.1 사용자 요구에 따른 콘텐츠 변경 |
| 1.4.10 리플로우 | 320px 폭·400% 확대에서 가로 스크롤 없이 콘텐츠 확인 | 준수 | 전 화면 | 7.1 사용자 요구에 따른 콘텐츠 변경(연계) |
| 1.4.12 텍스트 간격 | 줄간격 1.5배 등 사용자 재정의 시 콘텐츠 손실 없음 | 준수 | 전 화면 | 6.9 콘텐츠 간격(KWCAG 2.2 신설 항목) |
| 2.5.8 타깃 크기(최소) | 24×24 CSS px | **44×44pt**(Apple HIG) / **48×48dp**(Material) 하한, 인접 타깃 간 여백 8px 이상 | 전 인터랙티브 요소 | 국내 지침 미대응(WCAG 2.2 신설 SC, KWCAG 미반영) — 자체 상회 기준으로 대체 |
| 2.4.7 포커스 표시 | 키보드 포커스 시각적 식별 가능 | 준수(외부 키보드·리모컨 연결 태블릿 시청 대비) | 전 화면 | 6.2 초점 이동과 표시 |
| 3.2.4 일관된 식별 | 동일 기능은 동일 아이콘·라벨 | 준수(재생▶·닫기✕ 앱 전체 통일, 아이콘 단독 사용 금지 — 항상 텍스트 라벨 동반) | 전 화면 | 직접 대응 조항 없음(자체 채택 원칙, 국내 지침 강제 아님) |

> **주의**: 국내 지침의 자막·수어 관련 항목(예: KWCAG 5.2 자막 제공)은 WCAG의 요구 형태와 다를 수 있다(수어
> 통역 등 국내 특유 요구가 포함될 수 있음). 이 프로젝트의 자막 설계(A-3)는 현재 WCAG 1.2.2 상당만 충족하며,
> 수어 관련 의무 해당 여부는 07 §3이 별도 판정한다.

**폰트 크기 재정의 (현재 16/13/20px → 변경)**:
- 본문 최소 **18px**, 자막(캡션) 최소 **16px**(현재 13px는 하향 폐기), 제목 **22px** 이상.
- **큰 자막 모드**(토글, **기본값 OFF** — 자동 자막(캡션 표시)만 별도로 기본 ON이다. 확정 근거·B-1 정합은
  아래 A-3 참조) 시 본문 22px·자막 **22~24px**(정본은 아래 A-3 — 문서 내 다른 표기는 전부 이 값으로
  통일, ROUND-6-DECISIONS T2)·제목 26px로 스케일.
- `px` 고정이 아니라 브라우저/OS 텍스트 크기 설정에 연동되는 상대 단위(`rem`)로 전환 — 네이티브 `typo` 상수를
  웹 전환 시 `packages/ui` 승격 작업(theme.ts 주석이 이미 예고한 부채)의 **선결 조건**으로 흡수한다.

**`rem` 전환의 실현 경로·일정 (신규)**: react-native-web은 RN 스타일의 숫자 값을 기본적으로 `px`로 직역하므로
`rem`은 RN 표준 API가 아니다 — "px 고정 금지, rem 기반"은 웹 빌드 전용 스타일 레이어가 있어야 실현된다.

- **실현 경로**: `packages/ui`가 웹 빌드 한정으로 CSS 커스텀 프로퍼티 기반 타이포 스케일(`--gachinol-font-body`·
  `--gachinol-font-caption` 등)을 노출하고, 웹 엔트리(글로벌 CSS)에서 이 변수를 `rem` 단위로 주입한다.
  네이티브(iOS/Android) 빌드는 기존 숫자 상수를 그대로 쓰도록 `Platform.select('web')`로 분기해 네이티브
  경로를 무변경으로 유지한다.
- **일정**: **W1(구독자 웹) 착수와 동시에 `packages/ui` 디자인 토큰 승격을 선행 작업으로 완료**한다(구독자
  앱이 카톡 링크의 1차 노출 지점이라 최우선). **W2(기자·관제 웹) 완료 시점까지 3앱 전체 rem 전환을 마친다**
  — **위임 수신처 확정**: 이 항목을 02 §B 수정 대상·§E 체크리스트(W1 구간)와 08 §A W1 선행조건에 정식
  등재하기로 조율자가 결정했다([ROUND-2-DECISIONS Y2](reviews/ROUND-2-DECISIONS.md)). 03은 이 수치(본문
  18px+·타깃 44pt+·rem 전환 경로)의 **요구 원천**이고, 실제 등재·구현 진행 확인은 02·08 소관이다(본 문서
  범위 밖 — 02·08이 미등재 상태라면 그 자체가 02·08의 감점 사유이지 03의 책임은 아니다).
- **선후 관계 확정 — 토큰 게이트 → 패널 R1 (신규, [ROUND-5-DECISIONS U3](reviews/ROUND-5-DECISIONS.md),
  EVAL-ROUND-5 영역 6 감점 2 대응)**: 위 "W1 착수 전 완료"(아래 리스크 8과 동일 게이트)는 B-1 어르신 패널
  **R1보다 반드시 먼저 끝난다** — 08 §A 시간축 매핑표는 R1을 "W1 진행 중(§E 1번 토큰 완료 직후 ~ 4번 웹
  export 스모크 사이)"에 배치하므로, 토큰 확정 시점이 R1보다 항상 앞선다. 즉 **R1은 토큰 수치의 "사전
  검증"이 아니라, 이미 확정·배포된 토큰에 대한 조기 관측**이며, 아래 리스크 1의 "패널 R1 완료율 <90% 시
  즉시 토큰 재조정"은 그 관측에 따른 **사후 수정**으로 읽는다(B-1 회차 설명·리스크 1 트리거 셀에 동일하게
  반영, 舊 버전의 "R1=디자인 확정 전" 표현은 이 순서와 모순돼 삭제한다).

- **R1 미달 시 소급 재작업 규칙 (신규, EVAL-ROUND-10 영역 6 감점 1 대응 — [N4](reviews/ROUND-10-DECISIONS.md),
  07 §3-11과 대칭)**: 위에서 확정한 대로 R1은 사전 검증이 아니라 이미 배포된 토큰에 대한 사후 관측이므로,
  "완료율 <90%"에 따른 재조정은 그 시점에 토큰 위에서 **이미 구현 중인 화면들의 소급 재작업**을 뜻한다.
  07 §3-11은 동일 구조의 문제(KWCAG 적용 판정이 토큰 확정 후 도착하는 경우)에 이미 **2단 분리 + 지연 상한
  2주** 규칙을 신설해 뒀다 — 03 리스크 1에도 대칭으로 아래를 부여한다.
  - **① 재작업 규모 2단 분리(중대성 기준)**: 판정 주체(모더레이터+웹 프론트엔드 리드, 위 "치명적 접근성
    결함" 판정 절차와 동일한 세션 종료 후 24시간 이내 합의)가 미달 원인을 다음 두 등급으로 분류한다.
    - **경미**(개별 컴포넌트의 수치 미세 조정 — 예: 특정 화면의 패딩·폰트 크기 1~2단계 보정, 전역 토큰
      값 자체는 유지): **다음 정기 배포에 편입**한다(즉시 핫픽스를 강제하지 않아, 이미 배포된 화면 전부를
      멈추지 않는다).
    - **중대**(전역 토큰 값 자체가 기준 미달로 판정 — 예: 본문 18px 자체가 여전히 작다고 관측되거나, 동일
      결함이 복수 화면에서 재현): **즉시 토큰 재조정**하고, 변경된 토큰을 소비하는 전 화면에 소급 반영한다.
  - **② 지연 상한(2주, 07 §3-11과 동일 원칙)**: 중대 판정에 따른 소급 재작업이 **W1 단계를 2주 이상
    지연시키면**, 08 §D 리스크 테이블로 이관해 **기획(PM)이 재작업 범위 축소**(예: 구독자 웹 한정 적용 후
    기자·관제는 W2 완료 후로 이월)를 판정한다 — 무기한 소급 요구로 로드맵이 무한정 밀리는 것을 방지한다
    (07 §3-11 "②"항과 동일한 안전판).
  - **담당**: 웹 프론트엔드 리드(중대성 판정·재작업 구현), 범위 축소 판정은 **기획(PM)**. **기한**: R1
    결과 확인 **+2주** 내 위 등급 판정 및 ①의 조치 착수, 지연 임계(2주) 초과 시 즉시 08 §D 이관.

### A-2. 카톡 인입 → 원탭 재생 동선 (중간 화면 0개 원칙)

**원칙**: 카카오톡 알림 링크를 누른 순간부터 영상 첫 프레임이 뜰 때까지, 사용자의 **추가 조작을 요구하는 화면은
0개**여야 한다. 회원가입·로그인·앱 설치 유도 모달·쿠키 동의 전체화면·튜토리얼 오버레이 전부 금지.

> **쿠키 동의 전체화면 금지의 법적 지위 — 07 §3-14 판정 전까지 잠정 원칙 (EVAL-ROUND-3 영역 6 감점 1 대응)**:
> 위 "쿠키 동의 전체화면 금지"는 07 §3-14가 아직 확정하지 않은 (a)~(d) 판정(인증 쿠키·03 §B-2 이벤트 로깅의
> 온라인 행태정보 해당 여부, 05 §A-3 광고주 리포트가 집계 통계로 한정되는지)에 **종속된 잠정 원칙**이다.
> 07 §3-14가 "필수 쿠키 + 집계 통계"로 확정하면 이 원칙은 그대로 유지되고, 행태정보를 개인 단위로 광고주에게
> 제공하는 결정이 내려지면 03은 이 원칙을 재검토한다. 확정 전까지 UX 설계·배포 게이트는 위 원칙을 유지하되,
> 07 §3-14의 최종 판정이 이와 배치되면 07이 우선한다.

```
[카톡 채널 알림] → (탭) → [영상 상세/재생 화면, 큰 재생 버튼 노출] → (탭 1회) → [재생]
```

- 현재 아키텍처가 이미 이 원칙에 부합한다(공개 피드 API `GET /v1/feed/:id/playback`이 `@Public`, 익명 재생 —
  CLAUDE.md §11). 웹 전환 시 지켜야 할 것은 **회귀 방지**다: 딥링크 랜딩을 피드 목록이 아니라 **콘텐츠 상세로 직행**
  시키고(카톡 알림 링크 = `/watch/:id` 직결, 홈 피드 경유 금지), 상세 페이지 최초 렌더에 로그인·설치 관련 UI를
  절대 배치하지 않는다.
- **자동재생의 함정**: 모바일 브라우저(특히 카카오톡 인앱 웹뷰)는 소리가 있는 자동재생을 차단한다. "탭 하나로
  재생"을 지키려면 자동재생에 의존하지 말고, **첫 화면에 손가락 폭 이상의 대형 재생 버튼**(최소 64×64px, 화면
  중앙)을 항상 노출한다 — "안 눌러도 나오겠지"가 아니라 "눌러야 나온다"를 시각적으로 명확히 한다.
- **카카오 인앱 웹뷰 제약**: 카톡 내장 브라우저는 일반 모바일 브라우저와 렌더링·정책이 다를 수 있다(자동재생·
  다운로드·팝업 정책이 더 제한적). 웹 전환 QA에 **카카오톡 인앱 웹뷰 실기기 테스트**를 별도 항목으로 반드시 포함한다
  (일반 Safari/Chrome 테스트로 대체 불가).

### A-3. 자동 자막·큰 자막 모드

- **자동 자막 기본 ON**: `ai_analyses`/`Scene` 파생 캡션(현재 `apps/subscriber/app/watch/[id].tsx`의
  `CaptionedPlayer`가 이미 구현한 `selectActiveCue` 오버레이)을 웹에서도 유지하고, 자막 표시 여부를 사용자가
  끄는 것은 허용하되 **기본값은 항상 ON**이다(끄는 것도 요구사항이 아니라 옵션).
- **큰 자막 모드**: 상세 화면에 상시 노출된 토글(아이콘+텍스트 "글자 크게"), **기본값은 OFF로 확정한다**
  (EVAL-ROUND-4 D-17 대응 — 이전 A-1의 "기본값 OFF는 안 됨" 괄호 문구는 A-3·B-1·KPI와 상충하는 모호한
  표기였다). 글자 크기는 **자막 22~24px**로 확정한다(**본 절 A-3이 정본** — A-1 폰트 크기 재정의 절·실행
  체크리스트의 "20~24px" 등 상이 표기는 이 값으로 통일한다, EVAL-ROUND-6 영역 6 감점 1·ROUND-6-DECISIONS
  T2 대응). 자동 자막(캡션 표시, 위 첫 항목)과 달리 큰 자막 모드는 사용자가 **직접 발견해 켜는 옵션
  기능**이다 — 이 기본값이라야 B-1 과업 2("글씨가 작으면 크게 바꿔 보세요", 발견·조작 성공률 측정)가
  측정 가능하고, KPI "큰 자막 모드 활성 비율 = 관찰 지표"(기본 ON이면 100%에 수렴해 관찰 지표로서 의미를
  잃는다)와도 정합한다. 브라우저 `localStorage`에 선호도를 저장해 재방문 시 유지한다. 자막 배경은 현재
  `rgba(0,0,0,0.6)` 반투명(위 코드 확인)에서 큰 자막 모드 시 **불투명도 0.8 이상**으로 올려 야외 직사광선
  시청(제주 어촌·농촌 특성상 실외 시청 비중이 높음을 전제) 대비 대비를 확보한다.
- 자막 폰트는 시스템 기본 산세리프 유지(장식 서체 금지), 자간·행간은 A-1의 1.4.12 기준 준수.

### A-4. 회원가입·설치 요구 금지 (익명 시청 유지)

- 구독자 웹앱은 **로그인 개념 자체가 없다**(현재도 토큰 저장소 미보유 — 이 특성은 웹 전환의 이점이지 축소 대상이
  아니다). 라이브 채팅도 닉네임만으로 참여(`live.join` 핸드셰이크의 `auth.nickname`, JWT 불필요 — CLAUDE.md
  §11 "라이브+WS" 항목). 웹 전환 후에도 이 무회원 원칙은 **불변 계약**으로 유지한다.
- 예외: 관제 앱(센터 운영자)·기자 앱은 역할 기반 인증이 필요하므로 이 원칙 밖이다. 원칙은 **구독자(시청자) 한정**.

### A-5. 홈화면 추가(PWA) 안내 — "어르신 문구"

기술 용어(PWA, 설치, 매니페스트)를 노출하지 않는다. 톤은 "즐겨찾기"에 빗댄 익숙한 비유를 쓴다.

- **노출 시점**: 강제 팝업 금지. 영상 시청을 1회 이상 완료한 뒤, 화면 하단에 **닫을 수 있는** 작은 배너로만
  1회성 제안. 재방문 시 다시 띄우지 않는다(거절/무시 = 영구 숨김, 로컬 저장).
- **문구 예시**(확정 아님, 카피라이팅은 후속 슬라이스에서 지사 담당자 검수 필요 — **담당: 센터 운영 +
  지사 담당자 검수, 기한: W1 패널 R1 착수 전**):
  > "다음에도 카카오톡 없이 바로 보고 싶으세요? 화면 아래 [공유] 버튼을 누르고 **'홈 화면에 추가'**를 선택하시면,
  > 우리 마을방송 아이콘이 휴대폰 화면에 생깁니다."
- **iOS/Android 분기 안내 필수**(브라우저마다 조작 경로가 다름 — 하나의 문구로 뭉뚱그리면 실패):
  - iOS Safari: 하단 공유 아이콘 → "홈 화면에 추가"
  - Android Chrome: 우측 상단 점 3개 메뉴 → "홈 화면에 추가" 또는 자동 설치 배너
- **카카오톡 인앱 웹뷰에서는 이 기능이 동작하지 않는다**(공유 시트가 시스템 브라우저와 다름). 웹뷰 감지 시
  "다른 브라우저(Safari/Chrome)로 열기" 버튼을 먼저 제시하고, 그 경로로 넘어간 뒤에만 홈화면 추가 배너를
  노출한다. 이 분기 처리 누락은 "안내를 따라했는데 안 된다"는 CS로 직결되므로 D절 리스크 표에 별도 항목화.

### A-6. 재생 실패 시 어르신 화면 (폴백 UI, 신규)

재생 실패 시의 대체 시청 경로는 지금까지 [04 R13](04-live-stability.md#f-통합-리스크-테이블)(웹앱 재생
경로 장애 → YouTube 링크 전환)·[02 §D](02-web-architecture.md#d-리스크-테이블) 리스크 표에만 정의돼 있고,
구독자 UX의 정본인 03에는 **어르신이 실제로 보는 화면**이 없었다(EVAL-ROUND-2 영역 6 감점 4). 아래로 확정한다.

- **트리거**: 라이브 재생 실패([04 R13](04-live-stability.md#f-통합-리스크-테이블), 재생 오류율 >2% —
  04 수치 재사용) 또는 VOD 재생 실패(HLS manifest 오류·hls.js 예외) 공통 적용.
- **화면 문구**(기술 용어 금지, A-5와 동일 톤): "지금은 화면이 잘 안 나오고 있어요. 아래 버튼을 눌러
  다른 곳에서 봐 주세요." + 손가락 폭 이상의 큰 버튼.
  - **라이브**: [유튜브에서 보기](YouTube 링크로 즉시 전환) + [전화로 문의하기](지사 담당자 전화번호,
    B-3의 "전화 1차 채널" 원칙과 동일 — 운영 주체·응답 SLA·대장 기록은 06 §A "지사 담당자 직통 전화
    (시청자 대상)" 행(ROUND-3-DECISIONS Z4 신설)이 정본) 2버튼.
  - **VOD**: YouTube 상시 대체 채널이 없으므로(라이브 전용 폴백, 04 §B 콜아웃 참조) [다시 시도] +
    [전화로 문의하기] 2버튼만 노출한다 — 없는 대체 경로를 있는 것처럼 안내하지 않는다.
- 04는 이 트리거의 **판정·수치**(재생 오류율 임계치)를 소유하고, 03은 그 트리거가 발동했을 때 어르신이
  실제로 보는 **화면 설계**를 소유한다 — 상호 링크로 정합을 유지한다.

## B. 검증 방법

### B-1. 애월·제주시 어르신 패널 테스트 설계

MVP 우선 대상이 애월·제주시 2개 지사 부활(CLAUDE.md §11)이므로, 패널도 이 두 지사 관할 주민으로 한정해
실제 서비스 대상과 표본을 일치시킨다.

| 항목 | 설계 |
|---|---|
| 모집 인원 | 지사당 8~12명(총 16~24명), 60~80대, 스마트폰 보유자(카카오톡 사용 경험 필수 — 실제 유입 경로와 동일 조건) |
| 모집 경로 | 지사 담당자를 통한 마을회관·경로당·부녀회 네트워크 리크루팅(별도 리서치 업체 불요 — 지사가 이미 지역 신뢰 채널) |
| 회차 | **3회차**: R1 저해상도 프로토타입(**디자인 토큰 승격 완료 후** — 리스크 8 게이트 통과가 R1의 선행 조건, 화면 구현 착수 전 단계의 클릭목업으로 **이미 확정된 토큰 값**에 대한 조기 관측을 수행한다. 08 §A 시간축 매핑표상 "W1 진행 중(§E 1번 토큰 완료 직후 ~ 4번 웹 export 스모크 사이)"에 배치 — 토큰 게이트→R1 선후는 [U3](reviews/ROUND-5-DECISIONS.md) 확정, 위 A-1 참조) → R2 스테이징 빌드(**런칭 직전**, 실제 4G/카톡 환경) → R3(**런칭 +4주**) 실사용 로그+재방문 인터뷰 — R2·R3의 정확한 W단계 배치는 08 §A 신설 "W단계 ↔ 마일스톤 매핑표"(EVAL-ROUND-3 영역 6 감점 3 대응)가 정본이며, 03은 그 표의 "런칭" 앵커를 상대 시점("직전"·"+4주")으로만 인용한다 |
| 진행 방식 | 모더레이터 동석(지사 담당자 또는 리서처), 1:1, 자택 또는 마을회관, 회당 20~30분(장시간 집중 요구 금지) |
| 관찰 방법 | 화면 녹화(동의 하) + 모더레이터 관찰 기록, 개입 여부(도움 요청 횟수) 기록 |

**표본의 구조적 한계 (신규, EVAL-ROUND-7 영역 6 감점 2 대응)**: 위 모집 조건 "스마트폰 보유자(카카오톡
사용 경험 필수)"는 실제 유입 경로(카톡 채널 알림 클릭)와 표본을 일치시키기 위한 의도적 선택이지만, 그
결과 이 패널은 **이 서비스의 최대 접근성 장벽 집단을 원천적으로 배제**한다 — 01 §B-6이 식별한 "70대
이상 스마트폰 보유율 36.3%", 01 §B-2가 인용한 "고령층 약 60%가 앱 설치 실패"가 가리키는 인구다. 즉 이
패널이 전 회차 통과(과업1 완료율 ≥90% 등)하더라도 그것이 증명하는 것은 **"스마트폰과 카톡을 이미 쓰는
사람은 쓸 수 있다"**는 것이지 "고령층 전반이 쓸 수 있다"가 아니다 — 검증 설계가 이 한계를 명시적으로
인정하지 않으면 패널 결과가 과대 해석될 위험이 있다.

이 인구에 대한 검증은 패널과 별도 트랙으로 수행한다: 01 §B-6이 완화책으로 제시하는 **자녀 경유 등록·
마을회관 공용 기기 시청** 두 접점을 대상으로, B-3 지사 현장 온보딩 방문(지사당 최소 2회 방문)에
**비-스마트폰 보유자·설치 실패 경험자 대상 대면 관찰 1회**를 끼워 넣는다 — 정식 패널처럼 과업 성공률·
SUS를 집계하지 않고, 모더레이터가 "가족이 대신 눌러주는 방식"·"마을회관 공용 기기로 시청하는 방식"이
실제로 동작하는지만 정성 관찰·기록한다(치명적 결함 발견 시 위와 동일한 판정 절차로 처리). 이 관찰로도
닿지 않는 잔여 인구(대면 접점조차 없는 완전 미접근 인구)는 **이 계획에서 검증하지 않는다** — 검증 수단
자체가 없다는 것이 이유이며, 이는 축소가 아니라 명시적 판정이다.

담당: 지사 담당자(애월·제주시)+기획(PM), 시점: **B-3 온보딩 방문과 동시(런칭 시점)**, 관찰 결과는
R3(런칭 +4주) 보고에 함께 기록한다.

**과업 시나리오 (R2 기준, 실제 서비스 흐름과 1:1 대응)**:

5. (선택, 심화 — 06 §F 4번 FAQ 문항 검수의 참조 실체화, 신규 EVAL-ROUND-9 영역 8 감점 2 대응) "혹시 화면 글씨가 잘 안 보이면 어떻게 하는지, 도움말(FAQ)에서 한번 찾아봐 주세요." — 측정: FAQ 페이지 도달 여부, 해당 문항("글씨가 안 보여요" 류) 발견 여부, 문항 내용을 자기 말로 설명 가능한지(모더레이터 확인). 과업 4와 동일하게 강제 과업이 아니며 성공률 낮아도 감점 대상이 아니다 — 이 과업의 관측 결과가 06 §F 4번("FAQ 20문항 작성 — 어르신 문구 검수 = 03 패널에서 확인")이 참조하는 검증의 **실체**다(그 전까지 06의 이 참조는 03에 대응 실체가 없는 빈 참조였다).

**게이트 판정 규칙 (신규 — 표본 크기별 실패 허용치)**: 위 "≥90%"는 표본 크기에 따라 허용 실패 인원이
달라진다 — 이를 수치로 고정한다.

- **판정식**: 표본 N명 기준 과업1(원탭 재생) **실패 허용 최대 인원 = ⌊N × 0.1⌋**. 예: N=16이면 최대 1명
  실패까지 게이트 통과, N=20이면 최대 2명, N=24면 최대 2명. 이 인원을 **초과**하면 게이트 불통과(다음
  회차 착수 전 필수 수정).
- **경계값 처리**: 실패 인원이 판정식 경계의 ±1명 범위(예: N=20에서 3명 실패 = 85%, 경계 근접)에 해당하면
  **즉시 불통과로 확정하지 않고** 판정을 보류한 뒤 **다음 회차 표본을 24명으로 확대**해 재판정한다(소표본
  변동을 실제 결함과 구분하기 위함). 재판정에서도 경계에 걸리면 그때는 불통과로 확정한다.
- 과업2·3(≥70%·≥80%)에도 동일 판정식(⌊N × (1−목표비율)⌋)을 적용한다.

**부록 — SUS 한국어 문항 (고정, 표준 10문항 국문 번역 채택)**: 회차 간 비교 가능성을 위해 아래 문항 세트를
전 회차 동일하게 사용한다(Brooke 1996 원 SUS 10문항의 통용 국문 번역, 5점 리커트: 1=전혀 그렇지 않다 ~
5=매우 그렇다). 홀수 문항은 정채점(점수−1), 짝수 문항은 역채점(5−점수), 합산×2.5로 0~100 환산(표준 SUS
산식).

### B-2. 정량 지표 (실사용 로그, 런칭 후 상시 관찰)

- **재생 도달률(정본 정의 — 01 §A-4가 이 정의를 인용)**: 카톡 링크 클릭(또는 직접 URL 접근) → 첫 프레임
  재생 성공 비율. 목표 **≥ 95%**. 측정 도구: 클라이언트 이벤트 로깅(랜딩·재생 버튼 노출·탭·첫 프레임 각
  단계 타임스탬프) → 서버 집계. 게이트 여부: 배포 게이트가 아닌 런칭 후 상시 KPI.
  **"급락"의 정량 정의·담당·조치(신규, EVAL-ROUND-7 영역 6 감점 1 대응)**: 주간 이동평균이 직전 4주 대비
  **5%p 이상 하락**하거나 절대값이 **90% 미만으로 2주 연속** 관측되면 급락으로 판정한다. 담당: **웹
  프론트엔드 리드**, 트리거 확인 **+3영업일 이내** 위 "이탈 시점 퍼널"(5단계 분해)로 원인 조사에 착수한다.
  03을 이 지표의 정본으로 하고, 01 §A-4("구독자 URL→재생 성공률")는 값을 **95%로 통일**해 본 정의를
  인용하도록 갱신한다(01 갱신은 본 문서 범위 밖 — 교차 참조로 남김).
- **이탈 시점 퍼널**: 랜딩 → 재생 버튼 노출 확인 → 탭 → 첫 프레임 → 10초 이상 시청 지속. 각 단계 이탈률을
  분리 계측해 "어디서 어르신이 포기하는지"를 특정한다(총 이탈률만 보면 원인 진단 불가).
- **첫 프레임 도달 시간(TTFF)**: **정의·목표치의 정본은 [02 §C 성능 예산](02-web-architecture.md#c-성능-예산-고령층-회선기기-배려)**
  — "카톡 링크 탭 → VOD 첫 프레임, p75 ≤ 4초(LTE·카카오 인앱 브라우저 기준)"(ROUND-1-DECISIONS X4). 03은
  이 정의를 인용하며 별도 목표치를 두지 않는다(과거 버전의 "4G ≤3초"는 폐기). WiFi 조건은 4G보다 유리해
  별도 게이트를 두지 않고 참고 관찰만 한다(비게이트).
- **큰 자막 모드 활성 비율**: 관찰 지표(목표치 없음 — 높다고 좋고 낮다고 나쁜 게 아니라 "쓰이고 있는가"만 확인).
  측정 원천은 아래 "공급자·설정 측 계측" 항목이 소유한 02 §E 16번 확장 범위(토글 이벤트 로깅)다.
  **관찰 결과의 사용처(신규, EVAL-ROUND-7 영역 6 감점 3 대응)**: 목표치는 두지 않되 관찰이 방치되지는
  않는다 — 런칭 **+8주** 시점 활성 비율이 **10% 미만**으로 관측되면(A-3 토글을 발견하는 사용자가 사실상
  없다는 신호) 토글의 노출 위치·라벨을 A-3 배치 기준으로 재검토한다. 담당: **구독자 웹앱 담당 개발자**,
  판정 시점: 런칭 +8주.
- **공급자·설정 측 계측(신설, EVAL-ROUND-5 영역 6 감점 1 대응)**: **기자 업로드 위저드 완주율**·**업로드
  중단 후 재개 성공률**(KPI 요약 표)과 위 **큰 자막 모드 활성 비율**의 측정 원천은 [02 §E
  16번](02-web-architecture.md#e-실행-체크리스트-기술)이 소유한다 — **이번 라운드 02가 §E 16번의 범위를
  콘텐츠 소비 계측(재생 시작·진행률 25/50/75/100%·조회 집계)에서 업로드 퍼널 이벤트(위저드 단계 진입·이탈,
  업로드 시작/재개/완료)와 큰 자막 모드 토글까지 확장**했다(02 §B `services/api` 행 집계 엔드포인트 범위에도
  반영). 완주율 = `POST /contents` 생성 건수 대비 최종 업로드 완료 이벤트 건수의 서버 집계 비율, 재개
  성공률 = 업로드 중단 이벤트 발생 건수 대비 재개 후 완료 이벤트 건수 비율로 산출한다. 03은 이 계측을
  인용만 하며, 실제 구현 진행 확인은 02 소관이다(A-1 rem 전환 절과 동일한 위임 원칙 — 02가 미반영 상태라면
  그 자체가 02의 감점 사유이지 03의 책임은 아니다).
- **연령대 추정 CS 문의 비율**: 고령층으로 추정되는 문의("안 나와요", "글씨가 안보여요" 류 자연어 패턴) 비율
  추적. 측정 원천 = **06 §D 월간 VOC 리포트**의 유형별 집계(자연어 패턴 분류) — 이 분해를 06 §D 표준 항목에
  고정 등재하는 작업 자체는 06 소관이다(이번 라운드 06이 반영, 03은 인용만 한다).
  **담당·임계·사용처(신규, EVAL-ROUND-14 영역 6 감점 1 대응 — "큰 자막 모드 활성 비율"과 동일 원칙 적용)**:
  목표치는 두지 않되 관찰이 방치되지는 않는다 — 런칭 **+8주** 시점 이 비율이 그 시점 전체 문의 건수의
  **15% 이상**으로 관측되면(고령층 사용성 결함이 CS 부하로 전이되고 있다는 신호) 그 문의 유형이 지목하는
  화면을 A-1/A-3 배치 기준으로 재검토한다. 담당: **센터 운영자**(06 §D 월간 집계 산출) + **웹 프론트엔드
  리드**(UX 재검토 착수), 판정 시점: 런칭 +8주(큰 자막 모드 활성 비율과 동일 시점 — 두 지표를 같은
  라운드에 대조한다).

### B-3. 지사 담당자 현장 온보딩 절차

패널 테스트와 별개로, **런칭 시점의 실제 최초 사용자 온보딩**은 연구가 아니라 운영 절차로 지사 담당자가 수행한다.

1. 지사 담당자가 마을방송 재개 전 마을회관·경로당 방문 일정을 잡는다(1개 지사당 최소 2회 방문).
2. 현장에서 참석자 본인 스마트폰으로 **직접 카카오톡 채널 알림을 재현**(테스트 알림 발송 또는 실제 첫 방송 알림)해
   "탭 → 재생"을 1:1로 시연·동행한다. 화면 캡처나 원격 설명이 아니라 **본인 손으로 직접 눌러보게** 한다.

   **시연용 콘텐츠 출처 (EVAL-ROUND-10 영역 6 감점 2 신설 — 사실 정정, EVAL-ROUND-11 영역 6 감점 1·
   정합성 이슈 K-2 해소)**: 위 시연이 요구하는 "실제 첫 방송 알림"과 "테스트 알림"은 모두 **재생 가능한
   published 콘텐츠 또는 진행 중인 방송**을 전제한다 — 그 공급원(런칭 시점 최소 확보 건수·출처)의 정본은
   **08 §A 앵커 4(대외 런칭 게이트 = 시드 콘텐츠 6건, 08 소유)·01 §A-7(전환 기간 중 서비스 상태 — 구간별
   콘텐츠 출처)**다. 舊 참조("01 §A(전환 기간 중 서비스 상태)·08 §A W1 DoD(런칭 최소 콘텐츠 요건)")는
   **오조준**이었다 — 라운드 10 N1이 W1 DoD를 **기술 런칭**(TTFF 실측·OG 렌더·카카오 인앱 브라우저 실측
   등 기술 지표만 판정)으로 한정하고 콘텐츠 요건은 앵커 4(대외 런칭)로 분리해, W1 DoD 위치에는 콘텐츠
   요건이 존재하지 않는다(`grep "최소 콘텐츠" 08-rollout-transition.md` → 0건). 실체(시드 콘텐츠 6건
   게이트) 자체는 오조준일 뿐 공백이 아니며 08 §A 앵커 4·01 §A-7에 이미 신설·등재돼 있다(둘 다 grep
   재확인 완료). 03은 그 요건을 전제로 인용만 한다(A-1 rem 전환 절과 동일한 위임 원칙). **미확보 시**
   (방문 시점까지 재생시킬 published 콘텐츠가 없거나 "테스트 알림"이 무엇을 재생시키는지 정의되지 않은
   경우) 해당 지사의 온보딩 방문 일정을 **대외 런칭 게이트(시드 콘텐츠 6건) 통과 이후**로 이월한다(舊
   "W2 DoD 충족 이후"에서 재정박 — 01 §A-7 구간별 서비스 상태 표가 "대외 런칭 게이트 통과~W2(기자 웹
   가동)" 구간부터 시드 콘텐츠 6건 + 센터 자체 제작 지속분을 시청 가능으로 확정하므로, 이월 기준을
   콘텐츠가 실제로 존재하기 시작하는 시점과 일치시킨다) — 빈 피드 앞에서 시연을 강행하지 않는다.
3. 큰 글씨 인쇄 리플렛(A-5 홈화면 추가 안내 포함, 지사별 문구 검수 완료본)을 배포한다.
4. 리플렛에 지사 담당자 **전화번호**를 명시해, 웹/앱 UI 내 도움말보다 **전화 문의를 1차 채널**로 안내한다
   (고령층은 화면 내 도움말보다 사람과의 통화를 신뢰하는 경향 — 운영 주체·운영시간·응답 SLA·대장 기록 책임은
   06 §A "지사 담당자 직통 전화(시청자 대상)" 행(ROUND-3-DECISIONS Z4 신설)이 정본이며, 03은 그 채널 설계를
   그대로 인용한다).

### B-4. 공급자(기자) 사용성 검증 (신규, EVAL-ROUND-9 영역 6 감점 1 대응 — H-6, [ROUND-9-DECISIONS P4](reviews/ROUND-9-DECISIONS.md))

## C. 공급자(기자·주민) 측 UX

콘텐츠 확보 용이성(RUBRIC 영역 5)은 결국 "공급자가 얼마나 쉽게 올릴 수 있는가"로 귀결된다. 현재 기자 앱은
4단계 위저드(촬영 → 장면별 자막 → 분류 → 업로드, `apps/reporter/app/(app)/contents/new/{index,scenes,classify,upload}.tsx`)이며,
촬영 화면은 `expo-camera`의 `CameraView`로 **자체 녹화 UI**(권한 2종 요청, 녹화 중 이탈 차단 로직 포함)를 구현하고 있다.
이는 네이티브 전용 패턴이며, 웹 전환 시 그대로 가져갈 수 없다.

### C-1. 웹 촬영 플로우 단순화 (`<input capture>` 전환)

- **전환 방향**: `CameraView` 자체 구현 → `<input type="file" accept="video/*" capture="environment">`로 OS
  기본 카메라 앱을 그대로 호출. 웹은 커스텀 녹화 UI를 만들 수 없다(브라우저 표준에 없음) — 이는 **제약이자
  단순화**다. 권한 처리(카메라·마이크)를 OS가 대신하므로 현재 코드의 `ensurePermissions`류 로직이 통째로
  사라진다. **60대 기자에게는 오히려 이득**: 자체 앱 UI를 새로 배우지 않고 평소 쓰던 카메라 앱 그대로 촬영한다.
- **잃는 것 (명시적 리스크)**: 현재 `index.tsx`의 "녹화 중 이탈 차단"(`beforeRemove` 가로채기로 녹화본 유실
  방지) 같은 커스텀 세이프가드는 OS 카메라 앱 내부에서 발생하므로 웹 페이지 코드가 개입할 수 없다. 즉 **촬영
  자체의 실패는 OS 카메라 앱 신뢰도에 위임**된다. 대신 웹 페이지가 통제 가능한 지점(파일 선택 완료 후 업로드
  시작 전 이탈)에 자동 임시 저장(아래 C-3)을 건다.
- **갤러리 업로드 병행**: `capture` 속성 없는 동일 `<input type="file" accept="video/*">`를 "저장된 영상
  올리기"로 병행 제공(현재 `ImagePicker.launchImageLibraryAsync`가 하던 역할). 촬영이 서툰 사용자는 미리
  찍어둔 영상을 나중에 올리는 경로를 선호할 수 있다 — 강제 실시간 촬영만 두지 않는다.

### C-2. 장면별 자막 입력의 모바일 웹 최적화

- 현재 `scene-list-editor.tsx` 기반 자막 편집 UI는 네이티브 스크롤/키보드 회피 로직에 의존한다. 웹 전환 시
  모바일 브라우저의 가상 키보드가 뜰 때 입력창이 키보드에 가려지지 않도록 `scrollIntoView`+여유 공간 확보를
  명시적으로 구현해야 한다(네이티브에서는 OS가 자동 처리하던 부분).
  텍스트 입력 필드는 A-1 기준대로 최소 44pt 높이, 폰트 18px 이상.
- **음성 입력 보조**: 브라우저 `Web Speech API`(Android Chrome 지원)로 자막을 말로 채울 수 있게 하되,
  **iOS Safari는 이 API를 지원하지 않는다** — 플랫폼별 기능 격차를 감춘 채 버튼만 두면 iPhone 사용 기자에게
  "눌러도 안 되는 버튼"이 된다. iOS에서는 음성 입력 버튼 자체를 숨기고, **기본 텍스트 키보드 입력**으로
  대체한다(안내 문구: "이 기기에서는 음성 입력이 지원되지 않아요. 직접 입력해 주세요"). 자막 작성 자체가
  부담되는 기자·주민에게는 C-4의 **간단 모드**(자막 생략 → 지사 담당자 사후 입력)로 우회 경로를 제공한다.
  **사실 정정 (범위 결정, [ROUND-2-DECISIONS Y1](reviews/ROUND-2-DECISIONS.md))**: 서버측 STT(RTZR)를 통한
  자동 자막 생성은 이 문서의 이전 버전이 "ai-worker 기존 파이프라인"으로 전제했으나, 현재 ai-worker는
  **결정적 스텁**이며 RTZR 실 연동 코드가 없다(리포 실측, CLAUDE.md §11). 자동 자막은 08 로드맵의 **T-AI-1**
  (RTZR·실 비전 제공자 주입) 가동 **후**에나 가능한 개선이며, iOS 음성 입력 대체책의 전제가 아니다.

### C-2-1. 미성년자 피촬영자 플래그 (신규, 07 §3-3 액션 2 수신 — EVAL-ROUND-4 D-4·영역 6 감점 3 대응)

### C-2-2. 카테고리별 Scene 순서 체크리스트 UI (신규, 01 §C-1 수신 — PIVOT-PLAN §6-2 #9 대응)

### C-3. 실패 시 복구 (업로드 중단 재개)

- **사실 정정(02 §A 실사표 판정과 정합, EVAL-ROUND-4 D-9 대응)**: 현행 구현(`http-upload-service.ts`)은
  `expo-file-system/legacy`의 `FileSystem.createUploadTask` 기반이라 **웹에서 동작하지 않는다** — "웹
  `fetch`로도 동작 가능하나"라는 이전 서술은 리포 실체·02 §A 실사표("❌ 웹 미지원")와 상충하는 사실 오류였다.
  **02 §E 7번의 웹 XHR 업로더 어댑터 신규 작성**(`upload.onprogress`/`abort` 기반 진행률·취소 구현)이
  선행돼야 웹에서 presigned PUT 업로드 자체가 성립한다. 그 어댑터가 갖춰진 뒤에도 **모바일 브라우저 백그라운드
  전환**(예: 업로드 중 카카오톡 알림 확인차 앱 전환)에서 iOS Safari는 백그라운드 탭의 네트워크 요청을 일시
  정지·종료시킬 수 있다는 플랫폼 제약이 남는다. 네이티브 앱(백그라운드 업로드 태스크 가능)과 달리 웹은 이
  보장이 약하다.
- **완화**: (1) 업로드를 청크 단위로 쪼개 재개 가능한 지점을 촘촘히 두고, (2) 브라우저 종료·전환으로 업로드가
  끊겨도 **콘텐츠 초안과 로컬 파일 참조를 `IndexedDB`에 보존**해 재진입 시 "이어서 올리기"를 제안하며,
  (3) 서버측은 이미 존재하는 presigned URL 재사용 가능 여부로 재개를 지원한다. 이 셋 중 (2)는 신규 구현이
  필요한 항목으로 실행 체크리스트에 반영한다.
- 업로드 실패 화면은 "다시 시도" 버튼 하나만 크게 — 에러 메시지에 기술 용어(HTTP, 타임아웃 등) 노출 금지,
  "인터넷이 잠깐 끊겼어요. 다시 눌러주세요" 류 사용자 언어로 치환.

### C-3-1. 업로드 중 이탈 방지 (신규, 01 §A-6 수신 — PIVOT-PLAN §6-2 #4 대응)

위 C-3은 네트워크가 **끊긴 뒤의 복구**를 다룬다. 여기서 다루는 것은 그 이전 시점 — 업로드가 **정상 진행
중인데 사용자가 화면을 벗어나려는 순간**의 **사전 경고**다(01 §A-6 발주 원문: "업로드 이탈 방지 배너 +
`beforeunload` 확인 다이얼로그").

- **탭/창 닫기·새로고침**: 업로드 진행 중 `beforeunload` 확인 다이얼로그를 띄운다. 브라우저가 커스텀 문구를
  제한하고 OS 기본 문구로 대체하는 경우가 있음을 인지하고 수용한다("업로드가 끝나지 않았어요. 지금 나가면
  처음부터 다시 올려야 해요" 류 의도만 전달되면 충분).
- **페이지 내 이탈(뒤로가기·다른 탭 전환)**: 업로드 진행률 표시와 같은 자리에 **닫을 수 없는 배너**("업로드
  중입니다 — 이 화면을 벗어나지 마세요")를 상시 노출한다. 별도 컴포넌트를 새로 만들지 않고 C-3 진행률 UI에
  통합한다.
- **소유권 경계(C-2-1과 동일 방식)**: 문구·트리거 시점·노출 조건은 **03이 소유**한다. `beforeunload` 리스너
  배선과 C-3 IndexedDB 초안 보존과의 연동은 **기자 웹앱 담당 개발자 구현**이며, 03은 그 구현을 전제로 UX만
  설계한다.
- 담당: 웹 프론트엔드 리드(UX 초안), 기한: **W1 착수 전**(01 §A-6 발주 기한과 동일) — 실 구현은 기자 웹
  업로드 파이프라인 착수 시점인 **W2**에 C-3과 함께 배선한다(설계-구현 시점 분리, C-2-1과 동일 관례).

### C-4. 60대 기자용 단계 축소안 ("간단 모드")

현재 4단계(촬영→자막→분류→업로드)를 유지하되, 자막 단계를 **선택적으로 건너뛸 수 있는 "간단 모드"**를 추가한다.

**범위 결정 (STT 비의존 재설계, [ROUND-2-DECISIONS Y1](reviews/ROUND-2-DECISIONS.md))**: 이 문서의 이전
버전은 간단 모드를 "AI가 STT/장면분석으로 자동 자막 생성"에 의존하도록 설계했으나, 현재 ai-worker는
**결정적 스텁**이고 RTZR 실 STT 연동 코드가 리포에 없다(EVAL-ROUND-2 I-2·I-3 실측). 자동 자막 생성은
08 로드맵의 별도 트랙 **T-AI-1**(RTZR·비전 실 제공자 주입, W2 완료 후 우선 검토) 가동 이후에나 가능한
**개선**이지, 간단 모드 가동의 **전제 조건이 아니다**. 아래는 STT 비의존으로 재설계한 흐름이다.

- **간단 모드**: 촬영 → (자막 생략) → 분류(간이, 정확한 분류는 검수 단계에서 확정) → 업로드. 자막 작성이라는
  가장 진입장벽이 높은 단계(문해·타이핑 부담)를 촬영자 본인에게서 걷어내고, **지사 담당자(검수자)가 업로드
  완료 후 사후에 자막을 채운다**(현행 Scene 구조 그대로 — `Scene.caption` 필수 제약은 검수 단계에서 사람이
  충족시킨다, AI 자동 생성에 의존하지 않는다).

  **사실 정정 (구현 착수 시 반증됨, 2026-08-16 — 대장 #123 / EXEC-DECISIONS #34)**: 이 문서의 이전 버전은
  *"C-5 주민 임시 업로드 링크가 이미 전제하는 '지사 담당자 검수 필수' 게이트 안에 자막 작성만 함께 옮기는
  것이라 **신규 인프라가 필요 없다**"*고 적었으나 **틀렸다. 기자 경로에는 그 게이트가 없다.**
  C-5의 검수 게이트는 `origin='resident_link'` 업로드에만 걸리고, 기자가 올린 콘텐츠는 업로드 즉시 정식
  파이프라인으로 들어간다. 게다가 서버는 콘텐츠 수정을 `draft`·`revision_requested`에서만, 그것도
  **소유 기자에게만** 허용해(`EDITABLE_STATUSES` + `loadOwned`) "업로드 완료 후 사후 입력" 자체가
  **원천 불가능**했다 — 신규 인프라가 없기는커녕 서버 계약 변경 없이는 성립하지 않는 설계였다.

  **채택된 구조 (사용자 결정 2026-08-16)**: **송출 허용 + 사후 보강**. 자막이 비어도 승인·송출은 진행되고,
  자막은 `published` 전까지 언제든 채운다. 승인 홉에 자막 가드를 거는 대안(자막 미완이면 승인 차단)은
  **명시적으로 배제**했다 — 자막 부담을 촬영자에게서 걷어내려다 방송을 막으면 목적이 뒤집힌다.
  구현(T-W2-34): `PATCH /v1/contents/:id/captions`(**같은 지사 기자**·`published` 전까지·자막 필드만,
  지사 경계 판정은 주민 검수와 같은 원천을 재사용) + **발견 수단**(`captions=needed` 대기열 + 목록 첫
  화면 건수 카드). 필터와 쓰기 게이트가 같은 원천에서 파생해 "목록엔 떠 있는데 열면 거부"가 구조적으로 불가능하다.

  **자막이 빈 콘텐츠의 실측 영향**: 파이프라인 무영향(media-worker·ai-worker에 Scene 참조 0건, 주민 제보가
  이미 자막 0으로 완주 중) · 구독자는 자막 오버레이가 **렌더되지 않는다**(빈 박스·오류 없음, 사후에 채우면 복구).
  **접근성 대가는 실재한다** — 자막 없는 콘텐츠가 송출될 수 있다는 뜻이므로, A절 큰 자막 모드의 효과가
  그 콘텐츠에는 미치지 않는다. 대기열을 비우는 운영 규율이 이 설계의 전제다.
- **정밀 모드**(기존 흐름): 자막을 직접 다듬고 싶은 기자를 위해 유지. 촬영자 본인이 자막까지 완성해 검수자
  부담을 줄이는 경로다.
- 이 전환은 **주민 공급자 확대**(C-5)와도 직결된다: 자막 입력이 필수가 아니게 되면, 전담 기자가 아닌 이장·
  어촌계장 등 주민도 "찍어서 올리기"만으로 콘텐츠를 공급할 수 있는 문턱이 생긴다. 다만 지사 담당자의 사후
  자막 입력 부담이 촬영 건수에 비례해 늘어난다는 점은 리스크 9로 관리한다.
- **향후 개선(T-AI-1 가동 후, 08 소관)**: 실 STT·비전 제공자가 주입되면 지사 담당자의 사후 입력을 **AI
  초안 생성 + 검수자 교정**으로 대체해 검수 부담을 추가로 낮출 수 있다 — 이는 T-AI-1 완료 이후의 개선이며,
  그 시점 전까지는 위 사람 입력 흐름이 유일한 경로다.

### C-5. 주민 참여형 공급 경로 (콘텐츠 확보 용이성 직결) — **횡단 결정 채택 (ROUND-1-DECISIONS X5)**

RUBRIC 영역 5(콘텐츠 확보 용이성)는 "공급자 진입장벽"을 명시적으로 묻는다. 전담 기자 12명(지사당 1명 수준)만으로는
"월~금 현장 촬영"(CLAUDE.md §2 편성 원칙) 물량을 채우기 어렵다. 웹 피벗은 앱 설치 없이 **링크 하나로 접근
가능한 공급 경로**를 열 수 있다는 점에서 콘텐츠 확보 전략의 지렛대다.

> **결정 사항**: 01 §C-2가 제안했던 스키마 변경형(`resident_tip` + 기자 대행)과 03이 제안한 무인증 임시
> 링크형이 이중 설계로 충돌했던 문제(C11)는 조율자가 **03(본 절)의 임시 업로드 링크형을 단일 설계로 채택**
> 하며 해소됐다(ROUND-1-DECISIONS X5). 03은 이 기능의 **UX·제약치(만료·건수·용량·남용 방지) 정본**이고,
> `ContentOrigin` 스키마 확장·API 구현·일정 편입은 **02 §E·08 W2 체크리스트(신규 항목)가 정본**이다 — 03은
> 그 구현을 전제로 인용만 한다. 01 §C-6의 "주민 제보 비중 10%" KPI는 이 기능이 W2에서 가동된 **이후 시점
> 기준**으로 조정한다(존재하지 않는 기능에 KPI를 걸지 않는다).

  사후 입력**·확정, C-4 STT 비의존 재설계와 동일 원칙)로 진입한다.

## D. 쉘 앱·PWA 설치 전략

| 사용자군 | 설치 권장 수준 | 근거 |
|---|---|---|
| **구독자(시청자)** | **선택**(설치 유도 최소화, A-5의 비강제 배너만) | 카톡 링크 원탭 재생이 핵심 동선이므로 설치가 시청의 전제가 되어선 안 됨. 설치는 재방문 편의 향상일 뿐 |
| **기자** | **권장(통합 쉘 1개 설치 권장 — 기자 전용 스토어 트랙은 두지 않는다, 02 §D-T2)** | 반복적·업무적 사용(주 5일 촬영·업로드) — 홈 화면 아이콘 접근성이 생산성에 직결. 기자 전용 스토어 리스팅은 없으므로(D2), 통합 쉘 1개(구독자 중심 + 역할 로그인 라우팅) 설치 또는 PWA 홈화면 추가로 접근한다 |
| **센터 관제(운영자)** | **권장하되 선택**(데스크톱/태블릿 브라우저 상시 탭 운영이 실사용 패턴에 더 가까움) | 관제는 다중 정보(검토 보드·라이브 프롬프터 등)를 동시에 보는 대시보드 성격 — 브라우저 다중 탭·즐겨찾기로도 충분할 수 있음. 설치는 강제하지 않되 태블릿 단일기기 운영 지사에는 권장 |

**원칙 — 설치 없이도 전 기능 동작**:

- PWA/쉘 앱은 **점진적 향상(progressive enhancement)**이며, 어떤 핵심 플로우도 "설치해야만" 동작하게 만들지
  않는다. 구체적으로: 시청·라이브 채팅·기자 업로드·센터 승인/반려 4대 핵심 플로우 전부 **순수 브라우저 100%
  동작**을 배포 승인 기준(D 체크리스트)으로 못박는다.
- 스토어 쉘 앱(TWA/Android, WKWebView/iOS)은 **동일 웹 앱을 감싸는 배포 채널**일 뿐 별도 기능 분기를 두지
  않는다 — 쉘 앱 전용 기능이 생기면 "웹으로 못 하는 것"이 생겨 위 원칙이 깨진다. **단 하나의 의도된 예외
  (라운드 12 신설 — 07 §1-4 액션 ④ 수신, EVAL-ROUND-12 영역 1·11 감점 해소)**: 쉘(TWA·WKWebView) **UA/런치
  파라미터 감지 시 디지털 재화(후원·멤버십) 결제 동선을 비노출**하는 분기는 이 원칙의 유일한 예외로 허용한다
  (ROUND-1-DECISIONS X3·02 §D-T2 — Apple 3.1.1/Google Play Payments가 실물 재화는 웹결제를 허용하되 디지털
  재화는 IAP/Play Billing을 강제하므로, 쉘 안에서 후원·멤버십을 그대로 노출하면 스토어 리젝으로 직결된다. 이
  결정은 후원·멤버십 UI가 노출 대상으로 실재하는 시점 기준 IAP 리젝 리스크의 **유일한 실효 완화책**이다). **단,
  05 §A-4가 후원·멤버십을 이월 트랙으로 확정한 현재는 비노출 대상 UI 자체가 존재하지 않는다 — 이 게이트는
  A-4 착수(후원·멤버십 트랙 재개) 시 발동하며, 그 전까지는 구현 대상이 없다(트리거 대기, EVAL-ROUND-13 영역
  11 감점 해소·ROUND-13-DECISIONS M5 — 02 §E 11번·07 §1-4에도 동일 단서를 대칭 반영한다). 쉘 UA/런치 파라미터
  감지 로직 자체는 이 트리거와 무관하게 W3 이전 선구축 가능하다.** 이 예외는 쉘에서 기능을 **추가**하는 분기가 아니라
  IAP 규정 준수를 위해 후원·멤버십 메뉴를 **제거**하는 분기에 한정되며, 웹(비쉘) 경로에서는 후원·멤버십
  기능이 그대로 유지된다 — 구현은 02 §E 11번("쉘 UA/런치 파라미터 감지 → 후원·멤버십 메뉴 비노출 구현 및
  회귀 테스트", 담당 FE 리드, 기한 쉘 심사 제출 전 — 단 위 단서대로 A-4 착수 전까지는 이 기한이 W3 쉘 심사의
  차단 게이트로 작동하지 않는다). **그 외 기능 분기 금지 원칙은 무예외로 유지한다.**
- 카카오톡 인앱 웹뷰에서는 PWA 설치 API 자체가 동작하지 않을 수 있다(A-5) — 이 경우 설치 유도 UI를 아예
  숨기고(에러 상태로 두지 않고) 시스템 브라우저로 전환하는 경로만 제시한다.
