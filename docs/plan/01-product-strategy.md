# 01. 제품 전략 — 웹 피벗 마스터플랜

> 웹 피벗 마스터플랜의 제품 전략 챕터. 루브릭(`docs/plan/reviews/RUBRIC.md`) 영역 2(서비스 성립성)·
> 4(레거시 미디어 흡수)·5(콘텐츠 확보 용이성, 03과 공동 근거)의 1차 근거 문서다.
> 작성 기준일 2026-08-03. 인구·이용률 등 외부 통계는 출처를 각주로 표기했고, 프로젝트 자체 목표 수치는
> **"가정:"** 접두어로 표시했다 — 실사 전 잠정치이며 각 챕터의 실행 체크리스트에 검증 절차를 둔다.

## 0. 전제와 범위

### 0-1. 전환 확정사항 (본 문서의 출발점)

- 네이티브 3앱(`apps/reporter`·`apps/control-center`·`apps/subscriber`, Expo RN) → **웹앱 3종 + 스토어 쉘(래퍼) 앱**으로 피벗. 기존 로직은 Expo Web(react-native-web)으로 재사용.
- URL만 알면 언제 어디서나 접근·공유 가능 = 이번 피벗의 핵심 가치. 12개 지사가 보유한 카카오톡 채널에서 URL 클릭 → 즉시 시청.
- 백엔드 파이프라인 중 **웹 전환이 성립을 논증하는 루프**(촬영→**자동 트랜스코딩·프리뷰**→기자 승인→다채널 송출→시청)는 이미 구현·E2E 검증 완료(`CLAUDE.md` §11). **무변경.** 단, 실 STT·비전 분석(현재 `services/ai-worker`는 파이프라인 배선·`ai_analyses` 기록·추천 랭킹까지만 완료된 **결정적 스텁** — `ai_provider=stub` 기본값, `openai` 어댑터는 `NotImplementedError`, RTZR 연동 코드 부재)과 자동편집(`auto_edit`, 잡타입 상수와 media-worker 주석만 존재하는 **미구현** 기능)은 이 루프에 속하지 않는다. 리포 실체와 어긋난 종전의 "자동편집·AI 분석 구현 완료" 진술은 정정하며, 두 기능은 웹 피벗(W0~W4)과 분리된 **별도 트랙 T-AI**(T-AI-1 실 STT/비전 주입, T-AI-2 자동편집)로 08에 등재한다 — 웹 피벗은 T-AI 완료에 비의존이다(ROUND-2-DECISIONS Y1). T-AI 가동 전까지 본 문서를 포함한 계획서 전반은 "AI 자동편집"류 단정 표현을 쓰지 않고 "자동 처리(트랜스코딩·프리뷰)"와 "AI 분석(현재 스텁)"을 구분해 표기한다.
- 카카오톡 채널 = 반자동 게시(직접 발행 API 없음, `docs/infrastructure.md` §5-1), 라이브 = YouTube+Facebook 동시(§5-2).
- 조직: 제주방송센터(컨트롤타워) + 12개 지사(현재 애월·제주시 2곳 설립, 휴무 중). MVP = 2개 지사 부활.
- 센터 콘텐츠 6종(`ProgramCategory`, `packages/shared/src/content/category.ts`): 뉴스(주간뉴스 라이브)·정치인 대담·교양·지역특화 날씨예보·로컬 라이브커머스·긴급, + B2B 미디어 세일즈(콘텐츠 유형이 아닌 유통 채널).

## A. 서비스 성립성

### A-1. 파이프라인이 웹 전환 후에도 성립하는가 — 단계별 논증

핵심 질문은 "촬영→**자동 트랜스코딩·프리뷰**→기자 승인→송출→시청" 루프(구현·E2E 검증 완료 구간, Y1)가 웹으로 바뀐
뒤에도 끊기지 않는가다. 실 AI 분석(STT·비전)·자동편집(이하 9행)은 이 루프의 전제가 아니라 별도 고도화 트랙(T-AI)이며
성립 논증에 포함하지 않는다. 아래는 파이프라인을 현재 구현(네이티브)과 대조해 웹 전환 후 성립 근거를 짚는다(1~8행 =
루프 구성 단계, 9행 = 루프 밖 T-AI 대상).

| # | 단계 | 현재(네이티브) 구현 | 웹 전환 후 | 성립 근거 |
|---|---|---|---|---|
| 1 | 촬영 | `expo-camera`(CameraView.recordAsync) 인앱 녹화 + `expo-image-picker`(갤러리 선택) 이중 경로 (`apps/reporter/app/(app)/contents/new/index.tsx`) | `<input type="file" accept="video/*" capture>`로 OS 카메라 위임(기본) + `getUserMedia`/`MediaRecorder` 인앱 녹화(보조) | OS 카메라 위임 경로는 기존 갤러리 선택 경로와 사용자 흐름이 동일 — 신규 학습 부담 없음. 상세 A-3-② |
| 2 | 장면별 자막·분류 | reporter 앱 폼 UI (`Scene[]`: order·caption·description·startSec/endSec) | 동일 폼을 react-native-web으로 그대로 렌더 | 이 데이터 구조는 UI가 아니라 서버 계약(`packages/shared/src/content/content.ts`)이라 클라이언트 기술 무관 |
| 3 | 업로드 | presigned PUT, `expo-file-system` 업로드 태스크(진행률·취소) (`apps/reporter/src/upload/http-upload-service.ts`) | presigned PUT, `fetch`/XHR 업로드(진행률·취소는 XHR `progress`/`abort` 이벤트로 대체) | presigned URL 발급·완료 통지 API(`POST /contents/:id/upload-url`, `.../upload-complete`)는 클라이언트 비의존 — 무변경 |
| 4 | 트랜스코딩·프리뷰(자동편집 제외 — 9행 참조) | `services/media-worker`(BullMQ+FFmpeg, 720p 렌디션·360p 프리뷰·썸네일 — 구현·E2E 검증 완료) | **무변경** | 서버 워커, 클라이언트 기술과 완전 분리 |
| 5 | AI 분석(파이프라인 배선) | `services/ai-worker`(FastAPI) — 배선·`ai_analyses` 기록·추천 랭킹은 완료. 분석기 자체는 **결정적 스텁**(실 STT/비전 미주입, T-AI-1 대상) | **무변경**(스텁 상태 그대로 이관) | 상동. 스텁 산출물이라도 기자 검수를 전제로 노출되므로 웹 전환 자체와는 무관 |
| 6 | 기자 프리뷰 승인 | reporter 앱에서 저화질 프리뷰 재생 후 승인 | 웹 `<video>` 태그로 서명 URL 재생, 동일 승인 API 호출 | HLS/mp4 재생은 웹 표준 기능. 기존 앱도 재생 자체는 OS 플레이어 위임(RN Video 계열) — 웹 전환으로 재생 품질 저하 없음 |
| 7 | 센터 검토·추천·다채널 송출 | control-center 앱 검토 보드 + api 인프로세스 송출 워커(카카오/YouTube) | 동일 폼·API, react-native-web 렌더 | 송출 로직은 서버(`services/api`), 카카오 반자동 모델은 애초에 "담당자가 채널 관리자 앱으로 게시"라 조작 주체가 웹/네이티브와 무관 |
| 8 | 구독자 시청·라이브 채팅 | subscriber 앱, socket.io-client 채팅 | 웹 socket.io-client(동일 라이브러리, 웹 네이티브 지원) + `<video>`/HLS.js 재생 | socket.io는 웹 우선 설계 라이브러리 — 오히려 네이티브보다 웹에서의 지원 성숙도가 높음 |
| 9 | 자동편집(`auto_edit`) — **루프 밖, T-AI-2** | **미구현**. `packages/shared/src/job/job.ts`의 잡타입 상수와 media-worker의 "auto_edit 도입 시 edited_master 추가" 주석만 존재, 실제 처리 로직 없음(CLAUDE.md §11 "다음 후보 2") | 해당 없음 — 웹 전환 여부와 무관하게 아직 존재하지 않는 기능 | 이 홉은 1~8행의 성립 루프에 포함되지 않는다. 착수 여부·시점은 08에 등재되는 T-AI-2 트랙 소관이며 W2 완료 후 우선 검토(Y1) |

**결론**: 웹 전환의 성립을 논증하는 대상은 1~8행의 루프(촬영→자동 트랜스코딩·프리뷰→기자 승인→송출→시청)이며, 이 구간은
이미 구현·E2E 검증 완료다. 8단계 중 4~5·7 절반은 서버 로직이라 애초에 클라이언트 기술과 무관하고, 1(촬영)·3(업로드)·
8(재생·채팅)만 웹 고유 제약이 있다. 이 셋은 A-3에서 개별 관리방안을 갖는다. **루프 자체가 끊기는 지점은 없다** —
성립 여부는 "루프가 도는가"가 아니라 "1·3에서 얼마나 매끄러운가"의 정도 문제로 좁혀진다. 9행(자동편집)은 이 루프
밖의 별도 트랙(T-AI-2)이라 웹 전환 성립 논증에 포함하지 않는다 — `CLAUDE.md` §4가 정의한 "AI가 편집해 방송국이
송출"이라는 제품 최종 가치는 T-AI 완료 후에 성립하며, 그 전까지 본 계획은 "AI 자동편집" 같은 단정 표현을 쓰지 않는다.

웹 전환은 반대로 네이티브에 없던 유지보수를 새로 만든다 — 브라우저 매트릭스 회귀 QA(iOS Safari 15+ · Android
Chrome/삼성인터넷 최근 3버전 · 카카오 인앱 브라우저, 02 §C 기준)와 이를 지탱하는 Playwright E2E 유지, `hls.js`
어댑터 회귀, 브라우저 정책 변경(쿠키·자동재생·A2HS 정책 등) 추적이 그것이다. 가정: 이 항목들의 정기 소요를 월
20~30시간 수준(브라우저 매트릭스 회귀 1~2일 + 정책 추적 상시)으로 잠정 추정한다 — 실측 전 잠정치이며 doc 02가
이관 후 실측해 갱신한다. "9곳→1곳" 절감 주장은 이 상계 항목을 함께 읽어야 정확하며, 두 수치 모두 사전 추정치가
아직 부재하다는 한계를 공유한다(§A-4 KPI로 승격하지 않고 여기 정성 서술로만 남긴다 — 확정은 02 실측 이후). 이
위임의 수신처·수신 확인 방법은 §A-6 실행 체크리스트(전달처: 02 §E "유지보수 공수 절감·상계 실측" 항목)에 명시한다
(EVAL-ROUND-6 영역2 감점2 대응).

**"즉시 반영"의 성립 조건(신설, 영역2 감점2 대응)**: 위 "얻는 것" 표의 "앱 심사 없는 즉시 배포"·"유지보수 축소"는
PWA·TWA로 설치된 사용자에게도 배포 직후 신버전이 도달해야 실제로 성립한다. 이 성립 조건은 본 문서가 자체
정의하지 않고 **02 §D-T5 서비스워커 갱신 정책**(S3, 02 소유 — 신규 SW `skipWaiting`+`clients.claim` 즉시
활성화·HTML 엔트리 no-cache 재검증)이 단일 원천이다. 본 문서의 "즉시 반영" 주장은 그 정책이 실제로 신설됐음을
전제로 하며, 신설 여부는 §A-6 체크리스트에서 grep으로 확인한다.

### A-3. 잃는 것 — 개별 관리방안

#### ① 백그라운드 업로드

**손실 정의**: 현재 reporter 앱은 `expo-file-system`의 업로드 태스크로 진행률·취소를 관리한다(`http-upload-service.ts`).
네이티브에서는 OS 레벨 업로드 세션이 앱 백그라운드 전환 후에도 어느 정도 지속되지만(iOS `URLSession` 백그라운드 모드,
Android `WorkManager` 계열), **브라우저 탭은 백그라운드 전환·화면 잠금 시 JS 실행이 스로틀되거나 정지**되어 진행 중인
`fetch`/XHR 업로드가 끊길 수 있다. 이는 iOS Safari에서 특히 뚜렷하다.

**관리방안**:
1. **청크 분할 재개형 업로드**로 전환 — presigned PUT을 파트 단위로 여러 번 발급하거나 S3 멀티파트 업로드로 변경, 각 파트 완료 시점을 클라이언트가 로컬에 기록해 재접속 시 이어올리기. (구현은 doc 02/08에 위임 — 여기서는 **웹 전환의 필수 요구사항**으로 명시한다.) 승격 트리거는 **02 §D-T4가 단일 문장으로 소유**(본 문서는 인용): "업로드 실패율 주간 5% 초과 또는 평균 원본 크기 300MB 초과 시 멀티파트로 승격"(X6).
2. **이탈 방지 UX**: 업로드 진행 중 "화면을 벗어나면 업로드가 중단될 수 있습니다" 배너 상시 노출 + `beforeunload` 확인 다이얼로그로 실수 이탈 차단.
3. **운영 가이드**: 대용량 영상은 촬영 현장이 아닌 지사 사무실(고정 Wi-Fi) 복귀 후 업로드를 표준 흐름으로 안내 — 지사가 이미 소규모 인력 체제라 촬영과 업로드 사이 시간차가 부자연스럽지 않다.
4. **02 §D-T2로 쉘 = 순수 래퍼(WKWebView, 비즈니스 로직 0) 확정** → 네이티브 브릿지(Capacitor 등) 경로는 폐기됐다. 즉 위 1~3의 **웹 전용 완화책이 유일 경로로 확정**됐다 — "조건부 완전 해결"은 더 이상 유효한 옵션이 아니다.

**잔여 리스크**: 청크 재개형도 앱 강제 종료 시 미완료 파트는 재시작해야 한다(전체 재업로드는 아님). 완전한 네이티브 동등성은 아니나 실사용 영향은 "다시 몇 초~수십 초 대기" 수준으로 수용 가능.

#### ② 네이티브 카메라 세밀 제어

**손실 정의**: 인앱 카메라(`CameraView`)가 제공하던 노출·줌·해상도 프리셋 등 세밀 제어가 브라우저 `MediaRecorder` API에서는 제한적이다(특히 iOS Safari는 WebM 미지원·코덱 선택권 빈약).

**관리방안**: reporter 앱은 이미 촬영 경로 2종(인앱 녹화 + 갤러리 선택)을 병행하고 있다(`ImagePicker.launchImageLibraryAsync`).
웹에서는 `<input type="file" accept="video/*" capture="environment">`를 **기본 경로**로 삼는다 — 이 속성은 모바일 브라우저에서
**OS 기본 카메라 앱을 그대로 실행**시키므로, 줌·저조도·HDR 등 세밀 제어는 OS 카메라 앱에 위임되어 사실상 100% 보존된다.
브라우저 내 `getUserMedia`/`MediaRecorder` 실시간 녹화는 보조 경로로만 유지한다.

**잔여 리스크**: 브라우저 인앱 녹화에서만 가능한 실시간 프레이밍 오버레이 같은 부가 UI는 OS 위임 경로에는 없다. 다만 현재 `recordAsync` 구현도 그런 오버레이가 없는 단순 녹화라 실질적 회귀는 없음.

#### ③ 오프라인 촬영-후-업로드

**손실 정의**: 제주 산간·해안 마을은 통신 음영지역이 존재한다. 네이티브 앱은 오프라인 상태에서도 촬영본을 로컬에
쌓아두고 OS 백그라운드 재시도로 자동 업로드할 수 있으나, 웹은 이 재시도가 브라우저 생명주기에 종속된다.

**관리방안**:
1. Service Worker + 로컬 스토리지(IndexedDB/OPFS)로 촬영본을 임시 보관, 온라인 복귀 시 업로드 재개.
2. Android Chrome은 Background Sync API로 탭이 닫혀도 재시도 가능. **iOS Safari는 Background Sync 미지원** — 이 경우 "앱(탭)을 다시 열면 자동 재개"로 하향해 명시적으로 안내.
3. 운영 표준화: 오프라인 촬영은 사무실 복귀 후 업로드가 원칙임을 온보딩 시 고지(③은 ①의 Wi-Fi 우선 가이드와 사실상 동일 운영 동선으로 묶인다).

**잔여 리스크**: iOS 기자에게는 "재접속 전까지 업로드가 시작되지 않는다"는 제약을 명확히 인지시켜야 하며, 이는 doc 03의 온보딩 UX 과제로 넘긴다.

#### ④ 푸시 도달률

**손실 정의**: Web Push는 Android Chrome에서는 일반 브라우저 탭에서도 동작하지만, **iOS Safari는 16.4+에서 "홈 화면에
추가(A2HS)"한 PWA에서만** 지원한다 — 일반 탭 방문만으로는 푸시 자체가 불가능하다.

**관리방안**: 이 프로젝트는 애초에 **카카오톡 채널을 1차 유입·알림 채널로 설계**했다(`CLAUDE.md` §2 — "업로드 → 친구 알림 →
모바일 카톡에서 즉시 시청"). 따라서 웹푸시 도달률 손실은 설계상 이미 보조 채널 손실로 국한된다. 이 판단은 아래 통계로
뒷받침된다:
- 65세 이상 고령층의 메신저(카카오톡 등) 이용률 **92.6%**, 80세 이상도 **84.4%**[^messenger-elderly].
- "어르신 93%가 카카오톡을 즐기고 하루 4시간 미디어를 이용"한다는 보도(서울신문, 2025-09-30)[^kakao-elderly-daily].

즉 웹푸시보다 카카오톡 알림이 이미 더 넓은 도달을 가진 채널이며, 이는 챕터 B의 고령층 도달 전략과 정확히 같은 근거를 공유한다.
보조로 구독자 앱은 "홈 화면에 추가하고 알림 받기" 온보딩 유도(doc 03)를 둔다.

**잔여 리스크**: A2HS를 하지 않는 iOS 구독자는 웹푸시 0%다. 이는 카카오 채널이 커버하지 못하는 "웹으로 직접 URL을
방문했지만 카톡 채널 친구는 아닌" 소수 사용자에 한정된 잔여 리스크로, 챕터 B의 카톡 도달 확대가 진행될수록 자연 축소된다.

#### ⑤ 백그라운드 오디오 재생(신설, 영역2 감점1 대응)

**손실 정의**: 네이티브 subscriber 앱은 화면이 꺼지거나 다른 앱으로 전환해도(iOS `AVAudioSession` 백그라운드 모드,
Android `MediaSession`/포그라운드 서비스) 오디오 재생이 이어질 수 있다. **모바일 브라우저 탭은 화면 잠금·백그라운드
전환 시 미디어 재생이 정지되거나 화면이 켜져 있어야만 지속**된다(iOS Safari가 특히 엄격) — B-2가 인용하는
"어르신 93%가 카톡을 즐기고 하루 4시간 미디어를 이용한다"는 통계가 함의하는 "틀어놓고 듣는" 소비 패턴과 정면으로
충돌하는 손실이다.

**관리방안**:
1. **라이브**: 04 R13 폴백(연결 불안정 시 시청자에게 YouTube 앱 전환을 안내하는 경로)을 백그라운드 재생 중단
   상황에도 동일하게 재사용한다 — 지속 청취를 원하는 시청자는 백그라운드 재생을 지원하는 네이티브 YouTube 앱으로
   유도한다.
2. **VOD**: A2HS로 홈 화면에 추가한 PWA가 일반 탭보다 백그라운드 재생 제약이 완화되는지는 기기·OS 버전에 따라
   다르므로 개선 여부를 **W1 실측**으로 확인하고 결과를 이 절에 갱신한다. 실측 후 `Media Session API`(잠금화면
   재생 컨트롤 노출) 적용 여부를 브라우저 지원 범위 내에서 doc 02가 검토한다.
3. 실측 전까지는 "화면을 켜두면 재생이 유지됩니다" 수준의 정직한 안내만 제공하고(doc 03 UX), 과장된 기대를
   주지 않는다.

**잔여 리스크**: iOS Safari 일반 탭(A2HS 미설치) 사용자는 백그라운드 오디오 재생을 구조적으로 얻을 수 없다.
이는 A-3-④와 동일하게 A2HS 전환율 확대가 진행될수록 자연 축소되는 잔여 리스크다.

#### ⑥ 오프라인/저장 시청(신설, 영역2 감점1 대응)

**손실 정의**: 다운로드 후 네트워크 없이 재생하는 오프라인 시청 기능. **현행 네이티브 subscriber 앱도 이 기능을
제공하지 않는다**(서명 URL 스트리밍 재생만 지원 — `CLAUDE.md` §4·§11 어디에도 다운로드 기능 없음) — 즉 웹 전환이
새로 만드는 손실이 아니라 애초에 존재하지 않던 기능이다.

**관리방안**: 해당 없음 — 검토 결과 신규 손실이 아님을 확인하고 종결한다. 향후 오프라인 시청이 제품 요구사항으로
채택되면 웹·네이티브 양쪽 모두에서 별도 기능 개발이 필요하다는 점만 기록해 둔다.

**잔여 리스크**: 없음.

### A-4. KPI (서비스 성립성)

| 지표 | 목표 | 가정/근거 |
|---|---|---|
| 업로드 실패율(승격 트리거, 02 §D-T4 단일 문장 인용) | 주간 실패율 ≤ 5% **또는** 평균 원본 ≤ 300MB 유지 — 초과 시 즉시 멀티파트로 승격(X6) | 이 값은 목표가 아니라 **승격 발동 기준**이다. 이전 버전의 자체 KPI("1개월 ≥85%")는 02 §D-T4 트리거와 상충해 삭제 — 성공률 목표는 승격 이후 아래 값으로 대체 |

## B. 레거시 미디어 흡수 전략

### B-1. 프레임 — "개인단으로 가져온다"

레거시 미디어(지상파 지역국·지역신문)와 **기관 대 기관으로 경쟁하지 않는다.** 개별 지역 방송국은
법인·인허가·기존 시청권역을 가진 상대라 정면 경쟁은 자원 비대칭이 크다. 대신 레거시 미디어를 구성하는 세 요소 —
**시청자(개인 시청 습관)·콘텐츠(우리가 만든 것을 그들이 사감)·인력(개인 경력)** — 를 **개인 단위로 낱개 흡수**한다.
이 프레임의 성립 근거는 레거시 미디어의 "도달"이 실제로는 개인의 총합이며, 그 개인들이 이미 카카오톡이라는 우리
플랫폼과 공유하는 채널 위에 존재한다는 데 있다(아래 각주 통계).

**케이블/유선방송(SO)은 1차 흡수 대상에서 제외한다(정정, 영역4 감점2 대응)**: 종전 버전은 위 프레임에 케이블/
유선방송을 포함했으나, 실제 실행 대상(B-3 시연 대상·§B-7 컨택 리스트·B-5 KPI)은 처음부터 지상파 지역국·지역신문만
다뤄 프레임과 실행이 어긋나 있었다. 케이블 SO는 재송신·홈쇼핑 송출 수수료가 주 수익원이라 로컬 자체제작 콘텐츠를
구매하는 예산 편성이 지상파·신문 대비 구조적으로 얇고, 05 §A-3은 이미 "지역 케이블 채널 30초 스팟"을 우리 광고
단가의 CPM 비교 대상(즉 경쟁 매체)으로 다룬다 — 케이블은 이 계획에서 콘텐츠 구매자(흡수 대상)가 아니라 광고 매체
경쟁자 포지션이 실체에 가깝다는 뜻이다. 따라서 케이블은 B-3·B-4·§B-7의 능동 컨택 대상에서 제외하고, 위 세 요소
흡수 프레임은 지상파 지역국·지역신문에 한정한다. 케이블 흡수는 B2B 축이 정착된 이후 별도 재검토 대상으로 남긴다.

### B-2. ① 시청자 — 고령층 카톡 도달 전략

**왜 카톡인가**: 65세 이상 고령층의 메신저(카카오톡) 이용률은 **92.6%**, 80세 이상도 **84.4%**다[^messenger-elderly].
"어르신 93%가 카톡을 즐기고 하루 4시간 미디어를 이용"한다는 2025년 보도[^kakao-elderly-daily]는 이 연령대가 "디지털을
못 쓰는 세대"가 아니라 **"이미 카톡 위에 사는 세대"**임을 보여준다. 반면 앱 설치 자체는 고령층의 약 60%가
실패한다는 보도가 있다[^app-install-fail] — 즉 병목은 "디지털 활용력"이 아니라 **"설치라는 관문"**이며, 이는
챕터 A의 웹 전환 논거(설치 장벽 제거)와 정확히 맞물린다.

제주 인구 기준: 2025년 제주 65세 이상 인구 비중은 **19%**(전국 20.3%에 근접, 초고령사회 문턱)[^jeju-elderly-ratio].
애월읍 인구는 공개된 최신 통계 기준 **약 36,233명**(2019년, 이후 갱신치 미확인)[^aewol-pop]이다 — **이 수치는 7년
전 값이며 아래 목표 산정의 근거로 그대로 쓰지 않는다.** 최신 인구·연령 구조 실사는 §B-7 체크리스트 항목으로
등재했다(담당: 기획(PM), 기한: MVP 착수 전) — 실사 완료 후 본 절과 각주 5·6·아래 표를 갱신한다.

| 3. 확장 | 12개월 | 신규 지사 추가 시 동일 모델 복제 | 신규 지사 추가 시 동일 모델 복제 | 2단계 정착 지사의 운영 노하우를 신규 지사 온보딩 매뉴얼화 |

**시딩 개시 시점 재정박(신설, EVAL-ROUND-10 영역2 감점1 대응, A-7 참조)**: "0. 시딩" 단계의 기산점을 "MVP 착수"에서
**대외 런칭 게이트(시드 콘텐츠 6건 확보, A-7) 통과 시점**으로 교체한다 — 그 이전 구간은 카톡 채널 신규 유입을
유도하지 않는다(A-7 구간별 서비스 상태 표 참조). 이하 "1. MVP 확산"부터의 3개월·6개월·12개월 기산점은
**종전대로 MVP 착수 기준을 유지**한다 — 대외 런칭 게이트가 MVP 착수로부터 크게 지연되면 "0. 시딩"과
"1. MVP 확산" 단계가 시간축상 겹치거나 압축될 수 있으며, 그 경우의 재조정은 대외 런칭 게이트 통과 시점이
확정된 뒤 별도 판정한다(담당: 기획(PM)).

가정: 애월 Phase 2 목표(3,000명)의 분모는 "지사 관할 전체 성인 인구"(고령인구 한정 아님)로 재정의한다 — 카톡
채널 친구는 고령층 전용이 아니므로 고령인구를 분모로 쓰면 목표의 낙관/보수 여부를 판정할 수 없다는 지적을
반영했다. 고령층 도달 정도는 §B-5의 "친구 중 60세 이상 비중 ≥40%" KPI로 별도 추적한다. 제주시 목표는 §B-7
인구 실사 완료 후 확정하며, 그 전까지는 이 표의 "실사 완료 후 별도 산정"을 잠정 상태로 유지한다.

**1개월→3개월 10배 성장 구간의 산출 근거(신설)**: 표의 "1개월 100명 → 3개월 1,000명"은 지사당 +900명을
약 8주(2개월) 안에 확보해야 한다는 뜻이다. 이 구간의 유일한 채널은 오프라인 QR 등록 부스뿐이다(자녀 경유
캠페인은 위 표상 6개월 "정착" 단계부터 시작이라 이 구간에는 아직 없다). 산식(가정): 부스 운영 빈도 =
마을회관·경로당 순회 부스 주 3회 + 오일장 부스 월 6회 ≈ 월 18회(주 평균 약 4.5회) · 회당 평균 등록 인원 =
방문자 40명 × 등록 전환율 35%(§B-6 리스크 트리거 "<30%"를 웃도는 운영 목표치) ≈ 14명 · 8주간 부스 운영
≈36회 × 14명 **≈ 500명**. 이는 목표 900명의 약 56%에 그친다 — **잔여 약 400명은 초기 등록자가 본인의
카톡 지인에게 채널을 직접 공유하는 자연 확산으로 충당한다는 검증되지 않은 낙관 가정**이며, 이 갭을 감추지
않고 명시한다. §B-5 KPI 표의 "3개월 실측 후 6개월 목표 재조정" 트리거를 이 구간에도 적용해, 3개월 시점에
부스 기여분(등록 시 "어디서 부스를 통해 등록했는지" 대장 기록으로 실측 가능)과 자연 확산분을 분리 집계하고
1개월→3개월 목표 자체의 성립 여부도 함께 재판정한다.

### B-3. ② 콘텐츠 — B2B 판매의 역방향

`CLAUDE.md` §3-6은 "우리 콘텐츠를 방송3사·종편·케이블에 판매"하는 B2B를 명시한다. 이는 레거시 미디어 흡수 관점에서
뒤집어 보면 **"레거시 미디어가 우리 콘텐츠를 사감으로써 그들의 전파력이 우리 콘텐츠를 실어 나른다"**는 의미다 — 판매가
곧 흡수 채널이다.

| 레거시가 가진 결핍 | 우리가 가진 공급 |
|---|---|
| 마을 단위 초근접 취재 인력 부재(파견 비용 부담) | 12개 지사 상주 기자의 일상 취재망 |
| 로컬 소재(날씨·먹거리·축제) 제작 비용 대비 시청률 효율 낮음 | 이미 제작된 짧은 로컬 클립(장면별 자막까지 완비) |
| 고령층 지역 정서 콘텐츠(이장·촌장 인터뷰 등) 섭외 리드타임 | 지사 네트워크로 즉시 섭외 가능 |

**단계**: MVP+3개월 시점 대표 샘플 릴 3편(뉴스 소재·교양·날씨예보 각 1편) 제작 → 지역 방송사(KBS제주·MBC제주·JIBS 등)·
지역신문(제주일보·한라일보 등 온라인 클립 임베드) 편성/디지털 담당에 무상 시연 → 유상 계약 목표는 05 §E 시나리오별
수치(아래 B-5 참조, 05가 단일 원천)를 따른다. 가격·손익 구조는 doc 05 소관이며, 본 챕터는 "판매 가능한 공급
포지션"까지만 정의한다.

**출처 크레딧 필수화**: B-3의 논지("판매가 곧 흡수 채널이다 — 레거시의 전파력이 우리 콘텐츠를 실어 나른다")가
성립하려면 방송사 방영 시 출처가 시청자에게 노출돼야 한다. 크레딧 없이 소재만 팔리면 그것은 매출일 뿐 흡수가
아니며 B-3의 논지 자체가 무너진다. 따라서 B2B 계약서 표준안(05 §A-2 실행조건 4)에 **"판매 콘텐츠 방영 시 출처
크레딧(예: 제작 ○○마을방송국) 표기 의무" 조항을 필수 항목으로 명시**하도록 요구하며, 크레딧 표기가 불가한
거래처에는 단가 프리미엄 요구 또는 거절을 원칙으로 한다(B-7 체크리스트에 반영 확인 항목 등재).

**선행조건 인용(05 §A-2)**: B2B 실행은 05 §A-2가 실행 조건 1번으로 못박은 "콘텐츠 라이브러리 50건 이상 축적"을
전제로 한다. C-6 KPI(지사당 주간 업로드 3~5건 × 2지사)로 역산하면 라이브러리 50건 도달은 **첫 촬영 재개(=W2
DoD 직전, 08 §A 앵커) +약 5~8주 시점**이다.

**재정박(신설, EVAL-ROUND-10 영역5 감점1/N2 대응)**: 위 "+5~8주 시점"의 기준점을 종전 "MVP 착수"에서 **첫
촬영 재개** 시점으로 교체한다 — 종전 기준점은 C-6 재정박(§C-6 참조)과 동일한 사유(M1~M2는 08 §A 매핑표상
정의상 촬영 불가 구간)로 성립하지 않았다. 재정박 후에는 이 시점이 위 "MVP+3개월 시점 샘플 릴 제작" 착수보다
이른지 여부를 여기서 단정하지 않는다 — 첫 촬영 재개가 MVP 착수로부터 언제 발생하는지가 08 §A W2 DoD 실측
시점에 확정돼야 두 시점의 선후 비교가 가능하기 때문이다(담당: 기획(PM), 확인 시점: W2 DoD 실측 직후). 즉
이 축의 타임라인이 우연히 맞아떨어진다고 가정하지 않으며, C-6 업로드 속도와 W2 DoD 실측 시점이 함께 확정돼야
성립 여부를 판정할 수 있다는 점을 명시한다.

**컨택 경로**: 기관 대 기관 제휴 제안이 아니라, B-4에서 영입한 은퇴/프리랜서 방송인력의 **개인 네트워크**를 통한
소개 경로를 1순위로 삼는다 — 이는 B-3과 B-4가 서로를 지탱하는 구조다.

**B-4 미성사 시 대체 경로(신설, 영역4 감점 대응)**: B-3이 B-4 단일 경로에만 의존하지 않도록, B-4 파일럿 위촉이
MVP 착수 +8주 시점까지 0명이면(§B-6 "객원 인력 영입 자체 미성사" 리스크 트리거와 동일) B2B 컨택 경로를
**2순위 지자체 미디어 담당 부서 경유 소개**, **3순위 지역언론(지역신문·지역방송) 공모/협력 프로그램 경유
컨택**으로 전환한다.

### B-4. ③ 인력 — 은퇴·프리랜서 방송인력 영입

**목표**: 제주 지역 방송사(KBS제주·MBC제주·JIBS 등) 정년퇴직 또는 프리랜서로 활동 중인 아나운서·PD·카메라감독을
지사 "객원 기자/시니어 리포터" 또는 센터 "객원 아나운서"로 위촉한다.

| 단계 | 기간 | 목표 | 경로 |
|---|---|---|---|
| 파일럿 | MVP 3개월 | 애월·제주시 지사 각 1명, 총 2명 위촉 | 한국방송인총연합회 제주지회, 지역 방송사 정년퇴직자 개인 컨택, 프리랜서 아나운서 커뮤니티/블로그를 통한 **개인 단위** 접촉(기관 제휴 아님) |
| 확산 | 6개월 | 지사당 1~2명, 총 4명 | 파일럿 위촉자의 동료 추천(레퍼럴) |
| 정착 | 12개월 | 신규 지사 추가마다 1명 동반 위촉을 온보딩 표준 절차화 | — |

**시너지**: 영입된 인력은 개인 SNS·카톡 네트워크 등 **이미 구축된 개인 채널**을 가진 경우가 많다 — 영입 즉시 B-2의
시청자 시딩 효과를 겸하며, B-3의 B2B 컨택 경로도 함께 연다. 세 하위 전략(①②③)이 개별 채널이 아니라 하나의
인적 네트워크로 얽혀 있다는 점이 "개인단 흡수" 전략의 핵심이다.

**처우 원칙**: 정규 급여가 아닌 활동비 + 콘텐츠 재판매(B-3) 수익쉐어 조합. 초기엔 소정 활동비 수준으로 시작해
B2B 매출 실현 시 쉐어 비중을 높이는 단계적 구조를 제안. **위임 수신 확정(X8)**: 이 처우 원칙의 손익 검증·구체
금액은 05 §B 인건비 가정에 편입 완료됐다 — 상세 수치는 05 §B-3 참조(본 문서는 원칙만 유지, 손익 산정은 05가 소유).

**기대 공수(신설, EVAL 영역4 감점2 대응)**: 05 §B-3의 활동비 30만원/인은 그 자체로는 시급 환산이 불가능해
실현 가능성을 검증할 수 없다는 지적(30만원으로 주 10시간을 기대하면 시급 약 7천원 수준)을 반영해, 이 활동비가
전제하는 공수를 여기서 수치로 못박는다: **활동비 30만원/월 = 월 8~12시간 활동 전제**(촬영 지원 주 1회 2~3시간
+ B2B 소개 컨택 월 2건 각 1~2시간). 이는 시급 환산 시 약 2.5만~3.8만원/시간 수준으로, 정규 고용이 아닌
활동비 성격임을 감안한 자문료 수준 단가다. 이 공수 가정은 §C-7 총부하표의 "라이브커머스 방송 진행·준비" ·
"촬영·자막·업로드" 완화 효과(객원 인력이 지사 담당자 부하를 얼마나 흡수하는지)와 05 §B-3 "활동비 근거 확보
액션"에 함께 반영한다 — **담당: 기획(PM), 기한: MVP 착수 전.**

**활동비 근거 확보 액션(Y6)**: 05가 소유한 활동비 수치는 현재 시장가 비교 없이 책정된 잠정치다. 근거 확보(제주
지역 은퇴/프리랜서 방송인 2~3인 사전 의향 인터뷰 또는 유사 위촉 사례 조사)를 B-7 체크리스트에 담당·기한과
함께 등재한다 — 확보 결과는 05 §B-3에 반영되며, 예산 수치 자체는 계속 05가 단일 원천으로 소유하고 본 문서는
인용만 한다.

## C. 콘텐츠 확보 용이성

### C-1. 포맷 템플릿화 — 데이터 구조가 품질 하한을 강제한다

reporter 앱의 콘텐츠 업로드는 자유 형식 파일 첨부가 아니라 **장면 단위 구조**를 서버 계약으로 강제한다
(`packages/shared/src/content/content.ts`):

```
Content { title, category(ProgramCategory 6종 중 1), scenes: Scene[] }
Scene   { order, caption(자막, 필수), description?, startSec, endSec, thumbnailUrl }
```

이 구조는 UI 가이드가 아니라 **타입 계약**이라 우회가 불가능하다 — 기자가 "제목 없이", "장면 자막 없이" 콘텐츠를
만들 수 없다. 즉 포맷 준수가 "권장"이 아니라 "업로드 완료 조건"이며, 이것이 콘텐츠 품질 하한을 코드 레벨에서
보장하는 메커니즘이다. 웹 전환 후에도 이 계약은 무변경이므로 품질 하한은 그대로 유지된다.

**포맷 템플릿 확장 제안**: 현재 `category`는 6종(`news`·`politics_talk`·`culture`·`local_weather`·`live_commerce`·
`emergency`)으로 이미 나뉘어 있다. 이를 활용해 **카테고리별 Scene 순서 체크리스트**를 UI 레이어(doc 03)에 추가할 것을
요구사항으로 명시한다 — 예: `local_weather`는 [인사→관찰 포인트→활동 추천→마무리] 4장면 권장 순서, `live_commerce`는
[상품 소개→시연→구매 유도→이벤트 안내]. 이는 데이터 스키마 변경이 아니라 클라이언트 UI의 입력 가이드이므로
백엔드 무변경으로 구현 가능하다(doc 03에 요구사항 전달).

### C-2. 주민 참여 진입장벽 낮추기

**현재 제약**: `Content.reporterId`는 `role='reporter'`(지사 소속 유저)로 한정되어 있다(`packages/shared/src/user/user.ts`)
— 즉 지금 스키마상 "일반 주민 제보"는 정식 경로가 아니다.

**웹 전환이 여는 기회**: 웹은 "URL 하나로 촬영 참여" 구조를 저비용으로 열 수 있다 — 지사가 카톡으로 "제보 업로드"
링크를 발송하면, 주민은 앱 설치 없이 브라우저에서 촬영(A-3-② OS 카메라 위임)·업로드만 하면 된다. 다만 C-1의
Scene 구조 작성(장면별 자막)까지 주민에게 요구하면 진입장벽이 다시 높아진다.

**확정 모델(X5 — ROUND-1-DECISIONS 채택안, 03에서 제안된 무인증 임시 링크형으로 단일화)**: 이전 초안에서 본
문서가 별도로 제시했던 스키마 변경형(`resident_tip` `ContentOrigin` + 기자 대행)은 **폐기**하고, 아래 단일 설계로
확정한다 — 두 설계가 인증 모델·데이터 모델·남용 방지 방식에서 서로 달라 조율되지 않았던 문제(C11)를 해소한다.

1. **주민 제보 = 지사 담당자가 발급하는 임시 업로드 링크.** 주민은 로그인 없이 링크로 촬영·업로드(간단 모드: 파일
   업로드 + 제목 1줄, Scene 구조화는 담당 지사 기자가 검수 시 대행)한다. **STT 비의존 원칙(Y1)**: 자막·장면 설명은
   전 구간 **사람(지사 기자/검수자)이 입력**하며, 실 AI 자동 자막(STT)에 의존하지 않는다 — 현재 `services/ai-worker`는
   결정적 스텁이라 실 STT가 없기 때문이 아니라, 있더라도 검수 없는 자동 자막을 그대로 게시하지 않는다는 원칙이다.
   STT는 T-AI-1 가동 후 기자의 자막 초안 작성 부담을 줄이는 **개선**으로만 취급하며, 간단 모드·주민 링크 어느 경로도
   STT를 전제 조건으로 두지 않는다.
2. 지사 기자가 검수·장면 정리를 거쳐 정식 콘텐츠로 편입한다 — 승인 이전 단계에서 지사 기자 검토를 거치도록 기존
   워크플로우에 편입.
3. 만료·건수 제한·용량 제한·남용 방지(레이트리밋 등) 수치 설계는 **03(임시 업로드 링크 UX·정책)이 소유**하며,
   `ContentOrigin` 확장 등 스키마 작업은 **W2 범위**로 02 §E·08 W2 체크리스트에 구현 항목으로 편입한다(X5).
4. 주민 제보 콘텐츠는 인센티브와 연동해 참여를 유도한다 — **커머스 1단계(링크아웃) 정합화(Z1)**: MVP 범위의
   커머스 구현은 "상품 카드 + 외부 링크 + 클릭 계측"뿐이며 자체 포인트 원장을 구축하지 않으므로, 적립형
   "로컬 커머스 포인트" 같은 자체 정산 인센티브는 1단계에는 없다. MVP 인센티브는 상품권 추첨·우선 노출·
   시연 우선 초대처럼 백엔드 원장이 필요 없는 형태로 시작하고, 적립형 포인트는 커머스 2단계(자체 결제,
   05 §G 트리거 도달) 진입 이후 검토 항목으로 05 §G에 등재한다(doc 05 소관).

본 문서는 "왜 이 설계인가"(진입장벽 최소화, 개인단 흡수 전략과의 정합)까지만 다루고, 구현 세부는 위 위임 대상
문서를 단일 원천으로 삼는다.

### C-3. 날씨예보 킬러 콘텐츠 — 차별화 논리

`local_weather`는 기상청 예보와 **경쟁하지 않는 포지셔닝**이 핵심이다.

| 축 | 기상청 예보 | 이장·촌장 "감" 예보 |
|---|---|---|
| 목적 | 정확도(수치·확률) | 화용성(activity recommendation) — "내일 이런 활동 하기 좋겠다" |
| 범위 | 전국 일괄, 행정구역 단위 | 마을 단위, 개인화(물때·바람길·밭 상태 등 문서화 안 되는 현지 지식) |
| 신뢰 근거 | 관측·모델 | 오래 산 지역민의 경험적 직관 — 캐릭터성 자체가 콘텐츠 |
| 갱신 주기 | 일 수 회, 무인격 | 매일, 고정 출연진의 습관형 콘텐츠(리텐션 앵커) |
| 경쟁 관계 | — | **비경쟁**(오락·정보 보완재로 포지셔닝, 정확성 클레임 리스크는 면책 고지로 관리 — C-7 리스크 테이블) |

이 비경쟁 포지셔닝 덕분에 기상청 데이터 품질과 직접 비교되지 않으며, 오히려 "정확성보다 오래 산 지역민의 관점을
파는" 컨셉 자체가 타사가 복제하기 어려운 자산이다(제도권 기상 콘텐츠는 이 포맷을 구조적으로 만들 수 없다 — 공신력
있는 기관이 "감"을 표방할 수 없기 때문).

### C-4. 재미 요소

- **로컬 인물 캐릭터화**: 이장·삼춘·부녀회장 등을 고정 출연진으로 브랜딩(예명·캐치프레이즈) — B-4의 객원 인력과도 결합 가능.
- **사투리 자막 병기**: 원음(제주 방언)은 그대로 살리고 표준어 병기 자막을 추가 — 정체성은 유지하되 비제주 시청자·B2B 판매(B-3) 시 접근성 확보.
- **라이브커머스 이벤트성**(**커머스 1단계·링크아웃 정합화, Z1**): 실시간 경매·자체 재고를 잠그는 선착순 특가처럼
  자체 주문·재고 로직을 요구하는 게임화 요소는 1단계 구현 범위(상품 카드+외부 링크+클릭 계측뿐, 05 §D-4) 밖이다.
  MVP에서는 재고 로직이 필요 없는 형태 — 방송 중 한정 시간 할인코드 안내(구매·재고 확정은 외부 판매 채널이
  담당), 실시간 댓글 퀴즈·선착순 댓글 캡처 이벤트 등 — 로 시청 중 이탈 방지 및 채팅을 활성화한다. 실시간 경매·
  자체 재고 선착순 특가는 커머스 2단계(자체 결제, GMV 트리거 도달) 진입 이후 재검토 대상으로 05 §G에 등재한다.
  이벤트 운영 방안·비용은 doc 05 §D 소관(X8); 라이브 스트리밍 자체의 안정성은 doc 04 소관.

### C-5. 콘텐츠 캘린더

`CLAUDE.md` §2의 편성 원칙(월~금 지사 촬영, 토~일 센터 라이브, 긴급 즉시 라이브)을 콘텐츠 확보 관점에서 구체화한다.
아래는 **MVP 실제 편성(2지사)**과 **목표 상태(12지사 완성형)**를 분리한다 — 이전 버전은 5요일 풀편성 표 하나만
두고 본문에서만 "격일 로테이션"으로 완충했는데, 표 자체가 수정되지 않아 C-6 KPI(주 3~5건)와 불일치했다(C16).

**발효 시점 명시(신설, EVAL-ROUND-10 영역5 감점1/N2 대응)**: 아래 MVP 실제 편성(지사 월~금 촬영 로테이션)은
**W2 DoD 충족 이후 발효한다**(08 §A 앵커: 첫 촬영 재개 = W2 DoD 직전 — 그 전에는 지사 기자용 웹 업로드
경로 자체가 없다). 그 이전 구간(W0~W2)의 지사 촬영 편성은 **없음** — 이 구간에 시청 가능한 콘텐츠는 지사
촬영분이 아니라 센터 자체 제작분(소개 영상·날씨예보 파일럿 등, A-7 표 참조)뿐이며, 별도의 요일별 캘린더를
두지 않는다.

**MVP 실제 편성(애월·제주시 2지사, 격일 로테이션)**:

| 요일 | 애월 | 제주시 |
|---|---|---|
| 월 | 뉴스 소재 취재 | 휴 |
| 화 | 휴 | 뉴스 소재 취재 |
| 수 | 교양 | 휴 |
| 목 | 휴 | 지역특화 날씨예보 |
| 금 | 로컬 라이브커머스 소재 취재 | 휴 |
| 토 | 센터 라이브(주간뉴스, YouTube+Facebook 동시) | 센터 라이브 |
| 일 | 센터 교양/정치인 대담 라이브 또는 녹화방송 | 센터 라이브 |
| 상시 | 긴급(재난·위기) — 패스트트랙 즉시 라이브, 캘린더 예외 | 긴급 |

지사당 주 2~3건(요일 로테이션) 촬영이 이 표의 실제 산출량이다 — 애월 3건(월·수·금), 제주시 2건(화·목). 이는
C-6 KPI(첫 촬영 재개 시점 기준 M1 주 3건 → M3 주 5건, 재정박은 §C-6 참조)의 **출발점**과 정합하도록 맞춘 것이며,
M3 시점 주 5건까지의 증가분은 이 표를 요일 추가(예: 예비 소재일 편입)로 밀도를 높여 흡수한다 — 표와 KPI가 항상 숫자 그대로 일치한다는 뜻은 아니고,
표가 KPI 성장 궤적의 시작 상태를 보여준다는 의미다. 날씨예보는 매일 갱신이 이상적이나(C-3) MVP 2지사 인력 한계로
지사별 격주 로테이션으로 시작한다.

**로컬 라이브커머스 방송 슬롯(신설)**: 위 표의 "로컬 라이브커머스 소재 취재"(금, 애월)는 촬영·소재 확보이며,
실제 **라이브 방송**은 지금까지 이 캘린더 어디에도 없었다(EVAL 영역2·5 공통 지적). 아래와 같이 편성한다 — 두
지사 모두 현재 "휴"로 비어 있던 슬롯을 활용한다:

| 지사 | 요일(램프별) | 주체 | 빈도 램프 |
|---|---|---|---|
| 애월 | 목요일("휴" 슬롯 활용) | 지사 담당자 + 이장/어촌계장/부녀회장 | M3: 월 2회(격주) → **M6부터 월 4회(매주)**, M12까지 유지 |
| 제주시 | 금요일("휴" 슬롯 활용) | 지사 담당자 + 이장/어촌계장/부녀회장 | M3: 월 2회(격주) → **M6부터 월 4회(매주)**, M12까지 유지 |

**방송 시간 모수 — 단일 원천 선언(ROUND-4-DECISIONS V1)**: 정기 라이브(토요일 주간뉴스 + 일요일 교양/정치인
대담 또는 녹화방송) = 주 2회 × 회당 2시간 = **월 약 17.3시간**(주2회×2h×52주/12개월 환산). 라이브커머스 방송은
회당 **1시간**(가정 — 상품소개 중심의 짧은 포맷, 정기 프로그램 2시간보다 짧게 설계)으로 두고, 빈도는 위 램프
표를 따른다. **이 절(정기 라이브·라이브커머스의 회당 방송시간과 월간 방송 횟수)이 04 §E(용량·SLO#1 허용 중단
예산 산정)와 05 §B-1(라이브 인프라 비용 산정)이 인용하는 단일 원천이다** — 종전에는 이 값들이 05 §A-1/§B-1이
독자적으로 정의하고 04는 "01·05 어디에도 명시돼 있지 않다"며 임의 가정(2시간)을 쓰는 상태였으나(EVAL-ROUND-4
D-1), 편성의 실체(요일·슬롯·주체·빈도)는 이 캘린더가 쥐고 있으므로 값의 소유권을 본 절로 이관한다. 04·05는
이 값을 인용만 하며, 값이 바뀌면 본 절을 먼저 고친 뒤 04·05를 갱신한다.

이 방송은 C-6의 "지사당 주간 업로드 건수" KPI와 **별도 계상**한다 — 방송 자체는 라이브 이벤트이고, 방송 후
하이라이트를 VOD로 재업로드하는 경우에 한해서만 업로드 건수에 포함한다. 결제·정산은 커머스 1단계(링크아웃,
Z1) 원칙에 따라 상품 카드+외부 링크+클릭 계측만 우리 구현 범위이며, 자체 재고·주문 로직이 필요한 게임화
요소(실시간 경매 등)는 C-4에서 별도로 다룬다. 지사 담당자의 방송 준비·진행 부하는 C-7 총부하표에 반영했다
(M6 이후 매주 방송으로 전환되는 효과 포함).

**목표 상태(12지사 완성형, B-4 인력 확충 이후)**:

| 요일 | 편성 주체 | 콘텐츠 |
|---|---|---|
| 월 | 전 지사 | 뉴스 소재 취재 |
| 화 | 전 지사 | 교양(요일별 하위 토픽 로테이션) |
| 수 | 전 지사 | 지역특화 날씨예보(매일 갱신) |
| 목 | 전 지사 | 로컬 라이브커머스 소재 취재 + **라이브커머스 방송**(주 1회, 지사당 월 4회 — M6부터 도달, 위 램프 표 참고) |
| 금 | 전 지사 | 정치인 대담 또는 예비 소재(공백 보완용 재방영·하이라이트 리팩) |
| 토 | 센터 | 주간뉴스 라이브(YouTube+Facebook 동시) |
| 일 | 센터 | 교양/정치인 대담 라이브 또는 녹화방송 |
| 상시 | 지사/센터 | 긴급(재난·위기) — 패스트트랙 즉시 라이브, 캘린더 예외 |

가정: 목표 상태 표는 12지사·인력 확충 완료를 전제로 한 요일별 전 카테고리 커버리지 목표다. 킬러 콘텐츠(날씨예보)의
매일 갱신 속성(C-3)은 이 목표 상태에서만 성립하며, MVP 단계에서는 위 격일 로테이션 표가 실제 계획이다. 라이브커머스
방송의 빈도 램프(MVP 지사당 월 2회 → **M6부터** 지사당 월 4회, 위 "로컬 라이브커머스 방송 슬롯" 표가 소유)는
목표 상태(12지사 완성형)를 기다리지 않고 2개 지사 체제에서부터 이미 M6에 도달한다 — 목표 상태 표의 "주 1회"는
빈도 자체가 아니라 12지사 전체가 이 빈도로 커버된다는 확장 규모의 의미다. Z3 동시시청 계수와 함께 C-6이
소유하는 수요 궤적과는 별개의 공급 측 편성 궤적이다.

### C-5-1. 주 3건 → 주 5건 전환표 (첫 촬영 재개 시점 기준 M1 → M3, 재정박은 §C-6 참조)

C-6 KPI(첫 촬영 재개 시점 기준 M1 주 3건 → M3 주 5건)가 요구하는 증가분의 요일·소재·확보 경로를 명시한다 —
표만 두고 "밀도를 높여 흡수한다"고 서술만 하던 이전 버전의 공백을 메운다.

| 지사 | M1(첫 촬영 재개 시점, 현재) | M3(목표) | 추가 편성 요일 | 추가 소재 카테고리 | 확보 경로 | 담당 |
|---|---|---|---|---|---|---|
| 애월 | 주 3건(월·수·금) | 주 5건 | 화·목 신규 편입 | 화: 정치인 대담 또는 예비 소재(격주) · 목: 로컬 라이브커머스 보완 촬영 | 기존 담당자의 촬영 밀도 증가(신규 인력 없이) + W2 가동 이후 주민 제보(X5) 보완 | 지사 담당자(애월) |
| 제주시 | 주 2건(화·목) | 주 5건 | 월·수·금 신규 편입 | 월: 뉴스 소재(격일→매주 전환) · 수: 교양 · 금: 로컬 라이브커머스 소재 | 애월 캘린더와 동일 카테고리 로테이션 이식 + B-4 객원 인력 파일럿 위촉(3개월 시점 2명)의 촬영 지원 | 지사 담당자(제주시) |

가정: 이 증가분은 신규 채용 없이 ① 기존 담당자의 촬영 밀도 증가, ② B-4 객원 인력(파일럿 3개월 2명)의 촬영 지원,
③ W2 가동 이후 주민 제보(X5) 편입으로 흡수한다는 전제다. 이 전제의 실현 가능성은 **C-7에 신설한 "지사 담당자
겸임 총부하" 리스크가 상한**이며, 총부하가 이미 여유가 크지 않은 상태에서 이 전환표의 +2건이 추가로 얹힌다는
점을 함께 읽어야 한다.

**흡수 경로 실패 시 KPI 하향 규칙(신설, 영역5 감점 대응)**: 위 흡수 경로 3개 중 ②·③은 성사가 보장되지 않는다 —
②(B-4 객원 인력 촬영 지원)는 §B-6 "객원 인력 영입 자체 미성사" 리스크의 대상이고, ③(W2 주민 제보 편입)은 W2
산출물이라 08 시간축 매핑표상 기간이 미확정이라 M3 시점 존재 여부를 보장할 수 없다. 결국 ①만 남으면 담당자
1인의 촬영 시간이 12→20시간으로 늘어 C-7 총부하 상한을 추가로 밀어 올린다. 이를 자동으로 걷어내는 규칙을
둔다 — **첫 촬영 재개 +10주(=M3 실측 회의와 동시, 기준점 재정박은 §C-6 참조) 시점에 판정**: ②·③ 중 **하나만**
미충족(②는 위촉 계약 체결 0건, ③은 W2 미가동)이면 M3 목표를 주 5건에서 **주 4건으로 자동 하향**하고, ②·③
**둘 다** 미충족이면 주 3건(M1 수준)을 유지한다. 이 판정 결과는 C-6 KPI 표의 "지사당 주간 업로드 건수" M3
목표에 즉시 반영한다. **판정: 담당 지사 담당자 + 기획(PM), 시점: 첫 촬영 재개 +10주.**

가동되지 않은 경우 실제 부하는 이보다 각 2h 낮다.

가정: 지사 담당자 1인 풀타임 기준 주 가용시간을 ~40시간으로 볼 때, M3~M5 구간은 커머스 방송이 없는 주의
기본 합계가 대체로 상한 내에 있고, 당번과 커머스가 겹치는 주는 **약 37~47시간**(QR 부스 재산정·간단 모드 사후
자막 입력 신설·**카카오 채널 게시 행 신설(EVAL-ROUND-14 O1)** 반영, S4/O1)으로 초과한다. 그러나
**M6부터는 라이브커머스 방송이 매주 발생**하므로 "커머스 없음" 조합 자체가 사라진다 — 즉 매주 최소 30~40시간,
당번이 겹치는 주(2주에 1회꼴)는 37~47시간이 **상시** 발생한다. 여기에 C-5-1 전환표의 +2건(3개월 주 5건 목표)
까지 얹히면 촬영 항목이 최대치(20시간)로, 카카오 채널 게시 항목도 상한(≈50분)으로 함께 올라가 초과 폭이 더 커진다. 이는 "여유가 크지 않다"거나 "겹치는 주만
가끔 초과"하는 수준이 아니라 **M6 시점부터 당번 주마다 구조적으로 초과가 상시화**됨을 뜻한다(EVAL-ROUND-4

### D-1. 기존 지사 지표 충족 게이트 (확장 착수 전 확인)

### D-3. 확장 동결 조건

아래 중 **하나라도 해당하면 신규 지사 착수를 동결**한다. 동결은 "검토 보류"가 아니라 **신규 착수 액션 전면
중단**을 뜻한다.

1. **D-1 게이트 미충족**(WAU·SLA·손익 중 하나 이상 미달) — M6 말 판정에서 미충족이면 다음 판정 시점(3개월 후,
   M9 말)까지 동결한다.
2. **05 §B-3③ 현금 Kill Criteria 발동**(누적 상한 도달 또는 05가 신설하는 런웨이 트리거 — 05 소관) — 05가
   "지사 확장 동결"을 3단 의무 대응 중 하나로 이미 발동한 경우, 그 결정은 D-1 판정 결과와 무관하게 **상위
   게이트**로 즉시 적용된다(현금 우선 원칙 — D-1이 충족 상태여도 현금 동결이 우선한다).
3. **D-2 최소 요건 중 담당자 확보가 가정 리드타임(6~8주)의 1.5배(9~12주)를 초과해 지연** — 이 경우 해당 후보지만
   개별 동결하고 다른 후보지는 별도 판정한다.

**해제 조건**: 위 1은 다음 판정 주기(3개월)에 게이트 재충족 시 자동 해제. 위 2는 05 §B-3③이 정의하는 해제
조건을 그대로 따른다(05 소관, 본 절은 재정의하지 않는다). 위 3은 대체 후보지 확보 시 해제한다.

**판정: 기획(PM) + 센터장. 주기: 05 §B-3③ 현금 Kill Criteria 월례 점검과 동일 리듬으로 병행한다.**
