# 제온 로컬 LLM 구동 타당성 조사

> 조사일 2026-08-17. 사용자 지시: *"AI기반 편집을 하고 싶은데, LLM을 제온에 설치해서 구동하는게 얼마나 타당한지 조사해서 보고해줘, 그거 보고 판단할거야."*
> **모든 성능 수치는 제온 실측이다**(추정 아님). 재현 절차는 §6.

---

## 0. 결론

1. **돌아간다. 그리고 이 워크로드에는 지금 그대로도 충분하다.** 4B 모델 실측 **9.0 tok/s** 생성 · **140 tok/s** 입력처리.
   콘텐츠 1건당 LLM 소요 **약 2분**, 하루 최대 9건이라 **하루 17분**. 배치 작업이라 낮은 tok/s가 문제되지 않는다.
2. **다만 제온은 지금 자기 성능의 1/4만 쓰고 있다.** 메모리 24슬롯 중 **2개만 장착**돼 있어 메모리 대역폭이
   가능치(153.6 GB/s)의 **25%(38.4 GB/s)**다. LLM 생성 속도는 **전적으로** 이 값에 묶인다 —
   실측이 이를 증명한다: **스레드를 8→32로 4배 늘려도 생성 속도가 9.00→8.95로 그대로다.**
   DIMM 6개(중고 저가)를 꽂으면 **약 4배**가 된다. 이 프로젝트에서 가장 값싼 성능 레버다.
3. **비용은 로컬을 택할 이유가 못 된다.** 같은 작업을 Claude Haiku 4.5로 하면 **월 2,800원**(12지사 풀가동 기준),
   MVP면 **월 230원**이다. 로컬의 진짜 근거는 **데이터 주권** — 주민 제보 영상·초상권·미성년자 등장분의
   전사본을 외부 API로 내보내지 않는 것(07 §3-15 법률 리스크)이며, 그 근거는 **충분히 타당하다.**

**⚠️ 그러나 이 조사가 답하지 못하는 것이 하나 있고, 그게 실제 결정 요인이다** → §3. **"AI 편집"에서 LLM이
담당하는 몫은 전체의 일부**이고, 지금 막힌 곳은 LLM이 아니라 **그 앞의 STT(음성→텍스트)**다.

## 1. 제온 실측 하드웨어

| 항목 | 실측값 | 판정 |
|---|---|---|
| CPU | 2 × Xeon E5-2683 v4 (Broadwell, 2016) · 32C/64T · 2.1GHz | 충분 |
| 명령어 | AVX2 · FMA · F16C. **AVX-512 없음, AMX 없음** | 입력처리에 불리(세대 한계) |
| **메모리** | **16GB × 2 = 32GB**, DDR4-2400 ECC. **24슬롯 중 2개만 장착**(DIMM_C1, DIMM_G1) | ⚠️ **최대 병목** |
| 메모리 대역폭 | 이론 38.4 GB/s (2채널) / **실측 실효 22.4 GB/s** | 가능치의 25% |
| NUMA | 노드 1개(BIOS node interleaving 활성) | 소켓 간 인터리브 |
| GPU | **GeForce GT 710**(Kepler, 2014, 1~2GB) | **LLM 가속 불가** — 화면 출력용 |
| 디스크 | 루트 365GB 여유 / `/srv/dcpwork` 1.8TB 여유 | 충분 |
| 회선 | HuggingFace 다운로드 **7.5 MB/s** | 모델 수급 문제없음 |
| 빌드 도구 | gcc·g++·cmake·make **전부 없음** | 사전 빌드 바이너리로 우회(실증) |

**메모리 구성이 핵심이다.** E5-2683 v4는 **소켓당 4채널** DDR4-2400 = 소켓당 76.8 GB/s,
듀얼 소켓 합계 **153.6 GB/s**가 이 CPU의 설계값이다. 현재 소켓당 1채널씩만 채워져 **25%**만 쓰고 있다.

## 2. 성능 실측 (llama.cpp b10456, Qwen3-4B-Q4_K_M)

```
| 스레드 | pp512 (입력 처리) | tg128 (출력 생성) |
|-------:|------------------:|------------------:|
|      8 |   50.18 ± 0.14 t/s |    9.00 ± 0.01 t/s |
|     16 |   92.39 ± 0.43 t/s |    9.06 ± 0.01 t/s |
|     32 |  140.20 ± 0.40 t/s |    8.95 ± 0.02 t/s |
|     64 |  126.85 ± 4.30 t/s |    4.82 ± 0.32 t/s |
```

**읽는 법 — 이 표에서 가장 중요한 것은 오른쪽 열이 평평하다는 사실이다.**

- **출력 생성(tg)은 스레드 수와 완전히 무관하다** — 8스레드 9.00, 32스레드 8.95. 코어를 4배 줘도 **0% 개선**.
  이것이 메모리 대역폭 바운드의 교과서적 증거다. 토큰 1개를 만들 때마다 모델 가중치 전체(2.49GB)를
  메모리에서 읽어야 하고, 그 읽기 속도가 상한이다. **역산: 9.0 × 2.49GB = 22.4 GB/s** (이론 38.4의 58%, 정상 실효율).
- **입력 처리(pp)는 코어에 비례한다** — 8→32스레드에서 2.8배. 이쪽은 연산 바운드라 코어가 먹힌다.
- **64스레드(하이퍼스레딩)는 역효과** — pp는 10% 하락, tg는 **46% 폭락**. 물리 32코어까지만 쓸 것.
  (이는 미디어 인코딩에서 이미 확인된 특성과 같다 — infra §4-A ② "x264는 물리 코어 32에서 포화".)

### 2-1. 모델 크기별 예상 (같은 대역폭 22.4 GB/s에서 역산)

| 모델 | 크기(Q4) | 예상 생성 속도 | 800토큰 출력 소요 | 한국어 판단력 |
|---|---:|---:|---:|---|
| 4B | 2.5GB | **9.0 t/s** (실측) | 89초 | 단순 분류·요약은 가능 |
| 8B | 4.7GB | ~4.8 t/s | 167초 | 실용 하한선 |
| 14B | 8.5GB | ~2.6 t/s | 305초 | 편집 판단에 권장 |
| 32B | 19GB | ~1.2 t/s | 11분 | 메모리 여유상 무리 |

**DIMM 8채널을 채우면 위 값이 전부 약 4배**가 된다(14B가 ~10 t/s → 800토큰 80초).

## 3. ⚠️ 먼저 짚을 것 — "AI 편집"에서 LLM이 하는 일은 일부다

이 구분이 결정의 절반이다. 자동편집을 실제 공정으로 분해하면:

| # | 공정 | 필요한 것 | 제온에서 | 현재 상태 |
|---|---|---|---|---|
| 1 | **음성 → 텍스트(STT)** | Whisper 계열 **ASR**(LLM 아님) | CPU 가능, 10분물 ~3분 | ⚠️ **결정적 스텁**(미구현) |
| 2 | 무음·암부·정지 구간 검출 | FFmpeg `silencedetect`/`blackdetect` | **AI 불요**, 즉시 | 미구현 |
| 3 | **어느 구간을 남길지 판단** | **LLM** | 9 t/s로 가능 | 미구현 |
| 4 | **제목·캡션·요약 생성** | **LLM** | 9 t/s로 가능 | 스텁이 고정값 반환 |
| 5 | 컷·인트로/아웃트로·자막 번인·음량 정규화 | FFmpeg | 32코어로 빠름 | 미구현 |
| 6 | 장면 분류·인물 검출 | 비전 모델(VLM) | CPU로는 느림 | 스텁 |

**LLM이 담당하는 것은 3·4번뿐이다.** 업계 표준 워크플로도 정확히 이 모양이다 —
전사 → LLM이 **EDL(Edit Decision List)** 을 JSON으로 산출 → FFmpeg가 그 지시대로 자른다.
LLM은 영상을 만지지 않고 **텍스트만 읽고 텍스트만 쓴다.** 그래서 9 tok/s로도 충분한 것이다.

> **그래서 병목은 LLM이 아니라 1번이다.** LLM에 줄 전사본이 없으면 3·4번은 시작할 수 없다.
> 현재 `ai-worker`는 결정적 스텁이라 실제 전사본이 존재하지 않는다.
> **로컬 LLM을 도입하든 안 하든, 먼저 결정해야 할 것은 STT를 무엇으로 하느냐다.**

| STT 선택지 | 비용 | 속도(10분물) | 데이터 |
|---|---|---|---|
| **리턴제로(RTZR) API** — 현 정본 결정 | 10h 무료 + ₩1,000/h | 빠름 | **외부 전송** |
| **로컬 whisper.cpp** (large-v3, CPU) | 0원 | ~3분 | **제온 밖으로 안 나감** |
| 로컬 whisper.cpp (medium) | 0원 | ~1분 | 동일. 한국어 정확도 하락 |

**데이터 주권을 이유로 로컬 LLM을 택한다면 STT도 로컬이어야 논리가 성립한다** —
전사본을 외부에 보내는 순간, 그 뒤 LLM을 로컬로 돌리는 의미가 크게 준다.

## 4. 워크로드 대입 — 10분짜리 콘텐츠 1건

**전 공정 로컬 시나리오** (제온, 현재 메모리 구성):

| 공정 | 소요 |
|---|---:|
| 트랜스코딩(현행, 실측) | 18초 |
| STT (whisper large-v3 CPU) | ~3분 |
| LLM 편집 결정 (4B, 입력 3천·출력 800토큰) | ~2분 |
| FFmpeg 컷·렌더 | ~1분 |
| **합계** | **약 6~7분** |

**기자 대기시간이 18초 → 6~7분으로 늘어난다.** 이것이 실질 비용이다.
완화책: 프리뷰를 **2단계**로 — 트랜스코딩 직후 저화질 프리뷰를 먼저 돌려주고(현행 유지),
자동편집본은 준비되는 대로 갱신 알림. 기자를 세워 두지 않는다.

**처리량**: 하루 9건(12지사 최대) × 6분 = **하루 54분**. 32코어 서버에 전혀 부담이 아니다.

## 5. 클라우드 API 대비 — 비용은 결정 요인이 아니다

3·4번(편집 판단 + 캡션 생성)만 API로 보낼 경우:

| 항목 | 값 |
|---|---|
| 콘텐츠 1건 | 입력 ~3,000 토큰 + 출력 ~800 토큰 |
| Claude Haiku 4.5 단가 | $1 / MTok 입력, $5 / MTok 출력 |
| **MVP(2지사, 주 5건 = 월 22건)** | 입력 $0.07 + 출력 $0.09 = **월 $0.16 ≈ 230원** |
| **12지사(주 60건 = 월 260건)** | 입력 $0.78 + 출력 $1.04 = **월 $1.82 ≈ 2,700원** |

로컬 전력비도 비슷한 수준이다(제온은 이미 24시간 가동 중이라 **증분**만 계산: 하루 54분 × ~250W ≈ 월 6.8kWh ≈ 1,000원).

**⇒ 월 2~3천원 차이로는 어느 쪽도 정당화되지 않는다. 판단 기준은 비용이 아니라 아래 셋이다.**

| 기준 | 로컬 LLM | 클라우드 API |
|---|---|---|
| **데이터 주권** | ✅ 제온 밖으로 안 나감. 주민 제보·미성년자 등장분(07 §3-15)에 결정적 | ❌ 전사본 외부 전송 — 동의서 범위·처리위탁 고지 필요 |
| **판단 품질** | ⚠️ 4B~14B로 "어느 구간이 중요한가"를 판단. 편차 큼 | ✅ 확실히 우수 |
| **운영 부담** | ⚠️ 모델 관리·프롬프트 튜닝·품질 회귀를 우리가 진다 | ✅ 없음 |
| **지출 0 유지 지시** | ✅ 부합 | ⚠️ 소액이나 발생 |
| **외부 의존** | ✅ 없음 | ⚠️ 장애·정책 변경·쿼터 |

## 6. 재현 (실측 절차)

제온에 **시스템 패키지를 설치하지 않았다.** 홈 디렉터리에 사전 빌드 바이너리와 모델만 두었고,
`rm -rf ~/llm-bench` 한 줄로 완전히 원복된다(현재 약 2.5GB 점유).

```bash
ssh xeon
mkdir -p ~/llm-bench && cd ~/llm-bench
curl -sL -o llama.tar.gz https://github.com/ggml-org/llama.cpp/releases/download/b10456/llama-b10456-bin-ubuntu-x64.tar.gz
tar xzf llama.tar.gz
curl -sL -o qwen3-4b-q4.gguf "https://huggingface.co/Qwen/Qwen3-4B-GGUF/resolve/main/Qwen3-4B-Q4_K_M.gguf"
export LD_LIBRARY_PATH="$PWD/llama-b10456:$LD_LIBRARY_PATH"
./llama-b10456/llama-bench -m qwen3-4b-q4.gguf -p 512 -n 128 -t 8,16,32,64 -r 3
```

**함정 2개**(실제로 밟음):
1. **제온에 빌드 도구가 전혀 없다**(gcc/g++/cmake/make 모두 부재) → 소스 빌드 경로는 `apt install`을
   요구한다. **사전 빌드 릴리스 바이너리**가 유일한 무설치 경로이며, 실행 시 `libggml-cpu-haswell.so`를
   자동 선택한다(Broadwell = Haswell 후속이라 AVX2 경로가 정확히 맞는다).
2. **64스레드로 벤치하면 결과가 나빠진다** — 하이퍼스레딩이 메모리 접근을 경합시켜 tg가 46% 떨어진다.
   `-t 32`가 이 기계의 상한이다.

## 7. 선택지

### A. 로컬 LLM 도입 + 메모리 증설 (성능·주권 양립)
- DIMM **6개 추가**(현재 2 → 8, 채널당 1개씩)로 메모리 대역폭 4배. 중고 DDR4-2400 ECC RDIMM은 저가.
- STT도 로컬(whisper.cpp) → **전사본이 제온 밖으로 나가지 않는다.**
- 비용: DIMM 실구매비(수만 원 추정, **시세 확인 필요**) + 전력 증분 월 ~1,000원.
- 리스크: 소형 모델의 편집 판단 품질. **PoC로 먼저 검증할 것**(§8).

### B. 로컬 LLM 도입, 메모리는 그대로
- 지금 실측값(9 t/s)으로도 이 워크로드는 감당된다. 추가 지출 0.
- 더 큰 모델(14B)이 필요해지면 그때 증설.

### C. 하이브리드 — 로컬 STT + 클라우드 LLM
- 개인정보 민감도가 높은 **원본 음성**은 제온을 안 벗어나고, **텍스트만** API로.
- 판단 품질은 최상, 비용 월 2~3천원.
- 다만 전사본에도 실명·주소가 담길 수 있어 **주권 논거가 절반만 성립**한다.

### D. 자동편집을 AI 없이 먼저 (기계 편집만)
- 무음 트림 + 인트로/아웃트로 + 자막 번인 + 음량 정규화. FFmpeg만으로 결정적·테스트 가능.
- **AI 판단 없이도 자동편집의 8할은 여기서 나온다.** LLM은 그 뒤에 얹어도 늦지 않다.

## 8. 권고

**결정 전에 PoC 하나를 먼저 돌릴 것을 권합니다.** 이 조사가 답한 것은 *"돌아가는가"*(예)이고,
답하지 못한 것은 ***"쓸 만한 판단을 하는가"*** 입니다. 후자는 실제 우리 촬영본으로만 확인됩니다.

**PoC 설계**(약 반나절):
1. 이미 확보된 실기 촬영본(`movsample/*.MOV`, 63초·117초)을 whisper.cpp로 전사
2. 그 전사본을 4B와 14B에 각각 넣어 **EDL(어느 구간을 남길지 + 제목 + 캡션)** 을 뽑는다
3. 같은 입력을 Claude Haiku 4.5에도 넣어 **3자 비교**
4. 사용자가 결과물을 보고 판단 — *"이 정도면 쓰겠다"* 인지

PoC 결과가 나오면 §7의 A~D 중 하나가 자명해집니다. 지금 결정하면 품질을 모른 채 아키텍처를 고르게 됩니다.

**PoC와 무관하게 지금 확정 가능한 것 하나**: **STT를 로컬로 할지 RTZR API로 할지**는
자동편집 범위와 독립적이며, 다른 모든 선택의 선행 조건입니다.
